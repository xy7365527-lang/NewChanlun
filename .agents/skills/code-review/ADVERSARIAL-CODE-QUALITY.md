# 代码质量 lens

每个 reviewer 除 rubric 外再套本 lens。它是一个关于实现质量、可维护性、抽象质量与代码库
健康的严格标准。

首要：对代码结构要有野心。不要只找局部清理。主动寻找「code judo」式的重构——保持行为
不变、却让实现显著更简单、更小、更直接、更优雅。

## 基线

> 对当前分支改动做一次深度代码质量审计。
> 重新思考如何结构化/实现这些改动，在不影响行为的前提下显著提升质量。
> 改进抽象、模块化，减少意面，提升简洁与可读。
> 有野心：若存在涉及重构部分代码库的清晰改进路径，就去要。
> 极其彻底严格。量两次，切一次。

## 维度

每个维度只说一次，用适用的。

0. **对结构简化要有野心。** 不停在「这能再干净点」。找让整支分支、helper、mode、条件、
   层消失的重构。「code judo」常在。它更充分地用现有架构，让改动显著更简单。能删复杂
   度就别重排它。

1. **别让 PR 把文件从 1k 行以下推到 1k 行以上而没有极强理由。** 视为强气味。倾向抽
   helper/子组件/模块。diff 跨过阈值就问是否该先拆。只有文件仍保持清晰组织的强结构理由
   才能豁免。

2. **别让现有代码长意面。** 警惕插进无关流程的新 ad-hoc 条件、散落特例、一次性分支。
   把「随机位置的怪 if」当设计问题而非风格 nit。倾向把逻辑推进专用 helper、状态机或模块，
   而不是搅乱现有路径。

3. **偏清洁设计，不只接受能跑的代码。** 行为不变但结构显著更干净就推干净版。倾向删活动
   件的简化，而非把同样复杂度摊开的重构。

4. **偏直接、无聊、可维护的代码，不要 hacky 或魔法代码。** 把脆、ad-hoc、「魔法」行为当
   问题。警惕藏住简单数据形状假设的泛型机制。flag 薄抽象、恒等包装、只加间接不加清晰的
   透传 helper。

5. **影响可维护性时，推类型与边界清洁。** 质疑不必要的可选、`unknown`、`any` 或重强转
   代码。偏显式类型模型而非松散 ad-hoc 对象。分支靠静默 fallback 掩盖不清不变量时，问
   边界是否该显式。

6. **逻辑留在规范层，复用现有 helper。** 点出漏进共享路径的特性逻辑、或漏过 API 的实现
   细节。偏现有规范工具而非 bespoke 一次性。把代码推向对的包/服务/模块，而非默认漂移。

7. **不必要的顺序编排与非原子更新，在更清晰结构显而易见时当设计气味。** 无关工作无理由
   串行就问是否该并行。相关更新可能留半应用状态就推更原子的结构。不过度抠微优化，但要
   flag 让代码更脆的可避免编排复杂度。

## 输出期望

优先结构质量回归与漏掉的简化，其次意面与分支复杂度，再是边界、类型、文件大小，再是更小
的模块化与可读性。大结构问题在时不要用低价值 nit 刷屏。宁要少数高置信评论，不要一长串
表面笔记。

## 通过门槛

不要只因为行为看起来对就放行。下列视为**推定阻塞**，除非作者能给出理由：保留大量偶然复
杂度而 code-judo 能删掉它；把文件从 1k 行以下推到以上；加搅乱现有流程的 ad-hoc 分支；在
共享代码里散落特性检查；加不必要的抽象/包装/重强转契约；或复制现有 helper、把逻辑放在有
清晰规范家的错误层。这些不满足，就给显式、可执行的反馈，推更干净的分解。

## 语气

对质量直接、严肃、苛求。不粗鲁，但别把大可维护性问题软化成温和建议。代码把代码库弄得更
乱，就说。实现漏掉明显的大简化，也说。别满足于「也许改个名」当真正问题是结构性的。
