# 对抗评审 rubric

按适用的 lens 评审，不是每个 lens 都适用每个改动，用判断。

## 正确性

代码是否真的做到了意图说的？

- 边界：空输入、nil/未定义、边界值、并发访问
- 错误处理：错误被捕获、传播，还是被静默吞掉？
- off-by-one、类型强转、整数溢出、字符串编码
- 状态管理：竞态、陈旧闭包、悬空引用
- 快乐路径能走吗？悲伤路径能走吗？
- 幂等：操作跑两次、或上次跑到一半崩了，会怎样？答案若是「取决于留下什么状态」，就是缺对账步骤。
- 并发：多个 actor 能碰同一可变状态（文件、分支、共享数据）时，访问是被结构性串行化（锁、顺序阶段、排他拥有），还是靠守不住的口头约定？

发现潜在 bug 时，trace 执行路径。不要只标「这可能为 nil」，给出让它为 nil 的调用链。

## 根因 vs 症状

代码修的是真问题还是贴症状？

往往要看到改动文件之外。读周边代码（调用方、被调方、类型定义、兄弟模块），理解改动所在
架构。用可用工具（Read / Grep / Glob / Serena / codebase-memory）探索，跟调用链，读类型，
先理解代码为什么存在，再判断改动是否落在对的层。

- 掩盖更深不变量违反的 guard clause
- 藏住坏契约的重试逻辑
- 抹掉建模错误的类型强转
- 见 workaround 就问：为什么需要它？正确的修法长什么样？
- 本应修模块 B 契约、却修在模块 A
- 结构比指令强：若修法是注释「别做 X」或要人记的口头约定，问能否改成类型约束、lint 规则或运行时检查，让错的东西不可能发生。

## 结构完整性

代码是否与所在系统契合？

- 边界纪律：校验在系统边界，还是散在业务逻辑？数据进系统处校验一次，之后内部信任。
- 抽象层次：是否混了高层编排与底层细节？
- 耦合：是否引入让未来变更更难的依赖？
- 数据模型契合：数据结构是否匹配真实访问模式？对的结构让下游代码显而易见，错的处处打架。
- 外挂 vs 内建：改动是补丁式贴上去，还是读起来像设计当初就考虑了它？若当初就知道这需求，代码会长这样吗？
- 遗留双路径：是否加了新 API 却留旧 API？无外部消费方就同波迁移调用方并删旧路径，别留会变永久的兼容层。

不要因为简单代码缺抽象就惩罚。过早抽象比重复更糟。

## 验证

能从读代码判断它能用吗？

- 有测试吗？测行为还是测实现细节？
- 有能抓住回归的断言/不变量吗？
- 是 bug 修复：有 bug 的测试吗？
- 碰集成边界：全路径测了吗？
- 查真实的东西，不是代理：若用文件 mtime 或缓存状态查 liveness 而不读真实值，是验证缺口。
- 委托/异步工作：验证真实产出物，还是信自报与摘要？

## 复杂度预算

复杂度配得上它做到的事吗？

- 不损正确性与清晰度就能更简单的代码
- 只服务一个调用点的抽象
- 为尚不存在的场景做的配置/参数化
- 死代码、未用导入、残余参数
- 过度工程：无当前调用方的「以防万一」路径
- 为过渡稳定性留着、但迁移已完成的过时兼容路径——迁移完了就删脚手架
- 用户体验配得上复杂度吗？每个特性、控件、选项都要挣得存在。半成品特性比没有更糟。

更简单更好，除非更简单是错的。三行重复胜过过早抽象。

## 安全

只 flag 能实际 trace 通代码的安全问题。「这可能是个注入向量」而不展示输入路径，没用。

- 用户输入未经消毒流向危险 sink（SQL、shell、eval、innerHTML）
- 新端点缺鉴权/授权
- 代码、日志、错误消息里的密钥
- 安全关键路径的 TOCTOU
