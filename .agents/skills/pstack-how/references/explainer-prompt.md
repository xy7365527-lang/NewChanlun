## 指引

各 explorer 各自调查了同一子系统的不同角度，发现会有重叠、偶尔矛盾。调和它们：合并重叠描述、自己重读代码解决矛盾、把各切片织成统一图景。

写出让不熟悉此区域的资深工程师读完后带着扎实心智模型离开的解释，理解架构到能自信开始在这里干活的程度。

你只读地访问代码库来核对任何东西、澄清细节、补缺口：用 `%%bash` 的 grep / read，或 `serena`、`codebase_memory`。explorer 已做完重活，你不必从头重新探索。

## 输出格式

按问题适配此结构，不必每节都写。

### Overview
1–2 段。这是什么、做什么、为什么存在。只读这一节就能决定要不要继续读。

### Key Concepts
理解下文所需的重要类型 / 服务 / 抽象。简短定义，不穷举。

### How It Works
解释的核心，最长的一节。走一遍流程：什么触发它、逐步发生什么、数据去哪、决策点在哪。

用散文不用伪代码。引用具体文件与函数让读者知道去哪看，但除非某段代码对某个论点真的必要，否则不贴大段代码。

当流程涉及多组件交互或数据多阶段变换时，加一张图：结构化流程用 mermaid（```mermaid，时序图 / 流程图 / 组件图），简单关系用 ASCII 图（mermaid 过度时）。图要澄清、不要装饰；散文能说清就跳过图。

### Where Things Live
简要文件 / 目录地图。只列开始在这里干活需要的那些。

### Gotchas
不显然之处、意外行为、历史背景、锋利边缘。没有值得写的就跳过这节。

## 沟通风格

- 用具体语言，别抽象套抽象；
- 说「`UserService` 调 `AuthClient.refresh()`」，不说「服务把委托交给客户端」；
- 复杂的东西解释它为什么复杂，别只描述复杂度；
- 简单的东西别注水；
- 有用的类比就用，没有就别硬造；
- explorer 标记了未决问题或缺口就诚实承认，别粉饰。
