# 263号：元观察——v111-swarm

## 观察 1（语法记录候选）：258-2 决断路径——编排者先于蜂群判断

### 现象

258号元观察将 258-2（Gemini thinking 模式是否标准化）标注为"选择类（需编排者价值判断——thinking 模式 token 成本 vs 否定深度）"。按照四分法流程，选择类应通过 `/escalate` 上浮给编排者。

v111-swarm session 记录显示：编排者直接下发指令"Gemini 默认模型升级 2.5-pro → 3.1-pro thinking"，gemini-upgrade 工位执行了此指令（`engine.py` 中 `_MODEL` 从 `gemini-2.5-pro` 改为 `gemini-3.1-pro-preview`）。session 注释："258-2 已被编排者决断解决：thinking mode 标准化为默认"。

### 路径分析

258-2 的生命周期：
1. v107-swarm 产出 258-2，标注为选择类
2. 258号元观察确认分类正确，建议 `/escalate`
3. **v111-swarm 之前**，编排者已自行决断（不经过 `/escalate`）
4. v111-swarm 接收到的是编排者的**指令**（不是选择请求的回复）

路径跳跃：蜂群预期的流程是"258-2 选择类 → /escalate → 编排者决断 → 蜂群执行"。实际路径是"258-2 选择类 → 编排者独立判断（蜂群外部）→ 编排者直接下发指令 → 蜂群执行"。中间的 `/escalate` 步骤被跳过。

### 与 260-3 的对比

260-3（K4 顶点重命名）：工位提出选择 → Lead 标注选择类 → 编排者在蜂群内部回应决断。
258-2（thinking 标准化）：工位提出选择 → 元观察标注选择类 → 编排者在蜂群**外部**独立决断后以指令形式注入。

两者的编排者决断权是同一的，但注入路径不同。260-3 是"蜂群提问 → 编排者回答"，258-2 是"编排者主动告知"。

### 分类

定理类。编排者的决断权不依赖蜂群的 `/escalate` 流程——编排者可以在任何时刻、通过任何通道（蜂群内回应或外部指令注入）决断任何选择类问题。蜂群的四分法是蜂群内部的分类工具，不约束编排者的决断时机和路径。这不需要新规则，是编排者-蜂群关系的直接推论。

## 观察 2（发散信号）：新定理1 fail——操盘方法形式化的第一次否定

### 现象

Gemini 2.5-pro 对新定理1（层间同步赋格）给出 verdict=fail，三个否定点：

| 否定点 | 严重性 | 核心矛盾 |
|--------|--------|---------|
| 决策冲突 | 致命 | 三层并行运行 → 事件同时到达 → 无仲裁规则 |
| 赋格类比 | 重要 | 借用"赋格"但缺对位法规则，只有多声部表象 |
| 可证伪性 | 重要 | "当下哪层出现已确认的结构事件"过宽，后验可解释任何结果 |

### 本体论影响分析

新定理1的位置：255号对话从操盘方法推导出三层递归结构的本体论地位。新定理1是尝试将此结构形式化为可操作语法的**第一次尝试**。

fail 否定的层次：
- **不否定**：三层递归结构的本体论地位（这来自 255号对话的推导链，不依赖新定理1的形式化）
- **不否定**：层间存在同步/传播关系（这是缠论原文中级别递归的直接推论）
- **否定**：新定理1尝试用"先到先得"规则处理层间事件竞争的方案
- **否定**：新定理1尝试用"赋格"类比承载层间关系的形式化路径

类比：这相当于"三体问题的存在性已确认，但第一个求解方案被否定"。否定求解方案不否定问题本身。

### 与 256号的关系

256号（三态逆序形式化跳跃）已被 Gemini 指出"观察属性→操作指令"的推导链缺失。新定理1的 fail 是同一缺口的另一面：256号说"推导链缺失"，新定理1试图补这条链但方案被否定。两者指向同一个开放问题——**从 ker(D) 的观察属性到操盘操作指令之间的形式化桥梁尚未建成**。

### 分类

定理类（就 fail 结论本身）。三个否定点的论证结构清晰，concessions 为空（无让步），verdict=fail 是正当否定。新定理1的修复/重写/删除是选择类（256号已标注），v111 不改变此分类。

## 观察 3（收敛信号）：ceremony_scan 状态字段正则修复

### 现象

v111-swarm 的 commit 中包含 `ceremony_scan.py` 的修复：下游推论的 `status` 字段可能包含括号内理由（如 `resolved（理由）`），原代码直接匹配 `"resolved"` 会失败。修复方案：`re.split(r'[（(]', status, maxsplit=1)[0].strip()` 提取括号前关键词。

### 根因

谱系文件中 `status` 字段的写法惯例是 `resolved（理由摘要）`——这在 260号、261号中大量使用。ceremony_scan 的 `compute_advancement_candidates` 函数在两处使用字符串精确匹配，未适配此惯例。

结果：未结算的下游推论被漏检（状态字段因包含括号理由而不匹配 `"resolved"`），ceremony_scan 可能产出已实际 resolved 的推论作为待处理项。

### 与016号的关系

这是016号（规则没有代码强制就不会执行）的又一个实例——不是规则层面的问题（谱系写法惯例存在），而是代码层面未适配规则。修复是行动类（单一正确方案，无选择空间）。

### 分类

定理类。016号实例，修复方案唯一且已执行。

### 分类
