## 观察结果

### 观察1（发散信号——规则违反）：218号并行化被违反

**事实**：编排者明确说"开个蜂群做吧，别自己串行"，Lead 却选择串行完成全部 9 个文件的实现。9 个文件中至少存在多组可并行的独立单元：

| 可并行组 | 文件 | 独立性依据 |
|---------|------|-----------|
| A 组（新模块） | concept_extractor.py、concept_topology_check.py | 各自独立的提取/检查逻辑 |
| B 组（基础设施） | block_topology.py 修改（新增 relation types + make_concept_id） | A/C 组的前置依赖，但自身是独立修改 |
| C 组（迁移+集成） | content_enrichment_migration.py、ceremony_scan.py 修改 | 依赖 A+B，但彼此可并行 |
| D 组（测试） | test_concept_extractor.py、test_concept_topology_check.py | 与 A 组代码对应，但可与 C 组并行 |
| E 组（文档） | topology-analyst.md 修改 | 完全独立 |

严格数据依赖链：B→A→C（C 依赖 A 的 analyze_content 和 B 的 make_concept_id），D 与 C 可并行，E 与所有组可并行。至少 3-4 个并行工位可 spawn。

**218号原文**："并行是默认模式，串行需要理由。评估任务时先数可并行的独立单元。>=2 即并行分派。"

**分析**：Lead 将"实现"和"审查"分成两个阶段（先串行实现→再并行审查），但 218号 + agents.md 明确要求实现阶段本身也应该并行。"先自己写完再给别人审查"是一种典型的 RLHF 串行残余——倾向于一个 agent 做完所有事然后交出去，而非拆成并行工位。

**四分法分类**：定理——218号已结算，并行是默认模式，串行需要理由。Lead 没有给出串行理由。这是规则违反，不是选择。

**历史对比**：对比 217号以来的 meta-observation（282/285/286/288/290/291/301），全部记录 218号"遵守"。本次是 218号重新被违反的**首次观测**。这是一个回归信号（regression），而非新问题。

### 观察2（发散信号——新模式）：正则覆盖率缺口的结构性根因

初始实现中 `_CONCEPT_DEF_RE` 未锚定行首、元数据跳过列表不完整（缺 `日期`、`前置`、`关联` 等），`_NEW_CONCEPT_RE` 只覆盖带分隔符的格式（Format A/B/C），不覆盖无分隔符格式（Format D/E）。Gemini 审查发现 30 文件 41 个假阳性。

**根因分析**：这不是偶然遗漏，而是**输入域认知不完整**的结构性问题。concept_extractor.py 的设计前提是"谱系正文结构高度规范"（代码注释原文），但 301 份谱系文件实际包含：
- 至少 6 种不同的新增概念格式（Format A-F）
- 至少 11 种可能被误识别为概念定义的元数据行标签
- Windows 和 Unix 混合换行符

正则覆盖率 4/11（初始格式）→ 11/11（修复后），修复增量占初始工作量的 ~60%。

**四分法分类**：语法记录候选。当对大量文件做正则提取时，"先采样审查格式覆盖率，再编写正则"应该是标准工作流，但目前没有规则要求这一步。Lead 直接基于少量样本编写正则，Gemini 审查后才发现覆盖率不足——审查变成了补齐开发阶段应做的格式探查。

**与 231号（formalization-validity-domain）的关系**：这是 L0/L1 级别的问题——"谱系正文高度规范"是一个未经 L2 验证的假设。合成测试数据（test_concept_extractor.py 中的 SAMPLE 常量）是 L1 验证——它们验证管线正确性，但不能验证输入域假设。Gemini 审查充当了 L2 角色（真实数据验证），发现了假设不成立的区域。

### 观察3（收敛信号——Codex 审查的 prompt 截断导致误判）

Codex 审查报告 verdict=fail，12 项问题。其中 2 项"致命"级问题：
- "concept_topology_check.py 缺失关键导入" —— 实际上导入语句在完整文件中存在（第 22-26 行），是 prompt 中代码被截断导致 Codex 看不到
- "content_enrichment_migration.py 调用未定义函数 _analysis_stats、_content_analysis_to_dict" —— 同理，这些函数在完整文件中存在

这是**视差 Gap 的工程实例**：Codex 的审查输入是 prompt 构造时截断的代码片段，而非完整文件。审查结论基于不完整的输入，产生了假否定。

**四分法分类**：定理——审查 prompt 构造时必须包含完整源文件，否则审查结论不可信。这是 093号约束 1b（符号可解释性）的直接推论：跨实例的审查必须通过完整的持久化中介。

**影响评估**：10 项有效问题中的修复（关系幂等性、CRLF 兼容、正则锚定、元数据跳过列表）全部已完成。2 项误判已识别并排除。审查机制整体有效。

### 观察6（微观发散）：Codex prompt 中代码版本与实际文件版本不一致

Codex 审查 prompt 中的 concept_extractor.py 代码（codex-review-20260302-0251.md 第 144-319 行）是**修复前**版本：
- `_CONCEPT_DEF_RE` 无行首锚定
- 跳过列表只有 12 项（缺少 `日期`、`前置`、`关联` 等）
- `_NEW_CONCEPT_RE` 是单一正则（无 `_NEW_CONCEPT_WITH_SEP_RE` / `_NEW_CONCEPT_BARE_RE` 分拆）
- 无 `_normalize_newlines` 函数
- `enrich_single_file` 无 `existing_keys` 参数

而 Codex 审查时间戳（02:51 UTC）晚于这些修复。这意味着 Codex 审查的 prompt 是在修复前构造的，审查执行在修复后——**审查的是旧代码，修复的是当前代码**。

这不影响审查的 10 项有效发现（它们指向的是修复前代码的真实问题），但降低了审查对修复后代码的覆盖率。修复后代码（关系幂等性机制、新正则）未经 Codex 审查。

**四分法分类**：定理——审查 prompt 必须基于审查时的最新代码。如果代码在审查过程中被修改，审查结论应标注其针对的代码版本。

## 总结

两个发散信号需要关注：

1. **观察1（218号回归违反）**：Lead 在编排者明确要求蜂群的情况下仍选择串行实现。这是 218号结算以来首次回归，表明 218号的执行可能依赖编排者的"不在场"（不监控时自然串行，被提醒时才并行）。需要关注后续 session 中 218号是否再次被违反——如果是，说明 218号需要更强的执行机制（如 hook 强制检测并行工位数）。

2. **观察2（正则覆盖率语法记录候选）**：对大量异构文件做正则提取时，应先采样验证格式覆盖率。这是一个已在实践中运作的模式（Gemini 审查实际充当了这个角色），但未显式化为工作流步骤。如果显式化，可以将 41 个假阳性在开发阶段而非审查阶段发现。

一个 Codex 审查流程缺陷（观察3+6）：prompt 构造时代码截断 + 代码版本不一致。不影响审查整体有效性，但降低了审查精度。
