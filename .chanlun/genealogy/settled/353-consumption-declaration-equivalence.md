# 353号：消费断裂与声明缺口的等价性

## 1. 结论

声明缺口和消费断裂是同一个模式的两个方向：

| 方向 | 名称 | 形式 | 036号覆盖？ |
|------|------|------|------------|
| 声明 → 能力 | 声明缺口 | "声明了X但没有实现X" | ✓ 已覆盖 |
| 产出 → 消费 | 消费断裂 | "产出了Y但没有消费者消费Y" | ✗ 未覆盖 |

两者的共同结构：**一条连接声明了两个端点，但只有一个端点存在**。

### 等价性证明（L0推导）

036号原则："系统中任何层级，声明（declaration）与实际能力（capability）的不一致都会导致同构的失效模式。"

- 声明缺口：声明端存在，能力端不存在 → 声明无效
- 消费断裂：产出端存在，消费端不存在 → 产出无效

"产出"是"能力"的对偶——能力是"能做到X"，产出是"做出了X"。如果做出了X但没有消费者，等价于"能力存在但声明不存在"（反向缺口）。

因此：消费断裂 = 声明缺口的对偶形式。两者合并为统一检测规则：**扫描所有连接，检查两端是否都存在**。

## 2. 实例证据（v157-swarm 异质审计）

### 消费断裂实例（产出端存在，消费端不存在）

| 产出 | 产出者 | 缺失的消费端 |
|------|--------|-------------|
| `required_skills` JSON字段 | ceremony_scan.py | ceremony.md 不消费 |
| meta-observer 观察记录 | meta-observer agent | 写谱系后无下游动作 |
| source-auditor-prompt.sh | 开发者 | settings.json 未注册 |
| ceremony-step-guard.sh | 开发者 | settings.json 未注册 |

### 声明缺口实例（声明端存在，能力端不存在）

| 声明 | 声明位置 | 缺失的能力端 |
|------|---------|-------------|
| code-verifier file_write触发 | dispatch-dag.yaml | 无hook实现 |
| topology-manager 阈值触发 | dispatch-dag.yaml | 无检测逻辑 |
| 9个语义事件 | dispatch-dag.yaml | Claude Code不支持语义事件 |

### 递归闭合论证（编排者洞察）

编排者指出：如果消费链完整 → meta-observer 观察被消费 → 消费者发现断裂 → 产出修复工位 → 修复落地 → 消费链更完整 → ...

消费链断裂导致的不是某个具体功能缺失，而是**系统失去了自修复能力**。每个断裂点都是一个自修复回路的断点。修复优先级因此变为：先通消费链，具体修复作为工位自动涌现。

## 3. 036号定义域扩展

### 扩展前

> 声明-能力一致性原则：声明（declaration）与实际能力（capability）的不一致导致失效。

检测方向：声明 → 能力（单向）

### 扩展后

> 连接完整性原则：系统中任何连接（声明→能力、产出→消费、事件→处理器），两端都必须存在。单端存在的连接是断裂点，断裂点是自修复回路的断点。

检测方向：双向扫描

### 统一检测规则

对系统中每条连接：
1. 声明端是否存在？（dispatch-dag声明、agent定义、hook文件）
2. 能力端是否存在？（hook注册、ceremony消费步骤、代码实现）
3. 产出端是否存在？（ceremony_scan输出字段、agent产出文件）
4. 消费端是否存在？（ceremony.md消费步骤、下游工位、hook注册）

任何一端缺失 = 断裂 = 需要修复。

## 4. 边界条件

- D策略（082号）的合法性：某些连接**设计上**是单端的（Lead手动认领），这不是断裂而是设计选择。但如果Lead指令中缺少认领步骤，则D策略本身也是断裂。
- 平台约束：Claude Code不支持语义事件，导致dispatch-dag中的事件映射必然是断裂的。这不是实现缺口而是平台边界——应在dispatch-dag中标注"平台不支持"而非留为隐式断裂。
