## 结晶描述

**概念**：性能瓶颈/反转由**数据移动模式**（访存模式、拷贝量）决定，**不由编程语言或问题规模本身**决定。换语言（Python→Rust）、加规模、上 SIMD/GPU 是与"修数据移动模式"**正交**的维度——若数据移动模式错误，换语言可能不改善甚至恶化。

本节点记录该概念在**项目第二个独立子系统**的再次独立显现，确认其为**项目级稳定规律**。

## 跨域显现（knowledge-crystallization 稳定信号）

### 域1：逢亮认知引擎 / GPU架构（463 / 465 / 467，2026-03）

- 467号：GPU vs Rust+rayon 的转折点是**访存模式（规则 vs 不规则）**，不只是规模阈值。不规则图遍历在 GPU 触发严重 Cache Miss，CPU 缓存命中下邻域查询 <10ns vs GPU kernel 启动 5-10μs。
- 463/465号：kernel overhead / python-gpu roundtrip 的延迟**反转**——小规模不规则访存下，"更快的硬件"反而更慢，因为数据移动（PCIe 传输、kernel 启动）成本主导。

### 域2：缠论计算引擎 / Rust移植（本次，2026-06）

- bi 引擎 Rust 初版**比已优化的 Python 慢（0.8×）**。根因诊断：`unchanged` 分支无脑 `prev.clone()`，每 bar 全量拷贝增长到 43000 的笔列表 = **O(N²) 数据移动**。Python 版用"结果不变→复用引用"的零拷贝快路径已消除此项。
- 修复：改 `Arc<Vec<Stroke>>` 共享，`unchanged` 复用为 O(1) Arc::clone（架构报告 §5.1「前缀只读共享」）→ **2.4×**。
- 关键：性能反转不来自"Rust vs Python"（语言维度），来自**数据移动模式**（每 bar 全量拷贝 vs 共享）。换语言（已是 Rust）不解决；修数据移动模式才解决。

## 同构判定

两次显现：**独立子系统**（逢亮 topological-computation vs 缠论 newchan）、**独立任务**（GPU架构选型 vs Rust移植）、**独立时间**（2026-03 vs 2026-06）、**独立否定来源**（Gemini异质质询 vs L2 wall-clock实测）。显现同一概念 = knowledge-crystallization 定义的稳定信号（同一模式在多个独立上下文出现）。

## 边界条件（概念翻转）

- 该概念有效域：瓶颈是**数据移动主导**的工作负载（图遍历、流式增量重算、不规则访存）。缠论引擎逐bar重算与逢亮图遍历均属此类。
- 翻转条件：若某瓶颈是**纯指令吞吐主导**（密集规则算术、无数据移动瓶颈，如全图 PageRank、矩阵乘），则换语言/SIMD/GPU 直接有效，本概念不适用。这正是 467号给出的 GPU 真实有效域（规则批量计算）。

## 下游推论

- 引擎性能优化的**首要诊断步骤**是数据移动模式分析（拷贝量、访存规则性），而非"换更快的语言/硬件"。
- 架构报告 §5.1 的"前缀只读共享 + 尾部 CoW"是数据移动模式修复的范式——它正交于语言重写，两者可叠加（231号有效域：语言重写降常数，数据移动修复降阶）。
- 对未来引擎层移植（BSP/PH/递归栈）的告诫：移植时既要 bit-exact 又要避免重蹈 bi 的 clone 覆辙——native 语言不豁免 O(N²) 数据移动。
