## Response

**决策**：成立。L1/L2 的 `G=∅` 应判为 `inconclusive / underpowered`，不是“真证伪”。

代码层技术选择：不要把三条件法输出建模成 `bool` 或仅用空集合表达失败；应使用三态/带原因的判定结构，例如：

```rust
enum AlphaVerdict {
    Confirmed,
    Refuted,
    Inconclusive { reason: Underpowered },
}
```

**推理链**：  
`LCB(μ)>0` 在近似式下等价于 `n_eff > (1.645 * CV)^2`。若 CV=10，需要约 `271`；若 CV=20，需要约 `1083`。L1/L2 的 OOS 样本量只有 `38-188`，连 CV=10 的最低门槛都不到。并且 `n_eff` 通常不大于原始交易数，所以真实有效样本量只会更不利。

因此，L1/L2 上 `LCB<0` 更像是检验功效不足的结构性结果，而不是 `μ≤0` 的证据。`G=∅` 只能说明“当前样本和当前门槛下没有候选通过”，不能推出“候选真实不存在”。

**替代方案**：  
拒绝把 `G=∅` 直接判为 `Refuted`。这会混淆“未检出”和“不存在”。  
拒绝把该结果判为 `Confirmed`。功效不足只能反驳强证伪，不能提供 alpha 存在的正证据。  
拒绝临时降低 LCB 门槛救活候选。那会改变三条件法语义，除非另立实验协议。

**边界条件**：  
若 L1/L2 的真实 `CV_oos` 明显低于当前经验值，使 `n_eff > (1.645 * CV_oos)^2` 成立，则可重新考虑证伪力度。  
若未来扩样后 L1/L2 仍在充分功效下 `LCB≤0`，则可转为真实负证据。  
若失败来自条件1/2的领域概念错误，而不是条件3的 LCB 功效不足，则不能用本结论保护候选。  
若实际 block-bootstrap 实现与该近似充要条件不一致，应以实现级 `n_eff/CV/LCB` 诊断为准。

**风险**：  
CV=10-20 若不是 L1/L2 OOS 分层实测值，门槛推导会偏粗。  
block dependence、重尾 pnl、多重筛选会让有效样本量更难估，通常使功效问题更严重。  
`inconclusive` 容易被误用成“候选还活着”，正确含义只是“当前实验不能判死，也不能判成”。
