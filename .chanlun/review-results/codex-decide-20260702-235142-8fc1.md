**选项1：accept O(n²)**——correctness-first，若确认此为 `second_seq_scan_window=0`（无限扫）语义下

**选项2：advancing 变体**——不跨 append 持久化历史最小值，每次从"本次重扫覆盖到的区间"重新计算

## 现有实装代码（`rust/src/theta_v0/parser/segment.rs`，`IncrSegments::append`）

```rust
pub struct IncrSegments {
    segments_rc: Rc<Vec<Segment>>,
    end_indices: Vec<usize>,          // 段端在 strokes 数组中的下标
    pending_start: Option<usize>,
    strokes_len: usize,
    confirmed_len: usize,
    last_stroke: Option<Stroke>,
    /// 曾被跳过的 SecondKind 候选所属段的最早 seg_start，跨 append 持久化的历史最小值，
    /// 不因候选后续 confirm 或被新 confirmed 段覆盖而丢弃。
    earliest_unsealed_from: Option<usize>,
}

pub fn append(self, strokes: &[Stroke], config: &ParseConfig) -> IncrSegments {
    let n = strokes.len();
    let last_stroke = strokes.last().copied();
    if n == self.strokes_len && last_stroke == self.last_stroke {
        return self;
    }
    let IncrSegments { mut segments_rc, mut end_indices, earliest_unsealed_from: euf_persisted, .. } = self;

    // confirmed_bound 回退到 min(末段end, earliest_unsealed_from)。
    let confirmed_bound = match end_indices.last() {
        Some(&last_end_idx) => match euf_persisted {
            Some(euf) => last_end_idx.min(euf),
            None => last_end_idx,
        },
        None => 0,
    };
    let keep = end_indices.partition_point(|&end_idx| end_idx < confirmed_bound);
    let new_segments = Rc::make_mut(&mut segments_rc);
    new_segments.truncate(keep);
    end_indices.truncate(keep);

    // resume_seg_start = end_indices.last()+1（truncate 后倒数第二段的 seg_start）
    // ... [省略：找 resume_seg_start/resume_seg_dir 的分支逻辑，与本次讨论无关]

    let mut seg_start = resume_seg_start;
    let mut seg_dir = resume_seg_dir;
    let mut feat = FeatureSeqState::new(seg_dir, ExtendMode::Strict, TAIL_WINDOW, config.second_seq_scan_window);
    let mut cursor = seg_start;
    let mut euf_rescan: Option<usize> = None;   // 本次 append 重扫区间内新发现的 flag

    while cursor < n {
        let sk = &strokes[cursor];
        // ... 方向过滤 ...
        feat.append(cursor, h, l, strokes);
        let trig = feat.scan_trigger(strokes);
        if feat.skipped_secondkind() {
            euf_rescan = Some(euf_rescan.map_or(seg_start, |e| e.min(seg_start)));
        }
        let Some(hit) = trig else { cursor += 1; continue; };
        let k = hit.k;
        let end_stroke = k - 1;
        if end_stroke < seg_start || end_stroke - seg_start < min_seg.saturating_sub(1) {
            feat.skip_trigger(k);
            cursor += 1;
            continue;
        }
        let seg = make_segment(strokes, seg_start, end_stroke, seg_dir);
        new_segments.push(seg);
        end_indices.push(end_stroke);
        seg_start = k;
        seg_dir = opposite;
        feat.reset(seg_dir);
        cursor = k;
    }

    let pending_start = if seg_start < n { Some(seg_start) } else { None };
    // ★关键：历史最小值持久化——不因本次 rescan 干净（euf_rescan=None）而清零。
    let earliest_unsealed_from = match (euf_persisted, euf_rescan) {
        (Some(a), Some(b)) => Some(a.min(b)),
        (Some(a), None)    => Some(a),   // ← 即使本次重扫从 a 开始一路扫到 n 全干净，仍不清零
        (None, b)          => b,
    };
    IncrSegments { segments_rc, end_indices, pending_start, strokes_len: n, confirmed_len: keep, last_stroke, earliest_unsealed_from }
}
```

## `FeatureSeqState::scan_trigger` / `second_seq_has_fractal`（判定 flag 的来源）

`skipped_secondkind` 在 `scan_trigger` 内置真的条件：`has_gap && !second_seq_has_fractal(strokes,
seg_dir, b_stroke, second_seq_window)`——即某个分型候选有缺口，且"第二特征序列"（从 b_stroke+1 起，
取同向笔，方向性包含合并后）**当前**（对当前完整 strokes 数组，scan_window=0=无限）尚未出现任何分型。
`scan_trigger` 命中这种情况后 `continue`（不返回该候选，标记 flag，继续向后找其他候选）。

`second_seq_has_fractal` 的构造：从 `from_stroke_idx+1` 起单遍构建 elements（同向笔 + 方向性包含合并），
每加入一个新元素只检查**新尾部三元组**是否成分型，一旦成立立即 `return true`。**关键性质**：这个构建
过程完全由 `strokes[from_stroke_idx+1 .. 当前已知长度]` 的既定前缀决定——后续在数组尾部追加更多笔
**不会改变**已经算出的中间 elements（因为构建是严格前向增量、不回看未来），所以：
**一旦 `second_seq_has_fractal` 对某个 `(seg_dir, from_stroke_idx)` 在某个 n 处返回 true，它对任何
n' > n 也必然返回 true**（早终止扫描到的那个三元组在更长的数组里仍然会在同样位置被同样地扫到并判真）。
反之，某次返回 false 只说明"对当前 n 尚未发现"，不排除未来更长的 n' 才发现。

## 我（codex-challenger 工位）对"advancing 变体"的初步 sound 草证（请你审查/找反例）

**声称的不变式**：`confirmed_bound`（=下一次 append 的 `resume_seg_start` 的锚点，通过 truncate
`end_indices` 间接决定）与 `earliest_unsealed_from` 的"跨 append 持久化"字段无关，只需**每次 append
完整重扫 `[resume_seg_start, n)` 后，若该次重扫全程零 flag（`euf_rescan == None`），就允许清零**
（即把 `(Some(a), None) => Some(a)` 改为 `(Some(a), None) => None`，从而 `confirmed_bound` 可以在
下一次 append 中跳到 `last_end_idx`，边界真正前移；候选仍未解决则 `euf_rescan` 每次都会在同一个
`seg_start` 位置重新被打上，`confirmed_bound` 原地不动，等价于当前行为）。

**论证要点**：
1. `resume_seg_start` 恒等于**上一次 append 计算出的 `confirmed_bound` 所对应的截断点附近**——因为
   `end_indices` 在本次 append 开头就是按上次的 `confirmed_bound` truncate 过的。所以只要"改成不清零
   历史"和"完全按本次新鲜重扫结果决定"这两种策略在**同一个 append 内**对 `confirmed_bound` 的计算
   一致（即都用"本次重扫是否发现 flag"作为唯一依据，不额外叠加更早期 append 的历史 flag），"重新发现
   同一个尚未解决的候选"这件事会在**每一次** append 中被重新执行一遍（因为 `resume_seg_start` 结构性
   地锚定在那个位置，不会绕过去）——所以去掉历史 min 累积并不会"忘记"一个真正尚未解决的候选，因为
   下一次 append 的重扫窗口本来就会重新覆盖到它、重新把它标记出来。
2. 真正的差异只发生在"该候选本次已经解决"（`second_seq_has_fractal` 从 false 变 true）且**从
   `resume_seg_start` 到 `n` 的整个重扫过程中不再有任何新的候选被跳过**的那一刻：现行实现（历史 min
   永不清零）会继续把 `confirmed_bound` 锁死在这个早已解决的位置，导致 `euf_min=euf_fin=10`——即使
   之后每次 append 都从 10 开始重扫却从未再发现 flag（这正是本报告观测到的 O(n²) 现象的候选根因：
   **不是候选真的永不 resolve，而是清零逻辑被禁止了**）。若这次重扫全程零 flag，按"一旦真则永真"的
   单调性，[resume_seg_start, n) 内做出的每一个分段决策此刻都是"扫描全程无跳过候选"下产生的、因而
   等价于把 `divide_segments_with_tail` 直接跑在这个后缀上的结果——不存在"更早候选后来 resolve 后
   会级联改写这些决策"的风险（因为这次重扫本身就没有任何未 resolve 的候选残留）。
3. 潜在反例方向（我没有排除，请重点审查）：
   a. `resume_seg_start` 是否可能**跳过**（大于）某个仍然真正 unresolved 的候选位置——例如
      `confirmed_bound` 的 truncate 用的是 segment 的 `end_idx`（段端），而 flag 记录的是 `seg_start`
      （段起点，即上一段端+1）。是否存在 `end_idx` 与 `seg_start` 之间的差 1 类边界，使得
      `partition_point` 的截断结果与 flag 位置有一个off-by-one，导致 truncate 后 `resume_seg_start`
      实际上比 flag 位置**更靠后**（从而漏扫）？
   b. `pending_start`（当前未闭合的尾段起点）本身是否也需要参与 `confirmed_bound` 计算——若
      `pending_start < confirmed_bound` 而 pending 段本身还没决定方向就被"当作已确认前缀"处理，是否
      存在风险？
   c. 是否存在"同一次 rescan 内，earlier 位置的候选被跳过→继续扫描→later 位置发出一个 segment→
      更 later 的位置再次被跳过"的情形，导致 `euf_rescan` 的 `.min()` 逻辑取的是**最小 seg_start**，
      而实际"最早未解决候选"对应的是**更早的一个 seg_start**、却因为某种迭代顺序没被记录进
      `euf_rescan`？（即 `euf_rescan` 的 min 折叠是否有遗漏路径）
   d. `feat.reset(seg_dir)` 是否会在某个 segment 内把**上一个** segment 遗留的 `skipped_secondkind`
      标志"带过去"，造成误报或漏报？

## Response

**决策**：选项2，`advancing` 变体。

但精确定义不是只改 `(Some(a), None) => None`，而是 append 结束后直接：

```rust
let earliest_unsealed_from = euf_rescan;
```

`euf_persisted` 只用于本次 append 开头决定回退窗口；本次重扫完成后必须丢弃历史值。

**推理链**：`earliest_unsealed_from` 的领域含义应是“当前 prefix 下仍未封口的最早 frontier”，不是“历史上曾经 skipped 的最早位置”。`second_seq_has_fractal` 一旦为 true 后续永真，所以旧候选一旦在本次完整重扫中不再触发 flag，就没有继续锚定的语义理由。当前 `euf_min=euf_fin=10` 更像是状态语义错了，不是 canonical `scan_window=0` 的内在下界。

不变式应写成：

`append(S[0..n))` 后，`earliest_unsealed_from == min(seg_start)`，其中 `seg_start` 来自本次从 `resume_seg_start` 到 `n` 的确定性重扫中实际发生 `skipped_secondkind` 的段；若本次没有发生，则为 `None`。下一次 append 若它仍 unresolved，会被同一重扫窗口重新发现；若已 resolved，则因单调性不可重新变 false，可以安全前移。

(a) off-by-one：在“段连续，下一段 `seg_start = prev_end + 1`”成立时不是风险；`end_idx < euf` 会保留上一段，resume 回到 `euf`。加边界测试即可。  
(b) `pending_start`：不是这个字段的职责；无 euf 时本来就会丢最后完成段重扫尾部。只有旧 `pending_start` 被拿来当 confirmed prefix 才是真风险。  
(c) `.min()`：概念上正确，前提是 `skipped_secondkind` 在一次 `FeatureSeqState` 内 sticky 到 caller 观察。若它是瞬时 flag，则当前实现已不可靠。  
(d) `feat.reset`：真实实现风险。它必须清掉 skipped flag；否则主要是性能假阳性，严重时污染后续 frontier。

**替代方案**：拒绝选项1。现在不能证明 O(n²) 是无限窗口语义下界；相反，已有证据指向历史 frontier 不清零。有限 `scan_window` 可以作为运行时性能开关，但不能替代 canonical bit-exact 路径。

拒绝选项3。候选 C 仍有循环论证：先花 O(n) 判断是否 cascade，或者每次直接全量重算，都是 append 序列 O(n²)。它适合做 oracle/debug assert，不适合主路径。

**边界条件**：若改成 `euf_rescan` 后全量 `divide_segments_with_tail` 对拍出现任一字段不一致，推翻。若实际 `second_seq_has_fractal` 会因未来 append 改写历史 elements，推翻。若段连续/resume 不变式不成立，推翻。若修正后真实 workload 仍长期从早期 index 重扫，再考虑 indexed watcher 或接受 O(n²)。

**风险**：最大风险是只改 None 分支而保留 `(Some(a), Some(b)) => Some(a.min(b))`，那仍会把已解决的 `a` 锁死。必须新增守卫：每 append 全量 oracle 对拍；flag resolve 后清零/前移测试；清零后 later reflag 测试；`seg_start = prev_end + 1` off-by-one 测试；`feat.reset` 清 flag 断言；CL 300K 回归确认 euf 不再固定 10。
