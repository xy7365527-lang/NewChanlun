## 我（agent）提议的 D1 收窄版设计（供 codex 审查/推翻/修正）

### 核心思路：把比较对象从"全局单动作"收窄到"单槽位（level, 方向）局部决策"

`interp::interpret` 的 fold 本质上是**按槽位（level, σ）独立**处理的（见 `interp.rs:983-997`：`slot_in_at`/`slot_this_fold` 都以 `(c.level, c.dir)` 为键）。这意味着，**限定在单一固定槽位上**，interp 对这个槽位的裁决其实退化为"从多个候选中选一个赢家（≺_Θ 全序保证），然后对这个赢家做一个局部的 close/open/record 三选一"——这个局部三选一恰好是"单一决策"的粒度，与 mutex_class 的语义粒度一致。

**收窄命题**：

对固定槽位 `(ℓ, σ)`（某一级别 + 某一方向），定义**局部谓词投影** `proj(ℓ,σ)(Γ, active)`：
- `p_close`：`active` 中存在 `(ℓ, ¬σ)` 方向的未关闭腿，且 Γ 中存在方向为 σ、级别为 ℓ 的候选（reverse_signal 触发关闭）。
- `p_open`：`active` 中不存在 `(ℓ, σ)` 或 `(ℓ, ¬σ)` 的未关闭腿（空槽位），且 Γ 中存在 ≺_Θ 全序下**该槽位的赢家候选**（即所有目标本槽位的候选里，theta_key 最小的那个）方向为 σ。
- `p_hold`：槽位已被 σ 方向占据（同向加仓语境）或槽位被 ¬σ 占据但无反向触发。

**排除 P1（risk_liquidate）出收窄范围**——这是本收窄版与原 D1 最大的修正：P1 的全局强平语义**不经过 interp 的候选 fold**，而是经由 `KThetaRiskGate.force_flat` 直接把 `pi_theta_position` 的可行集收窄到 `{0}`（`coverage.rs:1903`，`force_flat` 优先收到 {0}）——这是完全独立于 interp 三桶机制的另一条路径（净持仓层的 K_Θ 约束，不是候选层的谓词优先级）。原 D1 设计把 `P1 risk_liquidate ← KThetaRiskGate.force_flat` 硬塞进桥接函数本身就是范畴混淆的一部分（P1 根本不该被投影到 interp 的候选桶里，它作用在净持仓这个更高的抽象层）。收窄版**明确声明 P1 不在比较范围内**，只比较 P2..P8（或 Lean 版 p1..p9 里对应"开/平/加/保持"的子集，扣除强平/去杠杆/执行修复这几个账户层专属类）。

**property test 方案**：
1. 生成随机 Γ（多候选，跨多个不同 (level,σ) 槽位）+ 随机 active（多条活动腿）。
2. 对每个出现在 Γ 或 active 中的槽位 (ℓ,σ)，独立计算 `proj(ℓ,σ)`，喂给 `mutex_class`（只用 P2..P8 子集，P1 固定 false）。
3. 断言：该槽位的 mutex 类别（Cj, j∈2..8）能一一映射回 `interp::interpret` 对该槽位赢家候选的桶归属（close/open/record）。
4. 因为现在是"槽位局部"比较，不再需要处理"同一时刻多槽位同时开关"这个原范畴错误——每个槽位独立验证，槽位之间互不干扰（interp 本身就是按槽位独立 fold 的，这是代码事实，不是收窄版的假设）。

### 我的疑虑（留给 codex 审查）

1. `interp` 的 fold 是**顺序敏感**的："本 fold 已开同 slot"（`opened` 累积，`interp.rs:991`）意味着如果 Γ 里同一槽位有多个候选，≺_Θ 排序后**第一个**处理的候选决定这个槽位的归属，后续同槽位候选一律进 `record`（冲突记录）。而"槽位赢家"这个概念在我的收窄命题里等价于"≺_Θ 最小的候选"，需要确认这与 interp 实际 fold 顺序处理是否真的等价（有没有可能因为 fold 的顺序性，槽位赢家不是简单的 theta_key 最小，而是依赖其他槽位候选处理后 active 状态的变化）？我倾向认为对同一槽位而言两者等价（因为 fold 对不同槽位的处理不会相互影响同一槽位的判定——但这需要 codex 验证，不是不言自明）。
2. `record` 桶（𝒦_x）在 interp 里既包含"非方向候选"也包含"同槽位冲突候选"——mutex_class 的 P8(hold)/C_0 兜底 是否能对齐这两种不同来源的 record，还是需要拆分成两个不同的 mutex 类别？

## Response

**决策**：D1 收窄版“方向正确，但原表述需再收窄”；Q2 选 **(a)**：保留 `closed_loop/mutex_interp.rs`，删除 `strategy/mutex.rs`。

**推理链**：
D1 不能说成静态 `per-slot(ℓ,σ)` 等价。`interpret` 的真实粒度是“按 `theta_key` 排序后的候选逐个 fold”，且 close 会修改同 level 的 `working` 状态，open 会写入 `opened`。所以良定义命题应改为：

给定排序后第 `i` 个候选 `g_i` 和其 prefix fold state，局部投影 `proj_i(g_i, working_i, opened_i)` 产生唯一 `Close/Open/Record` 决策；把所有局部决策聚合后，恰等于 `interp::interpret(Γ,A)` 的三桶输出。

P1 全局强平必须排除。代码里 `force_flat` 收窄的是 `KThetaRiskGate -> pi_theta_position` 的净持仓可行集，不是候选桶解释器路径。把 P1 投到 `interp` 桶里就是范畴错误。

`record` 不需要拆生产桶，但测试 oracle 必须拆原因：`RecordNonDirectional` 与 `RecordDuplicate/SameDir`。外部三桶仍都落 `record`；内部原因拆分是为了防止测试把两种不同语义都糊成 “hold” 后漏测。

property test 可执行，但要修正覆盖：
- 不要只测每个 `(ℓ,σ)` 的“赢家”；要测候选 prefix trace。
- 必测 permutation invariance，因为 `interpret` 先按 `theta_key` 排序。
- 必测 close-consumes-candidate 后，同 level 后续候选还能 open 的序列。
- 必测 Flat/无类候选、同 slot 重复、已有同向 active、相反 active、跨 level 混排。
- 若 active 允许同 level 多条腿，close 目标依赖 active 输入顺序；要么把 active 规范化为每 `(level,dir)` 至多一条，要么把“first matching active leg”写入命题。

**替代方案**：
拒绝原 D1 静态 per-slot 版本：它忽略 prefix state，尤其 close 后状态变化和后续 open。

拒绝 Q2(b)：把 `mutex.rs` 降成教学代码仍保留两条谓词链，会继续制造“哪个是规范”的维护成本。

拒绝 Q2(c)：`mutex_interp.rs` 是 Origin `chooseAction` 的 Rust conformance fixture；删它会丢掉 canonical port 的本地可执行锚点。

**边界条件**：
若后续证明 `strategy/mutex.rs` 实际早于 619 且只是历史待重锚库，可改判为“遗留但必须降权/重锚”；但当前 git 证据显示它与 `mutex_interp.rs` 同在 `ff88d81bc9` 新增，晚于 619 四天，所以不适用。

若 Origin 的 9 谓词链被正式替换，或 `interp` 改成真正全局单动作解释器，Q2 和 D1 都要重裁。

**风险**：
D1 测试若直接复刻 `interpret` 分支，会变成同义反复；应写一个小的独立 oracle，复用 `theta_key/reverse_signal` 可以，分支状态机不要直接调 `interpret`。
