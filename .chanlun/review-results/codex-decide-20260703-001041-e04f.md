## 问题

项目 `rust/src/theta_v0/` 下曾并存两个"零生产消费者"的谓词解释模块：

- `strategy/mutex.rs`（8 谓词 `MutexClass`，字面对齐 PDF《买卖点alpha2.pdf》Doc2 §5 / Doc3 §6）
- `closed_loop/mutex_interp.rs`（9 谓词 `ActionClass`/`choose_action`，模块文档自陈"忠实镜像 Lean 原型 `FullDefinitionStrategy.lean`"，且自陈"与 PDF §5 的 8 谓词语义映射不强行 1:1"）

两者都不被生产代码 `strategy/interp.rs::interpret` 消费——生产路径走 `interp::interpret` 的 `≺_Θ` 全序三桶 fold（close/open/record），两个谓词模块只是"测试期待建的对拍/验证脚手架"。

团队需要决定：这两个模块该删哪个、留哪个，作为 D1（逐候选级等价 property test）的 oracle。

## 两次独立 Codex decide 调用的结论（时间戳相差约2分钟，同一任务描述）

### 裁定一（ws-codexq2，先完成）：**删 mutex_interp.rs，留 mutex.rs**

核心论据（功能适配性）：
1. `choose_action` 的 9 谓词/10 类 `ActionClass`（含 `Deleverage`/`ExecutionRepair`/`PhaseThreeAccreteCore` 等）比生产 `interp::interpret` 实际输出的三桶（close/open/record）粒度**更细**，这些细分类别在生产代码里根本没有对应实现——用它做 D1 等价测试的 oracle 会重犯"范畴不匹配"错误。
2. `mutex_class` 的 8 谓词/三桶粒度与生产 `interp` 输出**恰好匹配**，是唯一能在同一输入空间上比较的候选。
3. `no-patch-mentality`（项目语法规则）禁止补丁式重复实装并存：两个"权威镜像"并存，日后测试失败时无法判断哪个代表项目规范语义。

### 裁定二（ws-codexp2，冲突记录）：**删 mutex.rs，留 mutex_interp.rs**

核心论据（治理合规性）：
1. 项目谱系 619 号（已结算 2026-06-26）裁定：`formal/Origin/` 六层是 `formal/` 的**唯一 canonical base**，"所有后续形式化（完全分类忠实编码 + 全定义策略 + T 层零件）向 Origin 对齐实例化"，旧零件走"port 重锚"而非"独立重新证明"。
2. `mutex_interp.rs::choose_action` 自陈"忠实镜像 Lean 的 9 谓词链（对齐 `Origin.FullDefinitionStrategy.chooseAction`）"——按 619 的语言这是合规的 Origin port。
3. `mutex.rs` 是直接从 PDF **独立重新推导**（不 port 自 Origin），且 git 时间线显示它是在 619 号裁定结算 4 天后才新增的（与 `mutex_interp.rs` 同一 commit）——按 619 纪律，这构成"结算后新增的独立重证"，涉嫌违反 619 已确立的架构纪律。

## Response

**决策**：选 **A**。619 号不覆盖 `rust/src/theta_v0/` 下这个零生产消费者的 Rust 测试辅助模块。保留 `strategy/mutex.rs` 作为 D1 桶级 property test oracle；删除 `closed_loop/mutex_interp.rs`。

**推理链**：
619 的约束对象是 `formal/` 内的 Lean canonical base。题面摘录里最强表述是“Origin 六层是 `formal/` 的唯一 canonical base”，并且影响范围枚举的是 `formal/Origin/`、`formal/Strict/`、`formal/Tlayers/`、`formal/Foundation/`、`formal/theta_v0` 等 Lean 形式化路径。这里的“所有后续形式化”应按该上下文解释为 Lean 形式化工作，不应扩张成“任何 Rust 注释里自称镜像 Lean 的代码”。

D1 的目标不是证明 Origin 合规，而是验证 Rust 生产路径 `strategy/interp.rs::interpret` 的逐候选桶级行为。生产解释器输出的是 close/open/record 三桶 fold；`mutex.rs` 的 8 谓词 + `bridge_bucket()` 正好落在这个比较粒度。`mutex_interp.rs` 的 9 谓词/10 类 `choose_action` 比生产语义更细，`Deleverage`、`ExecutionRepair` 等类在当前生产输出中没有同构目标。拿它做 D1 oracle 会把“Origin 行为分类”问题混进“Rust 生产桶等价”问题。

所以最终去留是：

- `strategy/mutex.rs`：保留，但身份限定为 **D1 bucket-equivalence shadow oracle**，不是 formal canonical base，也不是 Origin port。
- `closed_loop/mutex_interp.rs`：删除，不作为 D1 oracle 复活。
- `mutex.rs` 当前新增的 `predicates_of()`、`bridge_bucket()`、`shadow_fold_bucket_equivalence` 方向继续推进。
- 文档里保留一句边界说明：若将来要做 Origin conformance test，另建 Origin-port 测试层，不复用 D1 桶级 oracle 当 formal 权威。

**替代方案**：
B 拒绝：把 619 扩张到所有 Rust “镜像 Lean”代码，会让目录边界和治理对象失效。一个 Rust 注释不能自动把测试脚手架升级为 formal canonical artifact。

C 拒绝：双删会丢掉当前最小可用的 D1 验证面。自建限域 oracle 不触发 619，前提是它明确只测 Rust 生产桶等价，不宣称 formal 权威；既然 `mutex.rs` 已经是这个形态，没必要重建。

D 拒绝：`ActionClass -> 三桶` 投影不是当前已证明良定义的简单映射。尤其 `Deleverage`、`ExecutionRepair`、`PhaseThreeAccreteCore` 这类细分动作要么无生产对应，要么需要不可达性证明。为 D1 加这个 wrapper 是多写代码解决错问题。

**边界条件**：
此裁决在以下任一条件成立时翻转：

- 新结算谱系明确规定：`formal/Origin` 是所有语言实现、Rust 测试 oracle、镜像模块的唯一语义来源。
- D1 目标从“Rust `interp::interpret` 桶级等价”改成“Rust 对 `Origin.FullDefinitionStrategy.chooseAction` 的 faithful port conformance”。
- 生产 `interp::interpret` 升级为 9/10 类动作语义，并且三桶不再是真实比较面。
- `mutex_interp.rs` 提供并验证了总定义、无歧义的 10 类到三桶投影，且不可达类别有测试或证明支撑。

**风险**：
最大风险是 `mutex.rs` 以后被误读成新的 Rust 侧 canonical semantics。用文档和命名压住：它只服务 D1 桶等价。

第二个风险是桶级测试掩盖 Origin 细分类差异。这不是当前 D1 要解决的问题；需要时另开 Origin conformance 层。

第三个风险是 PDF 语义与 Origin 后续裁定冲突。冲突发生时，D1 继续守生产桶等价，formal 合规测试另行重锚到 Origin。
