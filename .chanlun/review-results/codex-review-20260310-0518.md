# Codex 异质审查上下文：OpenClaw 集成技术可行性

## 审查目标

评估在 OpenClaw（TypeScript/Node.js 项目）基础上构建 RTAS 蜂群的技术可行性。
RTAS = Recursive Topology Async Swarm（递归拓扑异步蜂群）。

## 我们的现有系统（NewChanlun，Python）

- 缠论引擎：K线分析，笔/线段/中枢/背驰识别（Python）
- 拓扑计算：topological-computation/ 目录，daemon.py 运行
- S_net（符号网络）：语言器官，Python 实现
- 谱系系统：.chanlun/genealogy/settled/*.md + .chanlun/sessions/*.md（文件系统 .md）
- Session 持久化：scripts/write_session.sh + precompact hooks（bash）
- 蜂群协调：通过 Claude Code Agent SDK（Python 生态）

## OpenClaw 关键架构（TypeScript/Node）

### 1. subagent 系统（核心问题：树形 vs DAG）

```typescript
// subagent-registry.ts: 全局 Map，parent→child 关系
const subagentRuns = new Map<string, SubagentRunRecord>();

// SubagentRunRecord 类型：
type SubagentRunRecord = {
  runId: string;
  childSessionKey: string;
  requesterSessionKey: string;  // 只有一个 requester（父节点）
  // ... 没有 peer/sibling/team 概念
};

// 查询函数只支持：
// - listRunsForRequester（parent→children）
// - resolveRequesterForChildSession（child→parent）
// 没有 sibling 间通信，没有 team/swarm 抽象
```

子代深度限制：DEFAULT_SUBAGENT_MAX_SPAWN_DEPTH
subagent-spawn.ts 中的 note 明确禁止轮询：
"do NOT call sessions_list, sessions_history, exec sleep, or any polling tool. Wait for completion events to arrive as user messages"

### 2. ACP（Agent Control Protocol）机制

- AcpSessionManager：管理 ACP 会话生命周期（初始化/运行/关闭）
- ACP 通过 WebSocket 连接外部 agent runtime
- SpawnAcpParams：可以指定 agentId、cwd、mode
- ACP 是通往外部进程（包括 Python）的桥接层

### 3. Memory Plugin 系统

```typescript
// memory-search.ts: 向量存储，SQLite 后端
type ResolvedMemorySearchConfig = {
  enabled: boolean;
  sources: Array<"memory" | "sessions">;  // 来源类型固定
  store: { driver: "sqlite"; path: string; };
  sync: { onSessionStart: boolean; onSearch: boolean; };
};
```
内存来源仅支持 "memory" 和 "sessions" 两种类型，不支持任意文件系统路径作为 memory 来源（需要 extraPaths 配置）。

### 4. Daemon 持久化（launchd/systemd）

- OpenClaw gateway 通过 launchd（macOS）/systemd（Linux）保持后台运行
- 状态通过 JSON 文件 + SQLite 持久化
- subagent-registry-state.ts：
  - persistSubagentRunsToDisk：写入磁盘
  - restoreSubagentRunsFromDisk：进程重启恢复
  - getSubagentRunsSnapshotForRead：跨进程读取（合并磁盘+内存）

### 5. Skills 系统

```typescript
type OpenClawSkillMetadata = {
  always?: boolean;
  skillKey?: string;
  requires?: { bins?: string[]; env?: string[]; };
};
// Skills 是 Markdown + 可选 tool 定义的集合
// 不是通用 plugin 接口，不能直接映射为谱系后端
```

## 我们的 RTAS 需求

- **DAG 通信**：任意 teammate 之间可以发消息（SendMessage 工具）
- **谱系持久化**：.chanlun/genealogy/ 文件系统 .md 文件，跨 session 存活
- **Python 后端**：缠论引擎/S_net 必须是 Python
- **蜂群拓扑**：ceremony → spawn workstations → parallel execution → shutdown
- **session 压缩**：precompact hooks 在上下文满时保存状态

## 具体审查问题

1. **语言栈维护成本**：fork OpenClaw 意味着同时维护 TypeScript（OpenClaw）+ Python（后端）。TypeScript 层除了 gateway/channel 外能提供什么 Python 没有的价值？

2. **树形→DAG 改造成本**：
   - SubagentRunRecord 只有 requesterSessionKey（单父）
   - 要支持任意 teammate 通信，需要在 registry 层加 peer 关系
   - 估计需要修改哪些文件？修改量多大？

3. **谱系作为 memory plugin**：
   - memory-search 的 sources 是 ["memory", "sessions"]
   - 要把 .chanlun/genealogy/*.md 作为 memory 来源，需要通过 extraPaths 还是新增 source 类型？
   - SQLite 向量化后，.md 文件的原始可读性是否保留？

4. **ACP 作为 Python 桥**：
   - ACP → WebSocket → Python daemon 的延迟代价？
   - 每次 Python 函数调用都要走 ACP/WebSocket 是否合理？

5. **持久化对比**：
   - OpenClaw：JSON + SQLite，进程崩溃可恢复
   - 我们：.md 文件（人类可读）+ bash 脚本
   - 哪种更适合 RTAS 蜂群的 "谱系" 需求（人类可读性 vs 程序查询性）？

6. **daemon 统一可行性**：
   - OpenClaw gateway（Node） + 逢亮 daemon（Python）统一成一个守护进程？
   - 进程模型：父进程管理两个子进程，还是其中一个调用另一个？

## 代码层否定清单（按你要求的格式）

- **问题**：`SubagentRunRecord` 单父字段（`requesterSessionKey`）与 RTAS 的 DAG teammate 通信定义冲突，属于模型层不一致，不是小修。
  - **位置**：`subagent-registry.ts: SubagentRunRecord`
  - **严重性**：**致命**
  - **修复建议**：改为多边关系模型（run/session 节点 + edge 表），至少支持 `parent_of` / `peer_of` / `depends_on`；同时引入 cycle check 与 ACL。

- **问题**：查询 API 仅 parent→children / child→parent，缺失 peer/team 维度，后续 SendMessage 只能“绕父路由”，语义错误且放大延迟。
  - **位置**：`subagent-registry.ts: listRunsForRequester / resolveRequesterForChildSession`
  - **严重性**：**致命**
  - **修复建议**：新增 team scope 查询与直接路由索引（sessionKey→channel），并定义 team-level permission。

- **问题**：持久化恢复（内存+磁盘快照合并）在 DAG 扩展后会出现一致性风险（孤儿边、重复边、旧版本 schema 读取）。
  - **位置**：`subagent-registry-state.ts: persist*/restore*/getSubagentRunsSnapshotForRead`
  - **严重性**：**重要**
  - **修复建议**：引入 schema version + migration；写入原子化（tmp+rename）；恢复时做图完整性校验。

- **问题**：`subagent-spawn.ts` 明确禁止轮询，当前模型偏“事件回传子任务完成”；RTAS 的 ceremony/并行编排需要 barrier/状态聚合，不补原语会卡在控制层。
  - **位置**：`subagent-spawn.ts` 注释约束 + 调度路径
  - **严重性**：**重要**
  - **修复建议**：补 `waitFor(team, condition)` 事件原语，不靠 polling，但要有聚合状态流。

- **问题**：memory source 仅 `"memory" | "sessions"`，谱系 `.chanlun/genealogy/*.md` 不是一等来源，靠 extraPaths 会导致语义混乱（来源不可区分、同步策略粗糙）。
  - **位置**：`memory-search.ts: ResolvedMemorySearchConfig.sources`
  - **严重性**：**重要**
  - **修复建议**：新增 source type（如 `genealogy`）+ 专属 ingest/sync 策略；保留文件路径、hash、版本戳。

- **问题**：ACP/WebSocket 若按“每个 Python 函数调用一次”会形成高频序列化瓶颈，RTAS 细粒度计算会被 IPC 吞掉。
  - **位置**：`AcpSessionManager` + ACP runtime bridge
  - **严重性**：**重要**
  - **修复建议**：改粗粒度 RPC（批处理/流式）；Python 侧驻留 worker，避免微调用穿透。

- **问题**：Skills 元数据是能力声明，不是通用插件生命周期接口，不能直接承载“谱系后端”。
  - **位置**：skills metadata/type 定义
  - **严重性**：**建议**
  - **修复建议**：把谱系系统放独立 service/plugin 层，skills 仅做调用入口。

## 六个问题的技术评估

### 1) 语言栈维护成本（TS + Python）
- **可行性**：**2/5（若 fork 做核心）**；**4/5（若 OpenClaw 仅做网关）**
- **主要障碍**：
  - 双栈调试/发布/观测链路倍增
  - 业务核心（缠论、S_net、拓扑）本来就在 Python，TS 层改动会长期追上游
  - 架构主导权分裂
- **推荐方案**：
  - **不要 fork OpenClaw 做核心编排**
  - 采用 **Python-first**：RTAS/谱系/计算在 Python，OpenClaw 仅保留会话壳与工具入口

### 2) 树形→DAG 改造成本
- **可行性**：**2/5**
- **主要障碍**：
  - 数据模型重写（单父→多关系）
  - 路由层重写（peer/team messaging）
  - 持久化 schema 迁移与恢复逻辑重写
  - 安全模型（谁能给谁发消息）缺失
- **需要改的文件（最小集合）**：
  - `subagent-registry.ts`（类型+索引+查询）
  - `subagent-registry-state.ts`（序列化/恢复/migration）
  - `subagent-spawn.ts`（拓扑生成、深度与环检测）
  - 消息分发/工具层（SendMessage 寻址与权限）
- **推荐方案**：
  - 不在 OpenClaw 内核硬改 DAG；在 Python RTAS 层维护 DAG，OpenClaw 只承载 session/tool 交互

### 3) 谱系作为 memory plugin
- **可行性**：**3/5**
- **主要障碍**：
  - `sources` 枚举封闭，不是可插拔 source
  - `.md` 高频更新与向量索引同步一致性
- **extraPaths vs 新 source**：
  - **PoC**：可先用 `extraPaths`
  - **生产**：应新增 `genealogy` source（可追踪来源、可定制同步）
- **原始可读性**：
  - 只要 `.md` 继续做 canonical source，可读性保留
  - SQLite 向量库存“投影索引”，不要反客为主

### 4) ACP 作为 Python 桥
- **可行性**：**4/5（粗粒度）** / **2/5（细粒度每函数）**
- **主要障碍**：
  - WebSocket + JSON 序列化反复开销
  - 失败重连、超时、背压处理复杂
- **推荐方案**：
  - 工具接口改为任务级（一次调用完成一个子拓扑计算）
  - 批量输入/流式输出，避免 Python 内循环被 RPC 化

### 5) 持久化对比（JSON+SQLite vs .md+bash）
- **可行性**：**混合方案 5/5**
- **主要障碍**：
  - `.md+bash` 查询弱、并发写风险高
  - 纯 SQLite 人类审计差
- **推荐方案**：
  - **双轨**：`.md` 作为谱系真相源（可读/审计），SQLite 作为检索索引（可查询）
  - 引入 append-only 事件日志，避免状态覆盖写

### 6) daemon 统一可行性
- **可行性**：**2/5（硬合一）** / **4/5（监督式双进程）**
- **主要障碍**：
  - Node/Python 生命周期与故障模型不同
  - 单进程互调导致重启链路脆弱
- **推荐方案**：
  - 用 systemd/launchd 或独立 supervisor 管理两个服务
  - 明确 IPC 契约（Unix socket/WS），不要相互内嵌调用
