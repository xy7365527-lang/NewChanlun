# 零拷贝 RustGraphAdapter 设计审查

## 任务背景

RustGraphAdapter.__init__ 每次从 Rust 复制所有顶点/边/邻接索引到 Python 对象。
5000V/30000E 时每次 add_edge 分配 17-31MB Python 对象。20步 OOM。

目标：设计零拷贝方案——Python 侧不持有任何 Graph 数据的 Python 副本。
所有查询直接代理到 Rust Graph（通过 PyO3 方法调用）。

## 当前 RustGraphAdapter.__init__（engine.py:527-550）

```python
class RustGraphAdapter:
    __slots__ = (
        "_rg",
        "_vertices", "_edges", "_active_ids", "_adj_out", "_adj_in", "_edge_keys",
        "_cached_active_edges", "_cached_all_active_edges",
    )

    def __init__(self, rg: "RustGraph") -> None:
        self._rg = rg
        # Materialise internal attributes from the Rust Graph so that
        # downstream code accessing graph._active_ids etc. works unchanged.
        rust_verts = rg.vertices   # dict[str, RustVertex]  ← 全量复制
        rust_edges = rg.edges      # list[RustEdge]         ← 全量复制

        self._vertices: dict[str, Vertex] = {
            vid: _rust_vertex_to_py(rv) for vid, rv in rust_verts.items()
        }  # 5000V → ~10MB
        self._edges: list[Edge] = [_rust_edge_to_py(re) for re in rust_edges]  # 30000E → ~15MB
        self._active_ids: frozenset[str] = frozenset(rg.active_vertex_ids())
        # Build adjacency indexes from Python edges
        adj_out: dict[str, list[Edge]] = {}
        adj_in: dict[str, list[Edge]] = {}
        for e in self._edges:
            adj_out.setdefault(e.source, []).append(e)
            adj_in.setdefault(e.target, []).append(e)
        self._adj_out = adj_out   # ← 邻接索引再次复制
        self._adj_in = adj_in
        self._edge_keys: frozenset[tuple[str, str, EdgeType]] = frozenset(
            (e.source, e.target, e.edge_type) for e in self._edges
        )
```

### 热循环问题

```python
# daemon.py:530-537
_aout = self.k_active._adj_out   # ← 取引用，热循环里复用
_ain = self.k_active._adj_in
_act = self.k_active._active_ids
def _deg(v: str) -> int:
    out = sum(1 for e in _aout.get(v, ()) if e.target in _act)
    inc = sum(1 for e in _ain.get(v, ()) if e.source in _act)
    return out + inc
start = max(active, key=lambda v: (_deg(v), v))
```

```python
# traversal.py:190-217
g_adj_out = self.k_active._adj_out   # ← 取引用，后面 terrain 计算热循环复用
g_adj_in = self.k_active._adj_in
for x in s:
    for e in g_adj_out.get(x, ()):  # ← 每次 get 是 O(1) dict lookup
        ...
```

这两处的关键点：**不是每次单独调用 `.get()`，而是先取 `_adj_out` 对象引用，再多次 `.get()`**。

零拷贝方案如果让 `_adj_out` 成为一个代理对象，则这两处引用会持有代理对象，`.get()` 调用会走代理的 `__getitem__`。
如果代理的 `__getitem__` 每次都做 FFI 调用（`rg.out_edges(vid)`），则热循环中每次 `.get()` 代价是一次 FFI + Python list 分配。

## 设计问题（供 Codex 审查）

1. **`_adj_out`/`_adj_in` 的零拷贝代理**：用 `AdjProxy` 对象（`__getitem__` → `rg.out_edges(vid)` / `rg.in_edges(vid)`），还是一次性懒加载某个顶点的出/入边缓存？

2. **`_active_ids` 的成员测试**：频率最高的访问是 `vid in active`。Rust 侧已有 `active_ids` 是 `HashSet<String>`，每次 FFI 调用 `rg.contains_active(vid)` ≈100ns。比 Python `frozenset.__contains__` 慢，但不分配内存。权衡点在哪？

3. **热循环中取引用的模式**：`_aout = self.k_active._adj_out` 后多次 `.get()`——如果 `_adj_out` 是 `AdjProxy`，这个引用是代理对象，每次 `.get()` 一次 FFI。可接受还是需要批量化？

4. **`_edges` 全量迭代**（graph_csr.py:80 `for e in graph._edges`）：CSR builder 需要所有边。零拷贝时只能做一次全量 `rg.edges`（克隆），但这是构建 CSR 的初始化操作，不在热路径。可以保留这次克隆吗？

5. **`__repr__` 和 `__len__`**（engine.py:699-706）使用 `len(self._vertices)`/`len(self._edges)` → 替换为 `count_*()` 方法。

6. **缓存策略**：`_active_ids` 是否应该在 adapter 上缓存一份 frozenset（懒加载，用于批量 `in` 测试），在 `_rg` 变化（add_edge/add_vertex/set_vertex_status）时失效？还是完全不缓存？

### 方案 A：纯代理（完全不缓存）
- `_adj_out` → `AdjProxy(_rg, 'out')`，`__getitem__` → `rg.out_edges(vid)` 返回 `list[Edge]`
- `_active_ids` → property，`frozenset(rg.active_vertex_ids())`（每次访问都调用 FFI）

### 方案 B：选择性缓存（per-adapter，`_rg` 变化时不迁移）
- `_active_ids` → 懒加载 frozenset，存在 adapter 上（每次 `_wrap(new_rg)` 时重新计算）
- `_adj_out`/`_adj_in` → `AdjProxy`（热循环可接受，因为 `.get()` 只在特定 vid 时调）
- `_edge_keys` → 完全删除，改用 `has_edge_key()`

**问题**：`add_edge` 每次都分配 `frozenset(rg.active_vertex_ids())`（edge 操作不改 active_ids，但 `_wrap` 仍触发）。

### 方案 C：跨 wrap 传播缓存
- `add_edge()` 后 active_ids 不变 → 传播旧的 `_active_ids` frozenset
- `set_vertex_status()` 后 active_ids 变化 → 重新计算

**问题**：逻辑复杂，需要显式追踪哪些操作改变 active_ids。

## Response

结论先给：**A 不可用，C 风险高，B 最接近可落地，但当前描述仍不通过**。  
你现在的三案都漏了一个核心点：`_adj_out/_adj_in` 在 `daemon.py` 的使用模式会把“代理 + 每次 FFI”放大成灾难级开销。

### 对 4 个问题的直接回答

1. **哪个方案最正确？**  
   **B 作为基础 + 必须补两件事**：  
   - `_active_ids` 做懒缓存（或版本化缓存）  
   - `_adj_out/_adj_in` 不能是“纯 FFI get”，必须有**批量或局部缓存策略**（至少 step 级）  
   否则 daemon 热循环会爆 CPU/分配。

2. **AdjProxy 的 `__getitem__` 在热循环是否可接受？**  
   **在 traversal 小规模（20–100 顶点）勉强可接受；在 daemon 的 `max(active, key=_deg)` 不可接受。**  
   daemon 场景是对 active 全集做 `_deg`，若 active=5000，会触发约 10000 次 `.get()`，每次 FFI + list/Edge 构造，明显不可接受。

3. **`_edges` 全量复制在 CSR 冷路径是否保留？**  
   **可以保留，但只能局部快照，不要挂在 adapter 常驻字段。**  
   冷路径一次性 clone 合理；常驻 `_edges` 违背你的“零拷贝常驻内存”目标。

4. **遗漏的边界条件？**  
   有，且不少（见下方问题列表）。

## 严格问题清单

- **问题**：`AdjProxy.get()` 设计在 daemon 热循环形成 FFI 风暴（不是 O(1) dict lookup 了）
