### schedule_adapter（transition.rs，幽灵买入修复）

```rust
fn schedule_adapter(x: &AssemblyState, intent: StrictAction, target_pos: u64) -> OrderOut {
    // 请求仓位增量 Δ = target_pos − positions（i64 域，可正可负）。
    let requested_delta = target_pos as i64 - x.positions as i64;
    // 现金约束：建仓（Δ>0）受可用 free 上界——affordable = min(Δ, free)，free<0 时下界 0。
    let filled_delta = if requested_delta > 0 {
        requested_delta.min(x.tw_state.free.max(0))
    } else {
        requested_delta
    };
    // 实际成交后仓位 = positions + filled_delta
    let filled_pos = (x.positions as i64 + filled_delta).max(0) as u64;
    let (ledger_event, tw_event) = if filled_delta > 0 {
        (LedgerEvent::Allocate(filled_delta), TwEvent::ShortDiff(-filled_delta))
    } else if filled_delta < 0 {
        (LedgerEvent::Realize(-filled_delta), TwEvent::ShortDiff(-filled_delta))
    } else {
        (LedgerEvent::Noop, TwEvent::ShortDiff(0))
    };
    OrderOut {
        action: intent,
        target_pos: filled_pos,
        ledger_event,
        tw_event,
    }
}
```

关键点：
- Δ = target_pos - x.positions（真实仓位增量）
- Δ>0 时 filled_delta = min(Δ, free.max(0))（现金约束）
- filled_pos 写回实际成交仓位（非请求仓位）
- target_pos 在 OrderOut 是 filled_pos（实际值）

risk_adapter 返回值：

```rust
fn stage_progression(policy: &RiskPolicy, s: &TwState, risk_mode: RiskMode) -> Option<TwEvent> {
    match s.stage {
        TStage::CostReduction => {
            if s.notional_in > 0 && s.holding >= s.notional_in {
                let recover_target = (s.notional_in - s.withdrawn).max(0);
                let w = recover_target.min(s.free);  // ← 受 free 上界约束

                    Some(TwEvent::RecoverCapital(w))

            } else {
                None
            }
        }
        ...
    }
}
```

- w = min(recover_target, s.free)
- free 退后 = free - w ≥ 0（因 w ≤ free）

```rust
pub fn eta_star(&self, s: &TwState) -> i64 {
    let kappa_q = (self.kappa as i128) * (s.notional() as i128);
    let eta = (s.l_wc() as i128) + kappa_q;
    eta.clamp(i64::MIN as i128, i64::MAX as i128) as i64
}

pub fn buy_core_legal(&self, a_n: i64, l_wc_next: i64, delta_q: i64, eta_n: i64, g_n: i64, q_n: i64) -> bool {
    let k = self.kappa as i128;
    let lhs = (a_n as i128) + (l_wc_next as i128) + k * (delta_q as i128);
    let rhs = (eta_n as i128) + (g_n as i128) - k * (q_n as i128);
    lhs <= rhs
}
```

## 仍需 Codex 攻击的疑问点

1. **positions 写回一致性**：schedule_adapter 写回 target_pos=filled_pos；transition_adapter 写回 positions=o.target_pos。
   但 o 是 OrderOut 结构体值，中间经 policy_output→schedule_adapter 链产生。
   问：positions 字段在 x 和 o 之间有无 off-by-one？首 bar filled_delta=1，filled_pos=1，
   positions 更新为 1。下 bar risk_adapter 读 x.positions=1，target_pos=max(1)=1，Δ=0→Noop。
   这是否真的闭合（无歧义）？

2. **stage_progression 的 free 下界**：w = recover_target.min(s.free)。
   当 s.free 为负时（理论上现修复后不会，但假设）：s.free 为负 → min(recover_target, negative) = negative → w 为负 → if w>0 分支不进 → None。
   即使 free 为负，代码路径也安全（None）。是否有其他路径能产生 free 为负？
   schedule_adapter 中：filled_delta=min(Δ, free.max(0))。free.max(0)=0 if free<0，
   所以 filled_delta=0，不进一步减 free。这条保证是否完整？

3. **EarningShares 阶段的持续行为**：phase=PhaseIII → intent=Add → target_pos=positions.max(1)=1（已有仓位 1）→ Δ=0 → Noop。
   EarningShares 后系统 Noop 循环——这是"增股数"的正确行为吗？还是 PhaseIII 的 intent 应产生更多仓位增量？
   codex #9 要求"EarningShares 后 intent 为 Add/BuyCore，不是继续 ShortDiff"。
   现在 intent=Add 确实了，但 risk_adapter 在 positions>=1 时返回 max(1)=1，Δ=0，实际上没有增仓。
   "增股数"在当前代码中是否真的执行了"增"动作，还是意图正确但执行仍是 Noop？

4. **debug_assert 仍非 assert**：两个 OQ-9 gate 检查仍是 debug_assert。release 下这些检查静默失活。
   codex #4 原判"重要"（非致命）。修复后是否仍是 debug_assert？如果是，这条"重要"未修复。

5. **kappa 字段私有化后测试一致性**：ledger.rs 测试中有 `RiskPolicy { kappa: -1 }` 和 `RiskPolicy { kappa: 3 }`
   直接构造（不经 try_new）。如果 kappa 字段已私有化，这些测试行是否会编译失败？
   若编译通过，说明私有化未完全生效（同 crate 内直接构造仍可）。

6. **tw_step RecoverCapital 分支**：`TwEvent::RecoverCapital(w)` → `free -= w`。

## Response

**结论：fail。** 修复闭合了“正常 policy_output → schedule_adapter → transition_adapter”路径上的幽灵买入，但仍有可证伪裂隙，尤其是 PhaseIII 空转和 `transition_adapter` 信任外部 `OrderOut`。

- **问题**：`PhaseIII/EarningShares` 仍不执行“增股数”。`Buy | Add => x.positions.max(1)` 只保证从 0 建到 1；一旦 `positions >= 1`，`Add` 的目标仓位等于现仓位，Δ=0，最终 `ShortDiff(0)`。所以 phase 已同步，但操盘执行仍是 Noop。
- **位置**：`transition.rs:risk_adapter`（无法读取仓库，未能核验行号）
- **严重性**：致命
- **修复建议**：将 `Add` 与 `Buy` 分离。`Add` 应产生正增量，例如 `positions + add_lot` 或 policy 计算出的目标仓位，并继续由 `schedule_adapter` 做 free cash-tight 截断。

- **问题**：`transition_adapter` 是 `pub fn` 且信任传入的 `OrderOut`。外部可构造不一致订单：`target_pos` 与 `tw_event` 不匹配，或重复注入 `ShortDiff(-1)`，从而绕过 `schedule_adapter` 重现幽灵买入/负 free。
- **位置**：`transition.rs:transition_adapter` / `OrderOut`
- **严重性**：致命
- **修复建议**：不要让外部直接传裸 `OrderOut` 进入状态转移；要么把 `OrderOut` 字段私有化并只允许 `schedule_adapter` 构造，要么在 `transition_adapter` 内重新校验 `tw_event == f(target_pos - x.positions)` 且 cash-tight。

- **问题**：`RecoverCapital` 的合法性没有在边界层保证。`stage_progression` 约束了 `w <= free`，但 `is_legal_from` 对 `RecoverCapital` 恒 true，`tw_step` 又执行 `free -= w`。任何外部注入 `RecoverCapital(w > free)` 都能制造负 free；若允许负 `w`，还可能反向增 free/减 withdrawn。
- **位置**：`ledger.rs` 或 `tw_step` / `is_legal_from` 的 `TwEvent::RecoverCapital`
- **严重性**：致命
- **修复建议**：`is_legal_from` 必须检查 `w > 0 && w <= free && withdrawn + w <= notional_in`；`tw_step` 最好返回 `Result` 或内部防御非法事件，不要只依赖上游生成器。

- **问题**：`RiskPolicy { kappa: -1 }` 在同文件 `#[cfg(test)] mod tests` 中仍可能编译，因为 Rust 私有字段对子模块可见。字段私有化只阻止模块外构造，不证明 crate 内 invariant 无法被破坏。
- **位置**：`ledger.rs:RiskPolicy` 及同文件测试
- **严重性**：重要
- **修复建议**：测试负值应改为 `assert!(RiskPolicy::try_new(-1).is_none())`。若要强 invariant，把构造集中到更窄私有模块，或用不可负的新类型封装 `kappa`。

- **问题**：OQ-9 gate 若仍是 `debug_assert!`，release 下完全失效。这不是测试问题，是运行语义问题。
- **位置**：OQ-9 gate 所在检查点（上下文未给文件行号）
- **严重性**：重要
- **修复建议**：对必须维持的策略/账本安全条件使用 `assert!`、显式错误返回，或把非法状态编码为不可构造类型。

- **问题**：`target_pos as i64 - x.positions as i64` 对 `u64 > i64::MAX` 不安全，Rust `as` 会截断/重解释，可能把大仓位转成负数，导致 Δ 错判。
