# 审计对象：parser 线段增量 frontier 修复设计（候选 A vs 候选 C，排除候选 B）

## 背景（阶段0 测量已裁决，非 NO-SHIP）

真实 BTC/CL 长历史逐 bar 增量 parser+塔 vs 单次全量重算（`classify_with_tower(parse_layer(bars))`）在
level≥2 发散：BTC 300K L2 bsp 19 vs 17、L3 bsp 3 vs 4；CL 各档 L2/L3/L4 发散。三诊断隔离：
- `detect_centers_windowed_resume`（塔层 resume）已 bit-exact（0..1500 无发散）。
- `IncrSegments::append`（parser 线段增量）在 bar 49291 发散：`seg[404]`（confirmed_len=406，
  即不是最后一段）end 48818/7655 vs 全量 48798/7648。0..50K 共 709 次持续发散。
- 生产全路径发散与 parser seg 发散逐字段同值 ⟹ 中枢层发散是线段层发散的忠实下游传播，塔层无独立 bug。

**根因**：`IncrSegments::append` 每次只丢弃/重算"最后一个 confirmed 段"（1 段回退），假设"倒数第二段
及之前不可变"。但 `second_seq_has_fractal`（第二特征序列分型扫描）的 `scan_window` 默认 = 0（无限全
扫，config.rs:65，bit-exact 优先于性能）。无限扫描意味着新 bar 引入的笔可以让**任意早**的
`SecondKindPending`（第二种情况待确认段）复活（第二特征序列出现分型），从而改写比"倒数第二段"更早
的段端。1 段固定回退深度 < 真实 mutable-frontier 深度（该深度理论上无界）。

## PDF 权威依据（`docs/formal-chain/区间套.pdf` §六-§十一，编排者 2026-07-01 最后下载=链最新端点）

canonical 定义（§六）：`T_t^inc = F(h_{0:t}) ∀t`（bit-exact，増量塔必须等于对完整历史 `h_{0:t}` 的单次
全量重算）。

confirmed prefix / mutable frontier 分解（§六.2）：`F_t = P_t ⊕ R_t`，`P_t`=confirmed prefix（未来
不会被新 bar 改写）、`R_t`=mutable frontier（未来可能被新 bar 改写）。严格要求：**`P_t` 可复用，
`R_t` 必须重算**——不能把未确认的最后窗口放进 `P_t`。

§七 裁决：这是**实现 bug，非定义冲突**——canonical 定义是"增量必须等于全量重算"，全量重算会重新
评估未确认最后窗口，增量也必须重新评估同一 mutable frontier，没有定义冲突。只有把 canonical 换成
"OnlineTower = 一旦 emit 就不可回溯"才会变成定义冲突，但那会放弃 `T_t^inc = F_t` 目标——当前测试名
`decisive_endpoint_tower_parity_longhistory` 已经选择了 `F_t` = 全量重算塔，所以"未确认 frontier
视为不可变就是 bug"。

§八 正确增量算法：定义 `Seal(w,t)=1` 表示窗口 `w` 在时刻 `t` 后不会被未来 bar 改写。定义最后已封存
边界 `b_t = max{end(w): Seal(w,t)=1}`。增量更新：
```
T_{t+1}^inc = Prefix(T_t^inc, b_t) ⊕ Detect(h_{b_t:t+1})
```
`Prefix(T_t^inc, b_t)` 只保留**完全结束于 `b_t` 之前的 sealed 结构**；`b_t` 之后开始的所有结构
（包含最后未确认窗口）都必须重算；**如果无法证明某窗口 sealed，就必须把它放进 frontier（重算）**。

更保守的写法（§八，seal 难定义时）：`b_t = last stable endpoint before current active candidate`
（即 rollback 到最早可能受未来 bar 影响的候选起点）。性能差一些，但**保证 bit-exact**。

§九 增量等价定理（归纳证明）：若 (1) F 确定性 (2) 存在边界 `b_t` 使 `Prefix(F(h_{0:t}),b_t) =
Prefix(F(h_{0:t+1}),b_t)`（prefix stability，即 `b_t` 前缀对未来扩展稳定）(3) 增量算法用
`T_{t+1}^inc = Prefix(T_t^inc,b_t) ⊕ Detect(h_{b_t:t+1})` (4) 初始 `T_0^inc=F(h_0)`，则
`T_t^inc = F(h_{0:t}) ∀t`。证明：归纳，假设 `T_t^inc=F(h_{0:t})`，由 prefix stability 前缀相同，
后缀由同一确定性检测函数对同一历史片段 `h_{b_t:t+1}` 计算，故与全量重算后缀一致。

当前实现违反定理的原因：**它选的 `b_t` 太晚**，把未确认最后窗口放进了 prefix ⟹ prefix stability
不成立 ⟹ `Prefix(F(h_{0:t}),b_t) ≠ Prefix(F(h_{0:t+1}),b_t)` ⟹ 归纳证明断裂。

§十 最终裁决：在"增量必须等于全量重算"的 bit-exact 目标下，这是实现 bug，应该修。正确修法：
**增量 resume 只能从 sealed prefix 之后开始；未确认 frontier 必须重算**。如果不修，高级别计数与
候选都会被污染：`Γ_{ℓ≥2}^inc ≠ Γ_{ℓ≥2}^full` ⟹ `μ̂_{ℓ≥2}^inc` 不是目标估计量 ⟹ 所有"高级别无
alpha"的结论都必须撤回或标注为 frontier-bug 污染。

§十一 两问题共同数学结构：都是"把局部边界条件误当成全局结构语义"。问题②："最后窗口已经登记"是
局部缓存状态，不是全局确认状态；正确全局语义是"只有 sealed prefix 可复用，mutable frontier 必须
重算"。

## 代码：`rust/src/theta_v0/parser/segment.rs`（`IncrSegments::append`，关键片段）

```rust
/// 增量 segment 状态（bit-exact 对齐 `divide_segments_with_tail`）。
pub struct IncrSegments {
    segments_rc: Rc<Vec<Segment>>,
    end_indices: Vec<usize>,          // 段端在 strokes 数组中的下标
    pending_start: Option<usize>,     // 未完成段起点
    strokes_len: usize,
    confirmed_len: usize,             // 本次 append 保留的 confirmed 前缀长度（l0_tower 复用证书）
    last_stroke: Option<Stroke>,
}

pub fn append(self, strokes: &[Stroke], config: &ParseConfig) -> IncrSegments {
    let n = strokes.len();
    let last_stroke = strokes.last().copied();

    // 相同输入早退：strokes 长度同 ∧ 末笔逐字段等 ⟹ 结果与 self 逐字段等。
    if n == self.strokes_len && last_stroke == self.last_stroke {
        return self;
    }

    let IncrSegments { mut segments_rc, mut end_indices, .. } = self;

    // 只回退"最后一个 confirmed 段"（confirmed_bound = 末段 end_array_idx）。
    let confirmed_bound = match end_indices.last() {
        Some(&last_end_idx) => last_end_idx,
        None => 0,
    };
    let keep = end_indices.partition_point(|&end_idx| end_idx < confirmed_bound);

    let new_segments = Rc::make_mut(&mut segments_rc);
    new_segments.truncate(keep);
    end_indices.truncate(keep);

    // 从"倒数第二段的 seg_start"（= 末段原 seg_start）续扫。
    let resume_seg_start = match end_indices.last() {
        Some(&last_end_idx) => last_end_idx + 1,
        None => /* 全扫 find_overlap_start(...) */ 0,
    };
    // ... 从 resume_seg_start 用 FeatureSeqState 续扫到 n，产出新 confirmed 段 + pending_start
}
```

实测反例：`seg[404]`（`confirmed_len=406`，**不是**末段 `segments.len()-1=407`）在全量重算下 end 变为
48798/7648（原增量给的是 48818/7655）——即增量把一个"本级更早的确认段"错误封进了 confirmed 前缀，
而 1 段回退永不重访它。

## 代码：`rust/src/theta_v0/parser/feature_seq.rs`（无限扫描机制，说明为何"任意早"段可复活）

```rust
/// scan_window：0 = 无限全扫（second_seq_scan_window config，default 0，bit-exact 优先）；
/// >0 = 有界窗口。
fn second_seq_has_fractal(
    strokes: &[Stroke],
    seg_dir: Direction,
    from_stroke_idx: usize,
    scan_window: u32,
) -> bool {
    let end_idx = if scan_window == 0 {
        strokes.len()               // 无限：一路扫到 strokes 末尾
    } else {
        (from_stroke_idx + 1 + scan_window as usize).min(strokes.len())
    };
    // ... 从 from_stroke_idx+1 到 end_idx 扫描第二特征序列分型，早停
}
```

`config.rs:65` `second_seq_scan_window` 默认 = 0。`SegmentTermination::SecondKindPending`
（`segment.rs`）表示"有缺口但第二特征序列尚未出现分型"——是否 Pending 依赖**未来笔**（新 bar 到来
后第二特征序列可能新增元素触发分型）。由于扫描无界，`SecondKindPending` 段可能在任意远的未来 bar
被确认/复活，没有理论上限的"安全回退深度"。

## codex 审计的具体决策问题

**候选 A（保守回退，PDF §八"更保守写法"，本报告推荐首审）**：
不再固定回退 1 段，而是回退到"当前没有任何 pending SecondKind 第二序列可回指其内"的段端。实现思路：
`IncrSegments` 增加字段 `earliest_pending_secondkind_stroke_idx: Option<usize>`（记录本轮扫描中曾经
进入 `SecondKindPending` 状态、其"分型极值笔偏移"或"段起点"的最早下标）；`confirmed_bound` 改为
`min(末段端, 该 pending 起点)`。scan_window=0（无限）下语义退化为"回退到无 pending 覆盖的最深稳定
点"。

**候选 B（有界扫描窗，仅列作对照，报告已建议不推荐）**：把 `second_seq_scan_window` 从 0 改为有界
`W`，回退深度变为 W 对应的最大段跨度，固定可算。风险：改 `W` 会同时改变 **canonical**
`divide_segments_with_tail`（全量重算也用同一 `config.second_seq_scan_window`）的判据——这不是纯
增量修复，而是改变了"什么算分型确认"的定义口径本身，可能越过 no-workaround 边界（`no-workaround.md`：
不允许通过改判据含义来"解决"矛盾）。

**候选 C（bit-exact 兜底）**：`IncrSegments::append` 检出"确认前缀内某段被本轮重划改写"时，
`cascade` 全量重扫该 parser 层（类比塔层已有的 `cascade_reset` 机制）。退化为 O(n)，但保证 bit-exact，
正确性优先、性能证书失效。

**问题**：A 的 pending 锚点若只记录“当前 pending”不 sound；当前状态机根本没有持久化被跳过的 SecondKind 候选  
**位置**：`rust/src/theta_v0/parser/feature_seq.rs:363`, `rust/src/theta_v0/parser/segment.rs:517`  
**严重性**：致命  
**修复建议**：在 `FeatureSeqState::scan_trigger` 遇到 `has_gap && !second_seq_has_fractal(...)` 时，把该候选所属 `seg_start` 记录到本轮 `earliest_unsealed_from`。`IncrSegments` 持久化它；下一次 `confirmed_bound = min(last_end_idx, earliest_unsealed_from.unwrap_or(last_end_idx))`。不要只存 active tail，也不要只存最后一个 pending。
