## 三个 P0 设计草案（逐条审计）

### P0-1：高级别背驰段 → 下沉触发的显式联动

**原文依据**：第29课 line 302「首先看大级别的背驰段，然后再按区间套的方法看小级别来精确定位」——
高级别处于背驰段是下沉的**前置门**，不是"对每个候选无条件下沉"。

**现状**（econ_positive.rs:319-351，见下方代码原文）：`build_multilevel_nest_cert` 对每个候选信号
**无条件**构造 `NestCertificate` 并调 `n_delta()`。`σ_p`（`parent_dir`，selector.rs:150 `z_of_candidate`）
是 MuClass 的**被动分类标注**（三态 Ambient/FollowParent/ShortDiff），不是"高级别背驰→触发下沉"的主动
状态机。`divergence.rs` 的 `segments_diverge`/`trend_divergence`/`consolidation_divergence` 已实装 A/B/C
趋势/盘整背驰判据（真 MACD 力度比较，L1 管线正确）。

**f2 设计草案**：引入 `DescendTrigger`——高级别 carrier 处于背驰段（复用 `divergence.rs` 的
`segments_diverge`/`trend_class` 判据）或第一类买卖点状态时，标记 `trigger_descend=true`；区间套门
（`build_multilevel_nest_cert`）只对被触发的高级别定位窗口下沉。设计声明"不新增判据，只加高级别状态
→门控的一个 bool 前置，不改区间套证书本身（NestCertificate/n_delta 递归逻辑不动）"。

**审计问题**：
(a) 门控触发条件的原文忠实度——第29课 line 302 是否要求"每次下沉都必须先有高级别背驰段"，还是
    背驰段只是缠师举例的典型场景（存在其他触发下沉的合法原文场景，如二三类买卖点直接触发而不
    经背驰段）？如果原文外延比"背驰段触发"更宽，此设计会不会漏判合法下沉场景（假阴性）？
(b) 与现行"每候选无条件构造证书"的关系——加门控后，`NestCertificate` 仍会构造（只是被触发的窗口
    才走），信号集会怎样变化？这个变化是否就是修复目的所要求的（即：现状 95% 退化 depth=1 是否
    正是因为"无条件构造"导致大量非背驰驱动的伪下沉，加门控后能否让 depth=1 主导的样本更纯净地
    对应"真背驰驱动的一级下沉"，还是只是简单地砍掉信号数量而不改变 depth 分布本质）？
(c) depth=1 主导是市场几何事实（已订正，非 frontier bug）的前提下，这个状态机的预期效果是什么？
    诚实评估：如果 depth 分布不会因为加门控而改变（因为深度是市场结构决定，非触发条件决定），
    那么这个 P0 到底解决了什么问题——是"信号质量"问题（滤掉非背驰驱动的假信号）还是"必要性"
    问题本身就不成立（现状设计已经通过 σ_p 分类/后续 μ 学习间接筛选，无需前置状态机）？

### P0-2：持仓节点 = 容器/position instance（非买卖点叶子）

**原文依据**：级别容器.pdf p13「递归声部树中，持仓节点必须是容器 carrier 或容器-入场证书 position
instance；买卖点叶子只能作为开仓证书，不能作为父声部持仓节点」；p15「carrier_id=hostOf(g);
entry_signal_id=id(g); position_node_id=hash(carrier_id,entry_signal_id,side,generation)」。

**现状**：开仓以买卖点信号为单位（`RawSignal`/`SignalDecomp` 结构，见 econ_positive.rs 代码原文），
无独立 `position_node` 概念。`bsp.rs` 的 `BspPoint` 是买卖点端点条目（携带 pivot/center/struct_break_dir），
是判据输出，不是持仓身份。`voice_eat.rs` 的 `ContainmentReport`/`verify_containment` 已探测到
"par 实为依附 host（gap-B 反例）"的 uncovered>0 场景（已有否证机制，但未建 K_i carrier forest）。

**f2 设计草案（简化版）**：`position_node_id = hash(carrier_id=hostOf(g), entry_signal_id=id(g),
side=δ(g), generation)`（级别容器.pdf p15 原文伪码，直接照搬）。先做 §14 简化版
`posId^simp=carrier_id`（不携 entry_signal_id/side/generation 的完整四元组），据称足以解开
depth1/depth2 的 AncOK 剪枝（B9 定理：`active_depth_ge3>0 ⟹ active_depth1>0 ∧ active_depth2>0`
祖先闭合，现状实测矛盾 `active_depth_ge3:0→14166` 但 `active_depth1=0,active_depth2=0`）。
完整 §13 四元组 (c,γ,σ,n) 的多实例/generation 留作 P1（多空双开需要时再加）。

**审计问题**：
(a) 级别容器.pdf 核心裁决的忠实度——原文伪码是 `hash(carrier_id, entry_signal_id, side, generation)`
    四元组，f2 只取 `carrier_id` 单键简化版，是否足以承载"持仓节点=容器实例"的核心区分（buy/sell
    叶子 ≠ 持仓身份）？还是这个简化丢失了关键信息——例如同一 carrier 上先后开仓/平仓/再开仓
    （generation 递增）在只用 carrier_id 单键时会被识别为同一个持仓节点，产生错误的身份合并
    （不同批次的仓位被误认为同一持仓）？
(b) 与既有 TW 三阶段账本（`t_engine.rs` TStage 状态机）/ GAP3 结构的相容性——TW 账本的三阶段
    （CostReduction→CapitalRecovered→EarningShares）是否已经隐含了某种"持仓身份"追踪？如果
    position_node 是全新概念，它与 TW 账本的 free/holding/withdrawn 三量是否需要建立映射，
    还是二者是完全独立的关注点（position_node 管"谁持有"，TW 管"钱在哪个阶段"）？
(c) 简化 hash 方案的碰撞/同一性风险——`hash(carrier_id)` 单键在什么情况下会产生假阳性同一性
    （不同的开仓事件被哈希到同一 position_node，但语义上应该是不同的持仓）？在什么情况下会产生
    假阴性（应该视为同一持仓的两个事件被错误分开）？

### P0-3：多空对冲 overlay——先做诊断度量，不建账本

**原文依据**：多空对冲.pdf p13「三层判定：声部生成层 depth>0 是否 active；净额可见层 ‖ΔN‖_1
是否非零；经济有效层 Π^overlay/IR/回撤/尾部风险是否改善」；p9「N_t^1=N_t^0+H_t，
H_t=−σ_parent·h_t；Π^overlay=H_tΔP−ΔC；若只机械对冲无预测性则风险中性下 E[Π^overlay]≤0」。

**现状**：`σ_p`/ShortDiff 只在**分类/统计层**（selector.rs `z_of_candidate` 的 Vertical 三态、
mu_estimator/perm_test），账本头寸层 TW 三阶段 still-MISSING（econ_positive.rs:65,508 明确声明
"不触碰 TW 三阶段 GAP3/576"）。574号谱系（.chanlun/genealogy/settled/674-ledger-r-vs-tw-...）
已裁定：R=Π-A-W 账本 vs TW=free+holding+withdrawn 账本**machine-checked 不同构**（Lean 已证），
立场C 定案——双层并置，禁止声称双向同构，需诚实标注投影损失。无 overlay 腿（父子对冲头寸的
分账本）实装。

**f2 设计草案**：先实装**诊断型**——不改 R 账本 netting（不建 hedge-mode/portfolio-margin
账户系统），只加 `‖ΔN‖_1`（净头寸差的 L1 范数）度量 + `Π^overlay=H_tΔP−ΔC` 计算，作为
"depth>0 声部是否真的改变净头寸"的可观测量。多空对冲.pdf p13 三层判定的"净额可见层"先落地，
"经济有效层"（是否值得建账户型 overlay）留待诊断结果决定。

**审计问题**：
(a) 多空对冲.pdf「‖ΔN‖_1=0 时 overlay 净额不可见」引理的核对——这个引理是否要求诊断度量
    `‖ΔN‖_1` 的计算不依赖任何新增的持仓账本（即：能否只用现状信号流 + P0-2 的 position_node
    就算出 ΔN，还是必须先有某种 overlay 腿的记账才能算 ΔN）？如果计算 ΔN 本身就需要"父子腿
    分别记账"，那"先诊断不记账"在逻辑上是否自洽（诊断需要的输入恰是账本要提供的输出）？
(b) 诊断先行 vs 直接实装 overlay 账本的排序合理性——鉴于 674 号谱系已裁定 R vs TW 双层并置
    禁止冒充同构，overlay 账本一旦实装是否会引入第三个会计范畴（R/TW/overlay 三层并置)？
    这是否需要先确认 overlay 账本与已裁定的 R/TW 双层如何相容，而不只是"诊断完再说"？
(c) 与净持仓执行层的边界——诊断度量 `‖ΔN‖_1` 和 `Π^overlay` 是只读分析产出，还是会反馈影响
    交易决策（例如触发实际的对冲开仓）？如果是后者，"先诊断不记账"这个界限在哪里划——诊断
    结果一旦触发交易动作，是否事实上已经隐含了记账（否则如何追踪该笔对冲交易的盈亏）？

### nest.rs（`NestCertificate::n_delta` 核心递归，P0-1 声明"不改此逻辑"）

```rust
pub fn n_delta(&self) -> bool {
    Self::n_delta_rec(self.side, &self.terminal, &self.base_interval, &self.rungs)
}
fn n_delta_rec(side: Side, terminal: &BspBits, base: &NestInterval, rungs: &[NestRung]) -> bool {
    match rungs.split_first() {
        None => terminal.confirm_side(side),  // 基例 ℓ=e：Conf^δ_e
        Some((top, rest)) => {
            let child = rest.first().map_or(base, |r| &r.interval);
            top.cand && is_sub(child, &top.interval) && Self::n_delta_rec(side, terminal, base, rest)
        }
    }
}
```
