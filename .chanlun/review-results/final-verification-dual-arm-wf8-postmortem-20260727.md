## 2. 做对的三件事

### 2.1 金标准靠三方交叉指认，不靠单点

`/tmp/vocab_align_dump` 被三处独立文本指向同一物：ADR 0001 补充九尾句、
`oscillation-campaign-wiring-20260727.md:105-106`、`oscillation-criteria-alignment-20260727.md:98-99`，
且三处所载字节数一致（948340 / 354946）。三方对上才动手。

**教训固化**：若只有一处指认（尤其只有 ADR 一处），应停手上报而非直接用——
`/tmp` 下的物件无版本控制、无校验和，单点指认不足以承担「金标准」这个名分。
本轮实测后 md5 已入报告，此后可脱离 mtime 判断新鲜度。

### 2.2 纯态核验的判定粒度到 target 级（但执行次数不够，见 §3.4）

ADR 补充九的流程教训（共享工作区混入他 session 未提交中间态，编出混合 lib，
基线读数假漂移到 −20144870）本轮按纪律执行：先 `git status --short rust/`，
发现脏文件 `rust/src/bin/p107_level_calib.rs`。

关键判断不是「脏就停」，而是**脏在哪个 target**：它是 `[[bin]]`，而本轮全部实测走
`cargo test --lib`，只编 lib target。据此判定不污染并留痕，省掉一次不必要的 worktree。

**教训固化**：纪律的正确形式是「实测前核 **lib 树**干净度」，不是「核工作区干净度」。
后者过严会逼出无谓的 worktree 开销，前者才是因果面。

⚠️ 但这一次核验**只做了一次**，代价见 §3.4——本节标题里的「做对」仅限判定粒度这一点。

### 2.3 推算值明确标注为非产物级

「成功落账 13 次」是 `Σaction_by_level(351) − Σviolations(338)` 减出来的，
witness 里没有这个轴。它恰好是三项零读数的分母，最有解释力——也最容易被顺手写成
实测读数。报告里标注为推算，并单列成缺口 G8（建议独立成轴）。

## 3. 暴露的三个问题

### 3.1 验收票的 acceptance 写法诱导两种坏行为

票面写「见证读数：亏损入账计数 / 两终局分开呈报 / stage_event（若有到 0）」。
当真实窗口里这些事件根本没发生时，这句话有两个坏解法：

- **补跑到出数为止**——换窗、换参数直到某个桶非零，然后把它当"见证"；
- **单测冒充实测**——用 #380/#366 已有的单测覆盖顶替，报告里含糊成"已验证"。

两条都违 090。本轮走的是第三条：照实报零 + 定位根因 + 标注覆盖只到单测层。
但这是执行位自己选的，不是票面写的。

**建议**：实装票的终验 acceptance 应统一写成
「见证 X 的**读数**（非零则列明细；为零则定位根因并标注现有覆盖层级）」。
把"报零也是交付"写进票面，坏解法才没有生存空间。

### 3.2 终验票的基线在它自己开出后被改了三次

#384 的 blocked-by 只列 #380/#381/#366/#383。但票开出后又落了三张票：

| 票 | 对 witness 的改动 |
|---|---|
| #414 | `superseded` 桶**删除**（挂起不再随取代终结），新增 `suspension_continued_count` / `settlement_by_side` / `replenish_foreign_center_count` |
| #441 | 新增 `death_write_off_*` 三轴（campaign 死亡吞挂起核销） |
| #442 | `suspension_by_source` / `suspension_continued_count` / `settlement_by_side` 三桶**键形状加 level 维** |

后果：ADR 0001 补充九那张「wf8 实测对照」表，除 `lifecycle_*` 与四层报告外**大面积过期**
（报告 §5.1 逐项列了时效）。后续读者若拿它当现行基线比对，会把口径演进误读成回归。

**建议**：图票的终验票在开跑前应先做一次「基线时效核对」——列出票开出后落地的所有相关
commit / issue，判定哪些历史读数已跨版本不可比。本轮是在读数对不上时**回溯**做的这件事，
顺序反了，多花了一轮定位。

### 3.3 后台 Bash 不继承前台 cwd，差点误报「release 侧红」

`cargo test --release --lib` 首跑返回 exit 1，日志里是
`error: could not find Cargo.toml in /Users/silencehan/Projects/NewChanlun`——
不是测试失败，是后台任务的工作目录回到了仓库根（前台此前 `cd rust` 未被继承）。

若不看日志正文只看 exit code，报告里就会写成「release 侧红」这种量级的假阳性。

**教训固化**：跑测试类命令一律用绝对路径 / 显式 `cd`，且 **exit≠0 时必须读日志正文
判定是构建错误还是断言失败**，不能凭退出码定性。

### 3.4 纯态核验做了一次，不是两次——66 秒的窗口

写完报告后收尾核对 `git status`，发现多了一个脏文件：
`rust/src/theta_v0/backtest/wverify_run.rs`，mtime **12:34:54**，
而本轮第一次实测的 dump 落盘在 **12:36:00**——**另一 session 的未提交改动在我开跑前
66 秒落进了 lib 树**，本轮全部读数都包含它。

如果不是收尾时又查了一次，报告 §0 会留下一句白纸黑字的错误声明：「lib 本体无未提交改动」。
那正是 ADR 补充九那次 −20144870 事故的同款句式。

事后定性是好的（改动只有 2 行有效代码，在 `#[test]` 函数体内的 `eprintln!` 上，
且三个 `cmp` 全过是行为化证据），但这是**运气，不是流程**。同样是 66 秒，
落进来的要是 `account.rs` 的一行比较符号，这份报告的每个数字都得作废，
而我不会知道。

**教训固化**——纪律要从「实测前核一次」升级为**三段**：

1. **实测前**核 lib 树干净度，记下 `git status` 输出；
2. **实测后**再核一次，**两次输出必须一致**；不一致则查 mtime 与实测时刻的先后，
   逐项定性，并把定性依据写进报告（不能只写"应该没影响"）；
3. 报告里的纯态声明**必须引用实测后那一次**的输出，不能引用开跑前那次——
   开跑前的输出证明不了实测期间没被人动过。

更省事的替代是独立 worktree + 独立 `CARGO_TARGET_DIR`（#366 那轮就是这么做的），
代价是一次 worktree 开销。**在共享工作区多 session 并行的现实下，这个开销该默认付。**
本轮为省它而只做单次核验，事后看是错的取舍。

本轮**没有**在那两个历史提交点复检——那需要 checkout，超出本票「不执行 git 分支操作」的纪律。

所以本轮结论只覆盖一个提交点，**不构成对那条记录的证否**，报告里按 G9 如实登记。
把「我的实测支持 A」和「A 因此成立」分开写，是这类跨线争议里唯一诚实的写法。
