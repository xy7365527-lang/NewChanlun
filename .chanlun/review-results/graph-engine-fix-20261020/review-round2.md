## 本轮发现

**N1 — MED：新的「退回 / 重写」重开判断会让已批复的票被重新处理（就是 #1565 那种重复处理）**
- 位置：`.sandcastle/decision-claimer.mts:610`（`REOPEN_RE`）、`:633–635`
- 原因：重开判断只要首行里出现「退回 / 驳回 / 打回 / 重写 / 不批准 / 不同意」中的任何一个就生效，而且排在批复识别之前。用户、主控和全仓代理用的是同一个账号。我实测了两种情况：
  - 批复本身写成 `用户 2026-10-20 批复：「同意」——按草稿重写 §3 后落地`，结果是 `null`，批复认不出来。
  - 先有一条 `用户 10-20 批复：同意`，后面跟一条簿记评论 `已按用户批复重写正本 baohan.md`，结果也是 `null`：已经批复的票被重新打开。

  只要票还 open（批复了但还没关），live 模式就会重新认领、起草，T 类甚至会再落地一次。第一轮的代码里，前一种写法能正确识别，所以这是本轮新引入的问题。线上 #1565 / #1530 目前判对了，只是措辞碰巧没撞上。
- 建议：
  - 只把开头的退回词当作重开，例如 `/^(?:退回|驳回|打回|不批准|不同意)/`。
  - 或者批复冒号后的内容以退回词开头时才算否决，例如 `批复[：:]\s*「?(?:退回|驳回|不同意)`。
  - 去掉单独的「重写」这个词。
  - 补上面两个反例的测试。

**N2 — LOW：「用户还没批复」会被误判成已批复**
- 位置：`.sandcastle/decision-claimer.mts:620`
- 原因：只排除了「未」「待」，没排除「没 / 尚无 / 要求…再」之类说法。实测 `用户还没批复` 返回「票上已有用户批复」，票会被跳过、卡住，日志里只有一行。这是安全方向的错（不会重复处理），但会让票悬着没人管。
- 建议：把 `没` 和 `需` 加进排除字符集，例如 `[未待没需]`。

**N3 — LOW：删掉了一条已有负责人的专项测试**
- 位置：`scripts/wayfinder_engine.test.mts`，原 577–581 行的「已有负责人：不论 assignee 最近是否活跃，引擎都不放行」
- 原因：这条语义仍被 `:307`、`:377`、#1394 的断言和写前复核测试覆盖，所以不算真的丢了覆盖，但这句专门写给硬约束的说明没了。
- 建议：可以保留不处理，也可以恢复这条测试。

**N4 — LOW：网络层仍然没有测试（就是 LOW-10 没处理的那一项）**
- 原因：`fetchChildren` 填 `openSubIssues`、防环，以及 `releaseTicket` 先复核再写，都只被纯函数测试间接覆盖。比如有人以后把 `releaseTicket` 里那次复核删掉，现有测试不会变红。
- 建议：给 `gh` 加一层注入点或 mock，补一条「复核读到有负责人 → 不发 `--add-label`」的测试。

其他检查都没问题：环和重复挂载的处理、`underSpec` 只标在 SPEC 子树里、只有 map 直挂 SPEC 时的继承、决策票被排除在实施票之外、gh 失败时整轮跳过。
