## Unix 传输计费

`WireAttempt` 在同一个 job 上记录一次实际 reader/peer 尝试；同 attempt 的读写不重复记 request，重试重新记 request，绝对期限不重新开始。底层仍使用唯一读循环，保留原 LF、EOF、解析和每操作期限限制。实际读写返回的 n 字节先入账，再检查上限和期限；坏 JSON、校验拒绝、超帧、超时前前缀以及部分写失败不撤销已发生的字节。

wire 累计采用内部 u128，公开八字段限额仍是规范十进制字符串和既定数域。它修正了原记账器「实际已发生的超限尾字节未入账」的缺陷；其他预授权计数及空间预留/对账未改。旧语义的负例由工蜂在实现后临时恢复旧记账行为得到，不能写成提交前 TDD 时序。

工蜂原始交付通过资源核心 17 项、真实 Unix I/O 8 项、既有 transport 2 项及两条旧调用方定向回归，并完成 release bin 构建。主控与独立 DeepSeek 复核发现成功校验后的 job 期限检查以及零长度写的期限门缺口；新增测试先在原交付上实跑失败，修复 `settle` 后，主控复跑资源核心 17 项、传输 9 项全部通过。独评复核修复后无新阻断；错误返回同时保留资源停止和原底层诊断。

本片只覆盖实际 UnixStream 读写。connect/spawn 前的开工、HTTP、CLI stdout/stderr、内容 path 证明、节点与顶层记录访问、数据库暂存和存储分配仍须在实际 S/Q/E/B 调用点继续接线。测试内八字段不是首批实测资源档。

## 内容片段与已发布 Delta 读取

`s_content::fragment` 沿现有唯一 path/M-tree 解析器读取数组、对象、字节或单值范围，返回每片独立的路径与范围证明。公开数值仍为规范十进制字符串；末尾空范围先检查加法溢出，再按实际 total 截断。证明按根去重升序，每个节点均核标签、原件字节与摘要。接收方用本片证明独立重算，不能借旧缓存掩盖缺失节点。

读取按实际访问节点计同一 job 的唯一节点和期限；回复构造需要显式 `max_reply_bytes`，对证明、条目和字节展开逐步限额。它不是 wire 计费，也不覆盖外层 anchor/token/envelope；调用层仍须核完整回复并在实际 I/O 处计费。重复子图的超大数组可从高 offset 取得有界片段，不展开此前所有元素。范围证明不替代未读内容的 schema、来源和业务完整核验。

内部 `reader::delta_fragment` 在同一只读事务内先调用完整 `state::audit`，然后核实际发布代、交付保留窗口和 exact 八字段 anchor，再从真实 Delta 根读取。伪根、跨会话、改头、未发布节点和已淘汰旧代均拒绝；新提交不改变仍在保留窗内的旧代片段。测试还在 query-only 连接中确认读取不写库，且当前目录损坏不会因目标旧根未变而被略过。

### 对象键展开的限额修复

在 `d1041b00a2976f414f692fba48a568746feff33e` 之后，主控检查发现对象键先完整渲染至 Vec、之后才计入回复限额。8 TiB 逻辑键仅用少量共享节点表达，唯一节点预算不能限制其展开量。新增回归在旧实现实际失败：有限的 2000 次读取护栏先触发，错误不是应有的回复超限（`/tmp/1394-fragment-key-red-20260918.log`）；没有实际尝试展开 8 TiB 或等到 OOM。

修复把定位和展开分开：path 只交回键引用，fragment 按剩余回复预算先核原始字节长度下界，再用每次写入前检查上限的缓冲接原有渲染器。JSON 转义放大也受限；编码缓冲与解析后 String 各自有显式上限，证明和最终完整 item 继续统一计入回复。缓冲上界取渲染前剩余额度，渲染中新读证明可能增加暂存总量，最终回复仍检查完整总额；这里不声称回复字节上限就是进程峰值内存上限。

Luna 子代理复核修复后未见该无限展开缺口继续存在。最终片段 8 项、路径 9 项通过（`/tmp/1394-fragment-key-final-20260918.log`），包含转义放大、实际序列化长度恰好等于上限及少一字节的边界。Delta 读取 3 项再次通过，耗时 5.05 秒（`/tmp/1394-fragment-key-reader-final-20260918.log`）。此前整组 86 项结果绑定键修复前的提交；本次只追加受影响范围检查，不冒称重复执行了整组。

Luna 只读定位确认：`rust/src/session_protocol.rs` 的 `canonical_json`/`sha256_hex` 可供规范字符串组成的 token 与旧 Python 实现对拍；任意 JSON 数字仍不能宣称逐字等价。旧 `s_session/s_query.py::_token`/`snapshot_page` 在 checksum 后仍重建实际 projection；新 content token 不能沿用旧 schema，也不能靠 checksum 授予读取权限。真正的 capture 摘要来自 `s_session/s_query_integrity.py::capture_digest` 对完整捕获 image 的类型与长度分帧；`s_query.py::capture_verified` 还包含事务、data_version、文件身份及独立 capture/verify 资源门。当前 Rust 没有等价实现，不以某个根摘要或当前事务序号伪填它。

## 完整 Q 投影根与 projection anchor

`projection::build` 从同一事务已完成 `state::audit` 的发布快照取六族记录引用，按原 Python Q 的 `_order`/`_key` 元组排序并排除重复公开键、active/withdrawn 冲突。撤回对象按撤回代号排序，不能直接复用 S 快照的历史主序。完整 logical fixed_cut 保持 16 字段，projection 保持七字段；catalog_evidence、catalog、record 接入所指的实际值边，qcut3 依 F(0x22, V(完整投影)) 计算，不散列引用的四字段 carrier 或当前页。

会话代号从现有 `v2::protocol_identity` 读取，真实来源是协议控制表；首轮测试发现并修正了误从普通 meta 取值的问题。零代沿原合同保留空六族、前沿 -1、空 index_frontier 和未运行目录。历史 catalog 由冻结静态列按 catalog_id 排序，再取目标代已封存 axes，证据保持边；新提交不借当前目录状态覆盖旧 cut。

`reader::projection_fragment` 在每次请求的同一事务内先完整审计，再重建指定投影，逐项比较 exact 四字段 anchor 后读取范围。临时 Q 节点留在 HashReader 内存派生层，不写 S 数据库，也不持有跨请求事务；同一旧 cut 可在新请求中确定重建。Delta 的交付保留窗口不错误地淘汰合法旧 projection。

构造时按实际遍历累计六族顶层记录访问，并对读取和新建的节点计同一 job；目录项不计为六族记录。Luna 独评提出的 catalog item 记录计数建议经核 §5.6.1 后撤回，不扩写批准的计费口径。独评另发现排序元数据的无界字符串展开，已改为调用方显式传入的内部 `max_metadata_bytes`：按声明长度早拒、逐写限制转义输出、累计扣减已物化字节，失败已输出前缀也不退账。这个内部构造参数没有写入公共协议或新服务资源配置；它不等于完整 Q capture/cache 或进程峰值内存限制，正式调用层仍须接回原有资源门。

当前生产变化由 Astra 主控实现，已有 Luna/high 子代理独立只读复核，元数据修复后未发现新高影响问题；其结果已接回并中断回收。本轮未重试此前返回 402 的 DeepSeek，也没有新 Sandcastle 运行，不覆盖以前成功工蜂的收据。

## 一致捕获、真实 capture 摘要与审计期限

新增内部 `capture_verified`：以只读 WAL 连接在一个事务中读取实际 schema 元数据和全部 typed 行，记录同连接的 data_version，并核捕获前后的文件 dev/inode。完整新捕获允许捕获期间有提交，返回其实际读事务固定的切面；不会把旧图像重标为新版本。源事务结束、连接释放后，只用项目固定 DDL 重建私有内存 SQLite，再复用完整 `state::audit_bounded`。句柄转为 query-only，审计通过后才构造 `VerifiedCapture`，它可向上一片投影核心提供真实内容和捕获摘要。

`capture_digest` 保留源库实际 schema_rows/schema，包括原 DDL 字节、列元数据和排序后的隐式索引；逐表按原 PK 顺序、raw_events 按 seq 读取，按原 Python 算法的 NoneType/int/str/b 标签和八字节长度分帧。字符串用流式 JSON 编码分两遍取得长度和 Hash，不创建转义后的整份临时副本。没有把固定 DDL 副本的 schema 文本、文件路径、data_version 或物理页号混进摘要。

首轮真实测试发现仅按 PK 导入会丢失 S3 独立索引依赖的首次插入序。已在同一条源查询中保留实际 rowid，作为私有复制信息计入容量并原样导入；WITHOUT ROWID 表不取它，INTEGER PRIMARY KEY 别名的值保持一致。rowid 不改变原 capture_digest 配方，完成判断仍须完整审计，不能仅凭摘要相同复用健康结论。未修改源库或放宽出生序判据。
