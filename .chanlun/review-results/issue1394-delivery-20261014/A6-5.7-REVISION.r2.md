## 2 修订一：多请求一致性（替换 §5.7:336 的相应规定）

### 2.1 修订条文

§5.7:336 写明「每片须在新的短读事务确认该当前控制元组仍一致且 pending=false……这个多请求一致性行为属于新版本明文合同」。本修订保留「短读事务、控制元组一致、pending=false、变化即 MissingDependency、不拼接两次观察」五项，改变的是**审计执行的次数与位置**：

> S 财务读取会话（`financial-serve --protocol-revision s-session/3`）在写者收尾、写者收尾托管（`s-financial-session-custody/2`）落盘之后，由 runner 以同一冻结 S 二进制启动。启动时：对 S DB 以同连接三点 `data_version` 夹持做一次当前一致捕获，导入私有副本 P；在 P 上执行与冷路径逐字相同的 `state::audit`；以同一 `current_basis` 得到 anchor 与派生 basis 根；在同一捕获事务内记录控制原件 K0，并核其与 P 上同值。此后每个 `financial-basis-ref`、`financial-content`、`financial-closure` 请求须同时满足 R1–R8，才从 P 的新短事务供片；会话保留量受 R9 约束。
>
> 任一条经**显式比较**不成立，本请求返回 MissingDependency，会话失效并拒绝之后全部请求。请求内不重审、不回落冷路径；重审只能由 supervisor 停掉旧会话、在任何请求窗口之外重新启动。两类情形只拒本次、会话保持有效：① anchor 或会话身份与已审状态不符（reject-request）；② 本请求的 SQLite 读取确被请求期限中断或 busy 等待耗尽（由类型化记号判定，不看墙钟）。会话期间任何 S 写入都使会话失效，所以使用会话的阶段要求 S 静止。

来源说明：①是用户裁定项（`anchor_mismatch=reject-request`）。②不是用户裁定项，是实现层既有的 Incomplete 分类（`financial_session.rs:1266–1271`，`Fault::Incomplete` 转为 `SessionRequestDeadline`；c2 独审 F4 修订后的行为），APPROVED-SOURCE:292 要求资源门不满足时报告真实 Incomplete。S86 r6 的 runner 合同把会话失效判为 FAIL（DESIGN-R6 :57；`CONTRACT-R6-DRAFT.json` 的 `financial_session_stale_is_terminal_fail`；r6 runner `s86_session.py:284–285` 要求 FINAL 的 `stale` 为空），这是 runner 口径，不入 §5.7。

| `max_reply_bytes` | 规范正整数十进制文本：本块回复（规范 JSON 加末尾 LF）的字节上限；E/B 取冻结 `reader_resources.max_reply_bytes` |

### 3.2 回复

exact 九字段（`financial_reader.rs:835–837`）：`anchor`、`path`、`after` 三项逐字回显请求；`target_ref`（目标 ContentRef，E/B 下等于 `basis_ref`）；`total`（闭包节点总数，规范十进制文本，每块相同）；`nodes`（每项 exact `root,tag,body_hex`，即 §5.6:280 的节点格式，按摘要严格升序且大于 `after`）；`next`（本块最后一个节点的根）；`done`（当且仅当本块到达闭包末尾）；`ok`。

### 3.3 闭包与分块

闭包 = 从 basis 根沿 `path` 到目标的路径证明节点 ∪ 目标的完整可达节点，按摘要升序。S 用与冷路径同一个 `lookup_path` 与 `sc::verify`，在同一个逐节点核 F 的 `HashReader` 上枚举；每个出块节点再核一次 F(tag, body) = 摘要。一块 = `after` 之后按摘要升序的最长前缀，使回复不超过 `max_reply_bytes`；首节点即装不下则拒绝本次（`Incomplete/ClosureReplyBytes`，`financial_reader.rs:865–870`）。块边界只由请求与已审状态决定，所以会话与冷路径逐字节相同（#804）。

接收方块数帽 `max_chunks = 2·⌊max_total_wire_bytes / max_reply_bytes⌋ + 1`，只由冻结 `reader_resources` 派生，不新增冻结字段（`financial_content.rs:926–950`）。依据：S 贪心装满每块，相邻两块回复字节和大于块大小，故 k 块回复总字节大于 ⌊k/2⌋ 倍块大小，而总字节不超过 wire 帽；独审已核此推导（`7785c0ca…` 的 `chunk_cap_derivation`）。

会话为当前 (anchor, path) 保留至多一张升序摘要表，换键先丢旧表；表大小受 `max_closure_nodes` 约束并计入 R9（2.3 节）。枚举期间的瞬时集合（`Recording.seen`）不计入保留门，上界随 `max_closure_nodes` 线性，r5 规模估约 8–12 MB（推断，未测；闭包独审 N3）。

### 3.4 代替证明（替换 §5.6:282 在本读模式下的适用）

§5.6:282 要求「每个片段的证明独立完整」，即每片从 anchor 根覆盖到目标的路径。在 `financial-closure` 读模式下改为：

> 闭包块内的节点不各自附路径证明。接收方对每个节点照旧重算 F、按不同根计入同一 Job，同根不同字节即拒绝；整块写入自己的暂存（一块一个事务）。闭包取完后，接收方从 basis 根做一次完整核验（`verify_local`：完整 `sc::verify`，加六族记录计费与头部核验），并要求**该次核验实际读到的节点集与收到的闭包流逐个相同**：不多、不少，根可达节点即使接收方本地已有也必须出现在流中，不因已缓存而豁免。两者任一不成立，本次闭包尝试失败：先回滚本尝试写下的暂存行（每块的新摘要在该块事务提交的那一刻登记，块提交后的 checkpoint、对账或载体检查失败时同样回滚），再返回原前缀的 MissingDependency，由 `read_current` 照原规则重取 basis。

两个方向各有一条错误文案：核验读到而流里没有，报 `IdentityConflict：闭包流缺少根可达节点`；流里有而核验没读到，报 `IdentityConflict：闭包流含 N 个根不可达节点`（`financial_content.rs:1104–1115`）。「本地已有不豁免」与 §5.6:282「不得省略本响应必需的证明节点后假设客户端曾缓存」同向：成员核验包的是本地暂存，本地已有却不在流里的根可达节点同样触发前一条。

保留不变的部分：§5.6:282 的「相同根不同字节即拒绝」与「全部实际传输量照实累计」；§5.6:286「不能用一个根 Hash 代替原来应执行的检查」——完整核验、发布两轮 `verify_many` 与审计逐证据遍历全部保留；§5.7:338「整次读取受 reader_resources 与经济操作绝对期限共同约束，片段不重置期限」——每块经同一 `finance_transport`（单次 45 s、回复帽、wire 计费）与同一 Job；§5.7:362–364 的闭包导入、发布前持久可达、失败不产生 Prepared/grant/责任、离线恢复不依赖 S。实现与证据：闭包 r2 README :45、:51–57；r2 复审（`long-r4-closure-review/r2/RESULT.json` `caf5fa85…`）确认回滚登记时机（N1 关闭）。

## 4 单读法：每个冻结 manifest 只认一种读法

> E/B 的 S 读法由冻结 `finance.structure.reader_session` 的值决定，且只由它决定：值为 socket 路径时，全部 S 读取带 `--session`，缺节点只走 `financial-closure`；值为 `null` 时，全部 S 读取走冷路径，缺节点只走逐片 `financial-content`（第 5 节退场之前）。同一 manifest 内不存在第二种读法；一种读法失败即返回错误，不改走另一种（#799「接在同一个 if-else 上」的判别式由此不成立：选择在冻结时完成，运行中不发生切换）。

实现要求（A4）：`SourcePins::from_structure`（`financial_content.rs:227–257`）读 `reader_session` 并产出显式读法（建议枚举 `Reading::{SessionClosure, ColdFragment}`），`read_once` 的选择（现 `:450` `let closure = pins.session.is_some();`，分支 `:504–519`）改看该枚举；`with_session`（`:258–267`）去掉 `#[allow(dead_code)]` 或并入 `from_structure`。配锁：同一 pins 两种读法不可并存；`SessionClosure` 下导入失败后不发出任何 `financial-content` 请求；`ColdFragment` 下不发出 `financial-closure`。这也是 PLAN :42 列的增量独审点「同一 manifest 两种读法不可并存」。

## 5 被替代读法的退场条件

被替代的是 **E/B 以逐片 `financial-content` 取闭包**这条读法：`reader_session=null` 的 manifest、`download`（`financial_content.rs:1172`）、以及只在该读法下执行的 `import_proof` 单独暂存（`:499–501`）。S 侧 `financial-content` 命令本身不在退场范围。

> **退场条件**：上述读法在合入 #1394 的 PR 中删除；删除后 `reader_session` 只接受 socket 路径，`null` 被拒绝。该 PR 合入前须同时成立：
> 1. `SessionClosure` 读法在 Long 受测域 fresh-a、fresh-b 实跑 PASS 并经独审（PLAN S6、S9）；
> 2. 根确认现存全部 `null` 读法的经济库都是 TestOnly 证据库，不再发起新的 Prepare、Reserve 或 Commit（§5.8:381 已不授权带未结责任会话的热迁移）；仍要跑的短域例（如 PLAN S6′ cap80）已改用会话读法或经根裁定复用旧证据；
> 3. 闭包导入在最终字节上的节点集与独立遍历逐个相同的收据入仓，用来代替尚缺的「闭包与逐片节点集相同」Rust 锁（闭包 README :108）。
>
> 三项前提是合入 #1394 的 PR 的前置条件：任一条不成立就推迟合入，不以到期日并存（根已裁 A6-3）。

退场之后的旧库：`verify_image` 只读本地 `content_nodes`（闭包 README :103），不需要逐片读法；但它经 `verify_evidence` 调 `from_structure`（2.4），退场后 `from_structure` 拒绝 `null`，所以 `null` 读法的旧 `/2` 库在新代码下与九字段库处境相同，也不能离线审计。前提 2 因此同时覆盖这两类库，A4 按 2.4 的核对办法一并处理。r1 写的「`null` 时代的旧经济库照旧可离线恢复与审计」不成立，r2 撤回。

成因与代价：逐片读法对空 owner 约需 3.2×10⁴ 次请求、约 1 GB wire、经子进程约 7.5–8 分钟（`SECOND-QUESTION.md` :7、:13、:29–31，原型外推），在 Long 域装不进任何经济窗口，留着它也不能充当后备；它仍在用的地方只有短 TestOnly 域。代价是条件 2 可能要求把短域 runner 接上会话，或由根裁定复用旧证据。

## 6 接线条款：冷 6 参 `financial-closure` 是对照臂
