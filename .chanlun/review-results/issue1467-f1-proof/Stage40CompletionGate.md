## 本轮尝试及实际结果

尝试从已取得结束证据的线段构造 `a+A+b+B+c`，用两枢外缘分离取得趋势形态、真实笔源取得力度，并用后继中枢不再同向定位结束。尚未构成合格的完整走势。检查声明前件时已发现两处不能直接继承的接口，因而未继续生成合成行情、堆叠数值或给完成字段赋真。

第一处是 c 的角色。`docs/chanlun/text/blog/037-第37课.md:16–22`【正文】要求 A/B 同级、c 具有相应次级别身份、c 内含对 B 的三类点、方向上的新极值及其内部结构。第一种情况线段结束只提供该线段的结束证据，不能单独证明这些条件。第57课26–32行已经区分最低视点中的线段角色和离开/回抽所需内部结构；第84课52–56行允许另选初始构造，也没有把一条中间线段直接批准为这里的完整 c。

这是一项资格缺口，不是“任何已确认线段均不可能承担 c”的全称结论。若某一条线段确有相应内部来源及角色证明，应逐项检验；不能仅凭名称放行或拒绝。

第二处是结束证据的方向。第35课16行确实给出最低趋势随中枢次序不再同向而结束的描述；本仓 `.chanlun/definitions/beichi.md:313–323` 的既有裁定却明定，由背驰定义完成，不把“不再产生同向新中枢”直接作为另一完成判据。因而本研究可研究后继中枢与已发生结束的关系，但不能自行把这个几何条件接入完成入口，或宣称它已经等于动态完成。这里须解释适用对象和证据方向，不能以一个新的 Bool 隐去。

## 已有最小见证明确了哪一个接法不成立

沿用 `CenterAttemptSpec.lean` 的原 A 例，未改其任何定义：

- `leaveA` 发生区间是 `[3,4]`，可知时刻是 5。
- `retA` 发生区间是 `[4,5]`，可知时刻是 6。
- 原 `WITNESS_TARGET` 中 `firstPairUp` 在时刻 5 不成立，在时刻 6 成立。

若新增适配把 c 定为 **leaveA 本身**，该次回抽的终点 5 不在 c 的发生区间 `[3,4]` 内，因为 `5 > 4`。将二者共同确认的三类点登记在 c 内，不能由原 `UpPair` 关系推出。把发布推迟到 6，只改变何时知道，不能改变成员或发生位置的归属。

这是对既有定义的直接代入及整数比较，没有本轮新增 Lean 根或一般不可能性定理。它拒绝的是“c=离开单元，再借其后回抽把这次三类点算进 c”这个具名接法，不否定原 Stage11 的局部桥，也不否定 c 内另有更低结构的可能性。扩大 c 的发生范围属于另一个构造版本，必须重新解释方向、端点、成员和完成，不能原样继承 leaveA 的确认结果。

## 本轮核查的正规换模接口

按[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server#message-schema)用本机 `codex-cli 0.159.1` 生成实验性协议 schema。它确实包含 `turn/settings/update`，参数有 `threadId/turnId/model`；说明限定为当前运行 turn，并警告已捕获步骤与冻结设置的消费者不会回溯改变。`thread/settings/update` 则仅影响后续 turns。因此“协议没有任何换模接口”不是正确表述。

实际执行 `codex app-server proxy`，在发送 initialize 请求前的连接阶段失败：默认 `/Users/silencehan/.codex/app-server-control/app-server-control.sock` 不存在。`daemon version` 同样连接失败。只读进程 Unix socket 检查未见 codex 进程暴露有路径的 control socket；桌面进程的 IPC/browser socket 不当作该协议入口使用。本轮没有发送任何模型 mutation、没有启动/重启 daemon、没有写数据库或 UI 旁路，也没有宣称当前父推理已经由 GLM 服务。

这不证明所有其他环境均不能换模，只表明本轮所查官方连接方式没有接到承载当前 turn 的服务。启动另一台本地 app-server 不会把当前内存中的推理任务搬过去，不能拿另一个进程的设置成功作为父模型切换证据。

用户要求“父会话先切 GLM，再派发，派完恢复”，此前的权限选择问题仍未收到回答。本轮不能据自动 goal 续跑推定豁免。只在能够验证父模型实际服务、或收到用户对本次派发的明确调整后，才发送独评。所有待审材料保留 `not_reviewed`。
