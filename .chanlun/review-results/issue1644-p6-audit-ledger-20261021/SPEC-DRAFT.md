## 一、问题

S 写者每处理一条 ingest，要把「已经发布过的全部历史」和「这一代刚造出来的候选」各从头核一遍：

1. 接纳、Begin、Prepare 三个写事务前各跑一次完整 `state::audit`（#1481 第 11 行；main `s_allocation.rs:103` `Mode::Ordinary => return state::audit(tx)`），实测 ∝ G^3.09（#1481 评论 6160170913）。这是 #1481 方案三的对象。
2. prepare_source_audit 在 ordinary 分支逐个原始事件重算哈希、逐个对象/组/形态/见证/观察重核，「设计上就是全量核验」（#1488 PLAN.md:39–48）。
3. 清单组装对 scope 与三个根做全闭包 `verify_ref`，main `content_manifest.rs:1225` 注释写明「同一次读集核完整闭包；路径算子只核触碰边界，不能替代这里的全闭包校验」；publish 阶段又把同样三个根再核一遍（PLAN.md:70）。

这三处都是「对 N 的读」，所以每请求下限是 Ω(N)。用户 2026-10-21 要求「速度性能必须快」并要扩到交易挂单，主控据此裁 G4 挂单级默认 p99 ≤ 10 ms、≥ 1k 事件/s（#1612 评论 6307840577 第 5 条；ADR 0042 性能表）。G4 在 Ω(N) 下任何一档都不可达（ADR 0042「G4 依赖 #1481 方案三」段）。

去掉 Ω(N) 只有一条路：把「之前已经核过、此后没被动过」的结论存下来，下一代只核新增和被动过的部分。这就要一份**审计台账**。它撞上了已批合同的字面——APPROVED-SOURCE（用户「照办 批准」采纳，#1481 第 1 行）:65 要求「每次写前仍取得当前一致性读集中的全部可达根、独立索引和唯一依赖」，并说「共享表示……不保证每次校验只随新增数据增长」。所以这是 spec 级（ARCH.md:28）。

本票要定：台账的形状与坐标、存放位置、信任边界与「可丢弃、冷启动可重建」论证；清单全闭包核验的替代判据及其与 #804 锁的关系；回退口径；与 #1481 方案三的分工；与 G4 的关系；以及被修订的 SPEC 字面。

## 三、候选

**台账存放位置（K2）**

- **甲（推荐）写者专属旁挂文件**：与内容库同目录同卷的一个独立 SQLite 文件，只有 S 写者读写。内容库 schema 不变，旧二进制看不见它；丢弃 = 删除该文件。代价：与内容库的提交不是同一事务（WAL 模式下跨库不原子），须靠「台账只是缓存、冷启动必重认证」兜住一致性（裁定三）；多一个文件要纳入备份与目标卷容量账。
- **乙 内容库内新表**：与发布同事务原子写入。代价：内容库 schema 升版本，`mod.rs:835-853` 的精确核验使 P6 前的二进制拒库，回退要先显式删表（ARCH.md:169「回退不再免费」）；台账进入内容库字节，`compare_s86` 的表全集比对要另行排除。
- **丙 纯内存**：不建表。排除：与 #1481 第 24 行「不常驻全部原件」相冲，常驻量随 N 增长，全史规模不可行；且每次重启同样要全量重建。

**跨进程信任（K3）**

- **甲（推荐）每次冷启动线性认证折叠**：进程启动或 recover 时，对已发布历史按代依次执行与在线完全相同的 Δ 步，重新产出台账；旧台账文件不被准入读取（可用于诊断比对）。代价：冷启动 O(N_total)。在案外推（旧布局，未在 bounded-layout 复测）：9011 约 147·9011 ≈ 1.3×10^6 可达节点 × 9.5 µs ≈ 13 s；全史 4,613,599 代约 6.8×10^8 节点 ≈ 1.8 h。
- **乙 正常关闭时封印、重启验封即信**：关闭时写「台账折叠摘要 + 主库/WAL 身份与 stat」封印，启动时身份未变即信旧台账，否则全量认证。重启快。代价：两次进程之间若有人绕过写者改库并保住 stat，下一次写前查不出来，要等离线认证——这是对 :65「根/叶损坏……须在任何写入前拒绝」的进一步放宽；它与甲是同一判断（「旧前缀仍是已审状态」）的松紧两档，按 ADR 0041 第二条**不得做成可调字段**，只能单选。现在不推荐；若 bounded-layout 复测后全史冷启动不可接受，再开票单独裁。

**完整审计（全闭包读法）去留（K8）**

- **甲（推荐）降为测试 oracle 与离线认证入口**：不在任何生产准入路径上；CI 对拍锁实际执行它；9011 终态离线认证用它（#1481 第 30 行）。
- **乙 随完整重算一起删除**：与用户「完整重算就不要了」字面最贴近。代价：Δ 读法失去唯一的独立对拍对象，#804 锁只剩冻结基线（只覆盖入仓输入）与自身双跑，负例（同 ID 换内容、缺节点……）的拒绝类别无从对拍；且推翻 #1481 U-B。

## 四、裁定（草案，待批）

**裁定一：台账的形状与坐标。** 一份「S 审计台账」，按流分区，全部用身份坐标，不用数组下标、order_key 或出生序：

| 分区 | 主键 | 记录内容 | 写入时机 | 主要读者 |
|---|---|---|---|---|
| raw | raw seq（只追加） | 事件规范哈希、raw_bar 摘要、首次认证代 | 本代新事件发布后 | P6 来源审计② |
| object | object_id | 去掉三项代戳（first_known_generation、first_known_cut、published_generation）后的记录摘要、三项代戳原值、来源坐标集摘要、撤回状态、最近认证代 | 对象出生、修订、撤回的代 | P6 来源审计③ |
| witness / observation | 各自身份键 | 记录摘要、来源坐标集摘要、最近认证代 | 同上 | P6 来源审计③ |
| cover | raw seq | 归属的组身份 | 划分变化的代 | P6「划分覆盖全部 raw」增量维护 |
| node（已认证单位集） | (节点摘要, 上下文 Flavor{Value, JsonInner}, 核验模式 Mode{Public, Template}) | 首次认证代 | 该单位首次出现在某代各根的可达闭包中、并在该代按该上下文与模式核过时 | P6 清单④的「已认证」点查 |
| cert（逐代证书） | generation | 各根 ContentRef（scope、generated_state 为 Public 模式，publication_template、delta_template 为 Template 模式）、本代新增可达单位集（定义见下）的摘要与计数、台账截至本代的折叠摘要、核验判据版本；#1481 追加已发布历史侧的逐代结论字段 | 每次发布后 | P6 清单④、#1481 Δ 单代判据 |
| meta | 单行 | 台账格式版本 `s-audit-ledger/1`、rule_revision、内容库身份、certified_through_generation、生成二进制提交 | 冷启动认证完成、每次发布后 | 全部 |

**认证单位**取现役全闭包核验器的去重单位：main `rust/src/s_content.rs:1977-1980` `AuditMemo` 的 `seen: WorkSet<(NodeDigest, Flavor)>`（注释「已核过的 (摘要, 上下文)」），再加核验器的 `Mode`（`s_content.rs:259`；Public 模式拒模板占位）。同一摘要在 Template 根下核过、后来被 Public 根引用，是另一个单位，要在 Public 模式下重核——这与 #1481 第 24 行「异位置同摘要按新上下文重核」一致。序列节点（字节块、元素序列、字段序列）不是认证单位：现役 `seen` 只装值节点，序列随所属值节点整体折叠核验（字节序列的折叠 memo 键含 UTF-8 与数字进态，`s_content.rs:1985-1987`）；它们不入 node 分区、遍历时不止步，随所属值节点一起核。

**本代新增可达单位集**定义为：本代各根（scope、generated_state、publication_template、delta_template，即 main `content_manifest.rs:1226-1231` 全闭包实际核的全部根）按各自模式展开的可达单位集，减去 node 分区在上一代末的内容。它只依赖已发布原件（历史各代的根取自已发布 manifest 记录），冷启动折叠可逐代复原；在线事务里实际落库但不可达的中间节点（#1481 评论 6160170913 M2：表内约 55% 不可达）不在其中，不进 node 分区、不计入证书。早先落库、从未可达的节点若在本代第一次以某个单位变得可达，它属于本代新增可达单位，本代按该单位核过才入 node 分区。

代戳一栏的处理来自探针 0064：身份延续对象在去戳后内容 100% 相同，三项代戳只做 O(1) 逐条核对；把代戳移出生成态记录是规则修订级改动，登记给 #1491，不在本票。

台账有自己的格式版本，不进 rule_revision、公开根、可达闭包、manifest、Q/E/B 读侧，也不进 `compare_s86` 的 INVARIANT 集合。台账格式换版本即整份丢弃重建。台账表结构归 P6 实施票所有；#1481 往 cert 分区追加的字段经台账格式升版本加入（台账是缓存，升版本 = 下次冷启动丢弃重建，无迁移）。

**裁定二：存放位置 = 写者专属旁挂文件（候选甲）。** 内容库 schema 不变。前提：S 写者单线程顺序处理请求（现行即如此）；台账文件本身是 SQLite，每代的台账更新在台账文件内是一个事务，不会出现半代。写入顺序：内容库 Commit 成功后再提交该代台账事务；台账提交失败 ⟹ stale 停写，丢弃进程内全部台账状态，等监督器 recover（不重试、不跳过台账继续写）。生涯内准入因此不会读到与内容库不一致的台账：要么两者都到本代，要么写者已停。

台账文件字节计入每库存储帽 `max_store_bytes`（#1481 第 28 行，每库 64 GiB）的同一笔账，与内容库及 WAL 合计，不另立帽；它不占 S7 `audit_cache_source_bytes`（S7 管进程内保留量，台账在盘上，每请求只读写 Δ 行）。量级照实：node 分区行数 ≈ 已发布可达节点数，约为内容库节点表的一部分，全史规模下是几十 GB 级（旧布局外推），在段 B 实测前不作门值。

与现役 S 审计缓存的关系：s-cache Memo 的作用是「每次仍读全域，但逐字节相同就复用解码」，在 S 写者准入路径上它被台账 + 夹持取代——写前不再读全域，也就没有要复用的全域解码。退役归 #1481（Memo 用在 `state::audit` 一侧），在 #1481 方案三接线时把 S 写者准入路径上的 `cache::configure` 置为不参与，并按 #793 带票号改 `cache.rs:1-2` 文件头口径（读侧 Q/E/B 继续按原口径使用，不在本票）。S7 字段语义的最终归属随 #1641 的 `s-structure-resources/2` 签署；P6 本身不新增 S7 用量。

**裁定三：信任边界与「台账可丢弃、冷启动可重建」论证。**

台账结论只在「一个写者进程生涯 + #1481 U-A 夹持持续成立」之内可被准入读取。每次冷启动（进程启动、监督器 recover）先跑一次**认证折叠**：从 g=1 起按代调用与在线**同一个** Δ 步函数，把台账从空重新算出来；完成前不接受任何写请求。旧台账文件不参与准入，只作诊断比对（不同即记一条诊断记录，按 #799 限定词第 2 条不参与准入）。

论证分四步：
1. 台账是派生数据：它的每个字段都是已发布原件（内容库里的节点、索引、clock、manifest）的确定性函数，台账本身不产生、不改变任何公开事实。
2. 准入从不信任跨进程留下的台账：冷启动必经认证折叠，折叠只读原件。所以台账文件被删、被截断、损坏、或落后于发布代，结果都一样——折叠重新算出它。
3. 折叠与在线 Δ 是同一个函数在同一输入序列上的调用，输出逐位相同由锁保证（验收第 3 项），所以重建的台账与「不中断运行留下的台账」逐位相同。
4. 公开根、回执、内容库全部表与台账有无无关（台账不在内容库里），所以「丢弃台账 → 冷启动」前后公开输出逐位相同（验收第 4 项）。

代价：冷启动 O(N_total)。冷启动窗口帽为签署门字段 `audit_ledger_cold_start_window`，默认 `AwaitingPolicy`（ADR 0041 第三条之 2）；推荐值在 #1491 段 B 后于 bounded-layout/1 实测给出，旧布局参考上界只作参考（#1481 评论 6160170913：恢复窗保守上界 16 小时）。超窗即启动失败，不降级。该字段进 S 写者资源档：若 #1640（切片 1）定 `s-structure-resources/2` 字段表时 P6 已批，则预留进 `/2`（签署前 `AwaitingPolicy`）；否则 P6 实施票把资源档升为 `/3`，旧档拒绝。

**裁定四：清单全闭包核验的替代判据。**

判据本身不变：发布的四个根（scope、generated_state 按 Public 模式，publication_template、delta_template 按 Template 模式）闭包完整，每个节点字节与其摘要相符，依赖齐全，同 ID 换内容与缺节点拒绝。变的是读法：

- 已认证闭包 = node 分区在上一代末的单位集。本代闭包 = 已认证闭包 ∪ 本代新增可达单位集（裁定一定义）。
- 写前只核：(a) 本代新增可达单位按其上下文与模式的全部检查（与全闭包核验器对该单位做的检查相同）；(b) 从四个根按各自模式出发遍历，遇到 node 分区里已有的**同一单位**（摘要、上下文、模式三者都相同）即停——该子树在首次认证代已按同一单位核过，内容寻址、节点表只插入不更新；摘要相同但上下文或模式不同的不止步，按新单位重核；不在 node 分区的一律算本代新增可达单位、核过后并入；(c) 四个根的 ContentRef 四字段与真实节点逐项对应。
- 旧节点「字节未变」不再靠每次重读证明，而靠 U-A 夹持（同连接 data_version、主库/WAL 身份与 stat、写者自身效果日志）。夹持失效 ⟹ stale 停写。
- 同一请求内同一闭包只核一次：publish 阶段对同一组根的二次全闭包核验删除，改为核「本请求清单收据」与 prepare 阶段一致。

3. **「完整重算不要了」包不包括完整审计？** 你 10-21 的批复删的是完整重算的生成路径，ADR 0042 二、#1645 写的「不保留为……离线对照的任何用途」也都是指它；完整审计（`state::audit` 与全闭包核验）是另一样东西，#1481 你 10-13 授权时定的是「留作对拍 oracle 与离线对照臂，不参与准入」。三个选法：
   - 甲（推荐）：完整审计只留在测试和离线复核里当对照标准，生产里一次都不跑。好处是增量审计一直有独立的东西可以对拍，负例（换内容、缺节点）的拒绝类别也能对。
   - 乙：退役前把每一代的完整审计结果冻结入仓当基线，然后连代码一起删，和生成路径同一个处理法。代价是以后只能在入仓的那些输入上对拍，负例要另写。
   - 丙：直接删，不留基线。增量审计就只剩自己跟自己双跑，不推荐。
4. **能不能接受「某些磁盘级损坏晚一点才发现」？** 现行合同要求每次写之前都把全部历史重读一遍，所以哪怕硬盘悄悄坏了一个字节，下一次写之前就会被拒。改成台账以后，写者只盯「有没有别人动过这个库」（库的版本号、文件身份），这种不经过数据库、也不改文件信息的静默损坏，要等下一次重启或离线复核才会被发现。推荐接受：不接受就回到每次写前读全部历史，挂单级速度（G4）做不到。可以加一道定期后台复核来缩短发现时间，但它会和挂单抢 IO，默认不开。
