## 五个审查问题的 Codex 判定 + 本工位复核

### 1. 判据溯源诚实性 —— 部分成立

C2 溯源（`053:28` 二类点补充小转大）成立。C3 溯源本身成立（思维导图`128`/`044:52`），但**表述偏强**——第44课与思维导图都明确 C3 是**必要条件**，不是可单独确认成立的充分判据。设计稿 §2.2 把 C3 标为"✅ 结构可判"、并入门通行判据 C2∧C3，语言上容易读成"C3 满足即可信"，需要在结论文本中显式声明"C3 是工程侧保守过滤，非原文充分条件"。

**本工位复核**：这是合理的表述精度问题，非逻辑错误——必要条件作为 AND 门的一支在工程上是合法的（不会漏掉真阳性，只是不保证消灭假阴性）。判定：成立，但严重性为"文本澄清"级，不影响判据的可实现性。

### 2. C2 可实现性 —— 担忧成立（本次审查的核心发现）

生产代码中，B1/B3（`extract_signals_with_hist`）与 B2（`extract_second_for_level`）是**两次独立提取**，`mod.rs:253/259` 只做 `extend + sort_by_key(source_index)`，**没有按 source_index 合并 bits**。当一个 Type3-only 信号（`bits.buy3=true, bits.buy2=false`）进入 `build_nest_certificate` 的 `None` 分支时，它自己的 `p.bits.buy2` 恒为 false——即使同一 `source_index` 附近存在一个独立的 Type2 `BspPoint` 条目，也不会被这个 `p` 看到。

设计稿 §2.3 的 `XzdCertificate.type2_confirmed` 字段暗示可以直接从当前信号读出，但若不显式做跨条目查找（按 `source_index`/结构关联在同级 `bsp` 列表里找匹配的 B2 条目），`xiaozhuanda_confirm` 会系统性地把"存在共生 Type2 点"的真阳性判成假阴性。

**本工位复核**：本工位在调用 Codex 前已独立读代码定位到同一事实（`mod.rs:246-260` 的 extend 而非 merge），Codex 的判定与本工位预判一致，互相印证，非 Codex 单方臆断。**判定：成立，是设计稿的实质性缺口**，阶段2实装前必须补上"按 source_index/结构关联查找同级 B2 条目"这一步，否则 C2 门会系统性拒绝本应通过的信号。

### 3. 通道分离假设（"输入域不相交"）—— 部分成立，存在声明膨胀

`descend=Some`/`descend=None` 本就是同一个 `Option<usize>` 的两支，"不相交"是构造上的同义反复，不需要经验验证。设计稿 §4 结果包把"若通过域与区间套 120 条重叠则证伪"写成一个可能被证伪的经验边界，语气过强——按路由结构这件事根本不会发生（除非未来有信号被两条通道都处理，那是路由 bug 不是判据问题）。真正需要 L2 验证的是"`None` 域是否等价于原文『小转大』候选集，还是混入了其他建模缺口的残差"。

**本工位复核**：接受该判定。建议阶段2实装设计稿把 §4 边界条件2 的措辞从"验证不相交"改为"验证 None 域的语义纯度（是否混入非小转大的残差）"。

### 4. XzdCertificate 无 depth —— 语义要求成立，但存在一个真实的正确性陷阱

`NestCertificate` 本身没有独立 `depth` 字段（深度由 `rungs.len()` 派生），所以"不挪用 depth 字段"这个诉求本身没有直接的字段可挪用。但 Codex 指出：若阶段2实装图省事，直接用 `NestCertificate { rungs: vec![], terminal: bits, ... }` 来表示"小转大通道通过"，会踩中一个真实的正确性陷阱——**本工位已独立核实**（`nest.rs:200-217`）：`rungs=[]` 时 `n_delta()` 直接返回 `terminal.confirm_side(side)` = `bits.buy1||buy2||buy3`，而任何进入 `None` 分支的 Type2/3 信号本身就已经满足这个析取（因为它就是凭 buy2 或 buy3 才走到这个分支的）。也就是说，若用空 `rungs` 的 `NestCertificate` 冒充小转大凭据，`n_delta()` 会**无条件返回真**——与 C2∧C3 是否真的成立完全无关，是一个静默总放行的 bug，不是风格问题。

Codex 建议的最小修正：不新增完全平行的证书体系，而是加一层枚举 `enum GateCertificate { Nest(NestCertificate), Xzd(XzdEvidence) }`，`effective_nest_depth` 只接受 `Nest` 分支，门函数按 variant 分派，`n_delta`/深度诊断代码不会被 `Xzd` 变体污染。

**判定：设计稿"不可挪用 depth"的直觉是对的，但没有说清楚危险的具体机制（naive 复用 NestCertificate 空 rungs 会被现有 n_delta 静默通过）；Codex 给出的 GateCertificate 枚举方案比设计稿"新增平行 XzdCertificate 结构体"更符合最小复杂度（ponytail：不引入无谓的第二套平行类型体系）**——阶段2实装应采用枚举方案而非平行结构体。

### 5. C4 首次塔 vs 最终塔的零前视问题 —— 成立，且设计稿漏判了同样问题也影响 C3

设计稿 §3.3 只把"动态最后次级中枢"的零前视风险归给 C4，但 C3（"最后一个次级别中枢出现三类买卖点"）本身就是在找同一个"动态的最后次级中枢"——`044:56`原文明确"这个该级别走势最后个次级别中枢是动态的，不一定为小级别背驰点前的中枢"，这句话对 C3 和 C4 是同一个前提。若用最终塔回看来判 C3，容易把后续行情才确认下来的"最后中枢"提前绑定到当前 `source_index`，构成前视偏差；且第三类买卖点必须是"第一次回抽"（知识库 §10.3），最终塔回看还可能把非首次回抽的结构误判为符合。

Codex 建议的最小修正：证书区分 `source_index`（信号发生点）与 `confirm_index`（判据确认所用的观察点），C3 写成依赖 `confirm_index` 的显式函数（如 `sub_last_zs_type3_asof(confirm_index)`），若只能用最终塔判定，则 C3 不能进硬门，只能降级为回看诊断标签（与 C4 同等对待，而非区别对待）。

**判定：成立**——这是设计稿 §3（诚实边界清单）本身的一个遗漏项，不是新发现的判据问题，而是设计稿自己列的边界条件清单不完整（它意识到了 C4 有这个问题却没意识到 C3 有一模一样的问题）。这必须在阶段2实装设计定稿前补上，否则会把一个"待裁的零前视风险"错误地只圈定在 C4（软标注），而放过了同样风险却被当作硬门用的 C3。

## 结果包六要素

1. **结论**：设计稿的判据溯源基本可靠，但有一处实质性技术缺口（C2 需要跨条目查找，非当前信号自带 bits 即可判）、一处正确性陷阱（naive 复用 NestCertificate 空 rungs 会被 n_delta 静默放行）、一处遗漏的自我诊断（C3 与 C4 共享同一个零前视风险，设计稿只标注了 C4）。三者均可在阶段2实装设计阶段修正，不构成对"小转大通道"这个概念本身的否定。
2. **定义依据**：知识库 §10（二/三类买卖点定义、买卖点定律一）、§10.3（第三类须为"第一次回抽"）、`044:56`（最后次级中枢动态性）——均为 Codex 审查依据的同一批原文，本工位在调用前已独立核对。
3. **边界条件**：若阶段2实装采纳"C2 需跨条目查找"的修正后，命中率仍然极低（如 <1%），则原设计稿 §4 边界条件2 的"回到 C4/66课小平台"应急路径仍然有效，不受本次审查结论影响。若 C3 因零前视约束被迫降级为软标注（点5），则门通行判据退化为仅 C2（单条件），设计稿 §2.2"主判据=C1∧C2"这条更保守的表述反而变成阶段2实装的实际落点——这与设计稿 0节的"一句话结论"（"确认 = 等本级第二类买卖点"，未提 C3 硬门）内部更一致，值得阶段2设计者注意：C3 从"结构可判✅"降级不代表设计失败，而是与 §0 的原始直觉重新对齐。
4. **下游推论**：阶段2实装（task #15 TODO 清单）动工前必须补齐三处：(a) `xiaozhuanda_confirm` 增加跨条目按 source_index 查找 B2 的机制；(b) 用 `GateCertificate` 枚举代替平行 `XzdCertificate` 结构体；(c) C3 判据显式区分 `source_index`/`confirm_index`，若只能用最终塔则降级为软标注。这会改变 §2.3 的凭据结构设计（`XzdCertificate` 字段需要 `confirm_index` 或类似字段），阶段2设计需要一轮小修订，不需要推倒重来。
5. **谱系引用**：本次审查未发现定义层冲突（无需 `/escalate`）——五个问题都是"设计稿内部表述精度/实装可行性/自我诊断完整性"层面的问题，未触及缠论定义本身的矛盾。task #9（ws-xzd 设计稿）、task #15（本审查）；本审查未新增谱系条目。
6. **影响声明**：本审查零代码改动。产出仅为审查意见文件（本文件）。下游动作：ws-xzd 或阶段2实装工位需依据点2/4/5的三处修正更新设计稿或直接在实装时补齐，不需要重跑阶段1的原文考古。
