# Lead 并行调度与局部依赖规则（218号 + 275号谱系）

此规则优先级与 `no-workaround.md` 相同。

**compact 后效力声明**（407号/137号联合推论）：本规则中所有关于 Lead 行为的声明，在 autocompact 后效力为**零**。行为层恢复依赖 `session-start-ceremony.sh` 注入的角色边界锚点，不依赖本声明层的概率性引导。

## 核心命题

Lead 是 RTAS 的一环，不是 RTAS 之外的串行瓶颈。Lead 的一切操作遵守与工位相同的并行原则。

## 局部依赖原则（275号谱系）

**"附庸的附庸不是我的附庸"**——每个节点只管自己的直接依赖。全局 DAG 是局部依赖自然涌现的结果，不是事先规划的。

与操盘方法同构：主级别持仓不管次次级别的短差。次级别管次次级别，主级别只管次级别。每层只看自己的直接下级。

### 阻塞判定推论（652号并入）

局部依赖原则的适用域不限于 spawn 调度，同样覆盖**阻塞判定**。判断某个工作是否被某个矛盾/阻塞项阻塞时，问的是同一个局部依赖问题：**「这个工作依赖那个矛盾/阻塞项的输出吗？」不依赖 → 不阻塞。**

把一个局部矛盾放大为全局阻塞（"因为存在矛盾 X，所以工位 Y/Z/… 都停下"）违反 275 局部依赖——除非 Y/Z 的输入确实是 X 的输出。否则 Y/Z 与 X 各管各的直接依赖，X 的矛盾不向 Y/Z 传导。这与「把可推进误判为不可推进」（no-unnecessary-escalation 格式B blocked 条款，161号镜像）是同一误判的两面：局部放大为全局 = 不依赖的工作被误停。

可执行检查与 spawn 调度一致：阻塞不由"系统里存在矛盾"这个全局事实决定，而由被停工作与阻塞项之间是否存在直接数据依赖决定。无直接依赖的工作全部继续推进。

### 禁止的全局排序行为

1. **全局优先级排序**：Lead 不比较工位之间的 priority 来决定 spawn 顺序。ceremony_scan 输出中的 priority 字段是工位来源标记，不是全局排序依据
2. **越级管理子蜂群**：Lead 只 spawn 直接 teammate，不干预 teammate 内部的子蜂群拓扑
3. **中心化依赖调度**：Lead 不在内存中维护所有工位的依赖状态并按依赖序 spawn。无依赖的工位全部并行 spawn，有依赖的工位由前置工位完成后的回调触发
4. **全局工位评估**：Lead 不评估某个工位"不重要"或"可以后做"——工位是否有价值由工位自身和局部依赖关系决定

### ceremony_scan 输出的消费规则

1. ceremony_scan 输出 workstations 列表——Lead 全部并行 spawn（218号要求）
2. priority 字段是工位的**来源标记**（roadmap/session/structural/fallback），不产生执行排序效力
3. 工位之间的依赖关系不由 scan 输出决定——工位启动后自行检查前置条件（如文件是否存在、谱系是否已结算）
4. 资源受限时的降级：scan 输出中的 auto_verified 工位已跳过（VDW 机制），suspended 工位已过滤。剩余工位全部 spawn，如果并发上限不够，由平台排队处理——Lead 不做二次过滤

## 禁止的串行模式（RLHF 串行惯性）

1. **先总结再行动**：commit 后先输出总结段落，再决定下一步 → 总结嵌入格式A（143号已识别）
2. **逐个检查工位状态**：一个一个轮询工位 → 批量 TaskList + 批量处理
3. **等待测试完成再 commit**：Lead 自己跑 pytest 等结果 → spawn 测试工位，Lead 只消费结果
4. **先全关工位再开始下一轮**：等所有 shutdown 完成再 re-scan → shutdown 和 re-scan 可重叠
5. **等待确认再 re-scan**：commit/push 后等待确认 → 直接并行 re-scan

## 允许的串行（严格数据依赖）

仅以下操作允许串行，因为存在不可消除的数据依赖：

1. `git add → git commit → git push`：git 操作有严格顺序依赖
2. `ceremony_scan 输出 → spawn 工位`：工位列表依赖扫描结果
3. `TeamCreate → Task spawn`：spawn 依赖 team 存在

## 判断标准

在执行任何操作前，Lead 必须自检：
- 这个操作依赖前一个操作的输出吗？
- 如果不依赖 → 并行
- 如果依赖 → 串行，但必须能说出具体依赖什么数据

"方便"、"简单"、"习惯"不是串行的理由。
"优先级高"不是先 spawn 的理由——并行意味着同时 spawn。
