# 工位模型分配规则（编排者永久令 2026-07-04）

编排者三令合一（2026-07-04）：「不要所有agent都用fable，那样限额太高了，根据任务复杂度使用各种模型」+「结构工位和按需工位按照任务复杂度分配」+「包括结构工位，按需工位都要按照复杂度分配模型，这个要固化，永久化」。

**适用范围：全部工位类型无例外**——业务工位、结构工位（常设6个）、按需工位（13类）、workflow 内 agent。

## 分级表

| 档 | 模型 | 适用 |
|---|---|---|
| 机械 | `haiku` | 监控/待命型结构工位（meta-lead/quality-guard/meta-observer/topology-manager）、dag/索引追加、文件迁移、跑批执行、格式订正 |
| 常规 | `sonnet` | PDF/文档提取、谱系写入（genealogist）、代码验证跑测试（code-verifier）、codex/gemini 证据打包转发、文档措辞、对抗反驳票 |
| 高难 | `opus` | 代码静态核实（对齐审计）、主题综合、中高复杂度实装（有参照/有设计稿的代码件）、架构收口 |
| 最难 | `fable` | 终合成、全新统计/架构设计（无参照）、编排者显式点名场景 |

## 执行规则

1. Lead spawn 任何工位时**必须显式传 model 参数**（不允许静默继承主循环模型——继承=fable=最贵档）。
2. 判断在 Lead spawn 时做，不问编排者。拿不准时取低档，劣化再升。
3. 若工位交付质量因降档劣化（结果包缺要素、验收造假、测试漏跑），该类任务回升一档并在 memory `feedback_lead_auto_model_selection` 追记案例。
4. 每 workflow 至多 1 个 fable agent（终合成位），除非编排者显式扩容。

## 发生史

- 2026-07-02：编排者授权 Lead 自动选模型（节省开支）
- 2026-07-03：「写代码用 fable」（当时语境：单件高难实装）
- 2026-07-04：三令扩展至全工位并永久化，取代 07-03 单件口径；62-agent deep research（sonnet×46/opus×15/fable×1）获编排者事后确认为正确分配
