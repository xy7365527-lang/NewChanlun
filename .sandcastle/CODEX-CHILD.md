# Sandcastle 的 Codex 工蜂与交付封包

本入口绑定 #1456。它供当前 Codex 原生子代理管理单次 Sandcastle/Codex CLI 工蜂：主控派任务，管理子代理启动、等待或停止实际工蜂，再将结果回传。管理子代理 ID、父任务 ID 与外部 Codex session ID 分别记录；外部进程没有因此注册为 Codex App 的原生 child。

旧 `main.mts` 和常驻拾取队列仍是各自已有入口。本入口只处理显式指定的 ticket、工作区和版本，使用 Sandcastle 原生 Codex provider。#1448 的后续用户指令将执行与辅助复核工蜂指定为 `deepseek/deepseek-v4.1-flash`、`max`；模型常量在 `codex-router-runtime.ts`。根任务仍由 Astra 负责规划、架构、安全和最终验收。入口不经过 PrimeAgent，不改变全局模型、队列或合入设置。

本机需有 Python 3.11+、已运行的 Codex Router 和已登记 Flash max 的模型目录。入口只解析用户 `config.toml` 的 `openai_base_url` 与 `model_catalog_json`，再显式指定 `codex-router` provider；继续保留 `--ignore-user-config`，不加载其他用户插件、MCP 或模型设置。认证由 Codex 和 Router 各自沿用，不复制 API key。缺配置、错误模型目录或路由失败即停止，不自动换模型。

目前支持本机无秘密的 `http://127.0.0.1:<port>/v1` 地址。若 Router 改用含 caller capability 的认证路径，入口会在启动前拒绝，需适配安全的配置传递方式；不可删除认证路径来放行，也不可把 capability 写入命令或日志。`NewChanlun-sandcastle-host` 中已有的 Prime 队列改动属于另一入口，本次不覆盖或启动该队列。

## 单次运行

先为本票准备独立、干净且固定于目标提交的 `codex/*` 分支工作区，以及一份范围明确的提示文件。复核示例：

```bash
node --import tsx .sandcastle/codex-child.mts \
  --ticket 1456 \
  --parent-thread-id '<当前父任务 ID>' \
  --manager-agent-id '<实际管理子代理 ID>' \
  --checkout '/绝对路径/专用工作区' \
  --expected-head '<完整提交 SHA>' \
  --mode review \
  --prompt-file '/绝对路径/任务说明.md' \
  --output-dir '/绝对路径/尚不存在的结果目录'
```

管理子代理必须等到工蜂实际退出并取得结果，才能向父任务报告完成。非零退出、缺少最终结果、取消或版本异常都必须保留对应状态；不能把启动成功、拿到进程号或收到中途文本当作交付完成。主控停止任务时，管理者向运行入口传递停止信号，并确认自己启动的进程结束。

在当前 Codex 协作工具中，新管理工位用 `spawn_agent`；给已结束的工位分派下一项工作用 `followup_task`，并核实工位重新运行。`send_message` 只传递消息，不会启动已结束工位的新轮次；消息投递成功不能作为任务已开工的证据。

本入口的本地执行层使用 Sandcastle 的 `noSandbox`，内层通过 Codex `read-only` 或 `workspace-write` 执行。专用工作区固定任务对象，但这不是 Docker 隔离，也不限制所有宿主文件读取；提示中的任务范围仍须管理者审定。入口收紧 SDK 默认权限并禁用自动合并，不加载项目 `.sandcastle/.env`，拒绝带项目 `.codex/config.toml` 的工作区。认证沿用 Codex 官方已登录配置，保留现有网络代理路由；不能把认证内容或代理值写入提示、日志或报告。

每次输出目录必须尚不存在。入口写出 `state.json`、`events.jsonl`、原始输出与 `result.json`，后者绑定前后版本、实际退出状态和外部会话。运行完成与任务审查通过是两件事：即使外部工蜂正常退出，仍须读取结果中的发现并解决阻断项。取消或失败保留工作区与证据，管理者负责后续处置。

## 一次收齐交付材料

每片先收齐必要代码、验证和实体报告，再请求具体版本的合入。顺序如下：

1. 实施者提交本票外部行为及必要检查，列清实际改变的产品文件和需要入仓的报告。独立复核针对固定的产品字节；发现问题先修复，再补审真实变化面。
2. 报告、完整扫描分诊及引用的必要实体一并入 Git。独立复核输出应进入本次封包，不留到合入之后才发现漏件。
3. 使用交付预检核对实际 Git diff、文件摘要、报告是否在指定版本中、代码审查覆盖及已执行检查。检查失败或资料缺失先补齐；预检不代替实际运行或独立判断。
4. 纯报告尾部允许复用产品字节完全相同的已有编译、测试和审查证据；扫描必须保留实际运行的版本。报告导致扫描差异时明确披露，不能把旧扫描称为新版本已经通过。
5. 材料完整后，以具体 PR、版本、检查结果和任何仍需批准的例外一次请求合入；预检本身没有合入权限。
6. 合入后核实际主线提交与 CI，完成关票记录和本票工位处置。普通 CI 链接、状态、树或已有扫描结果是否相同，是机械交付收据；若出现新缺陷或需要新的实质分析，才进入新的修复与评审轮。

上述区分按内容而非文件名判断。新的测量、调研、安全分析或评审报告仍须遵守 `docs/agents/delivery-discipline.md` 第 6 条入仓；不能把报告改名“收据”来豁免。已有结果的机械核对也不必再次生成一份重复的实质报告，再为归档这份报告开启下一轮。

交付 manifest 放在仓外，绑定指定 Git 版本及产品/报告摘要，避免把 manifest 自身的最终 commit 写入自身而形成循环。它只描述可核对的交付材料；检查是否运行、扫描是否通过以及例外是否获批各有独立字段，不可互相替代。

预检命令：

```bash
node --import tsx .sandcastle/delivery-bundle.mts \
  '/绝对路径/本票工作区' '/绝对路径/仓外交付清单.json'
```

清单格式由 `delivery-bundle.ts` 的 `deliveryManifestSchema` 定义，测试内有完整样例。先列齐本票实际产出的报告，再填写 `productDiff`、`reports`、`reviews`、`checks` 和 `scan`。产品覆盖包含文件内容与权限；纯文档尾部可沿用连续版本的审查覆盖，旧扫描到最终版本之间的每项变化仍须列明。预检只能校验已声明证据的绑定，不能自行发现完全遗漏的仓外报告，也不证明报告内容的判断正确。

退出码 0 表示材料达到请求批准的条件；1 表示预检阻断（含清单字段不合法），2 表示调用参数、读取文件或 JSON 解析失败。输出分别区分 `READY_FOR_APPROVAL`、`READY_WITH_EXPLICIT_EXCEPTION` 和 `BLOCKED`，且始终保留 `mergeAuthorized: false`。例外披露就绪也不是例外已获批准。

本票改善派发、回流与封包，不替代 #1323 的业务实现，不裁资金或语义规则，不恢复暂停排程，不改变 main 的人工批准门。真实运行和验证结果由本票最终报告绑定；示例命令本身不构成已运行证据。
