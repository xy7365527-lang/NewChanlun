## 0. 结论摘要

1. **批量确认机制钉界**：`IncrSegments::append`（`segment.rs:565-737`）与其全量镜像
   `divide_segments_with_tail`（`segment.rs:372-434`）内部是**同一个不返回控制权的 `while` 循环**——
   一次调用（对应 parser 一个 bar 的推进）可以连续 `push` 多个 `Segment`（`segment.rs:712`），
   中间不经过任何外部可观测点。`active_segment_frontier`（`nest_lifecycle.rs:1648`）只在
   `append()` **返回之后**读一次 `l0.tail`，故批内除最后一个之外的所有段，从出生到确认之间不存在
   任何外部观测窗口。
2. **18 只的教义判定：本就不可见，非观测面缺口**。段 N+1 的 `start_index`（= 段 N 的确认端点 `k`）
   在段 N confirm 之前**不存在**——`OpenTail`（`tail.rs` 模块头）本身是"一个解析级别最多一个正在
   延伸的走势尾部"的单值设计，段 N+1 作为独立候选的身份直到段 N confirm 那一刻才被定义。若段 N+1
   自身的确认条件恰好由**已经在 strokes 数组里、无需等待未来新数据**的笔满足（#88 级联复活机制，
   `segment.rs:1004-1010` 测试实证"深回退"：一次 append 可回填、确认多段），则段 N+1 在其唯一可能
   存在的时刻就已经确认完毕——不是实现只在 bar 粒度采样错过了一个本可观测的中间态，是**该中间态
   在任何粒度下都不存在独立于其确认结果的"当下状态"**。这与 `tail.rs:11-14`"不预判最终结果"的
   裁定不冲突，反而是同一原则的推论：没有状态可保存，就没有可保存的状态。
3. **L2/L3 同构确认（#602 开工前必读）**：`detect_centers_windowed_resume`
   （`recursive_tower.rs:723-805`）内部 `while i + 2 < units.len()` 循环同样可以在**一次续扫**中
   `push` 多个 `Center`——不仅在普通单窗情形（`:758`，每次一个），**#148 升级重切分支
   （`:770-789`）显式循环 `k` 次、把一个成立窗口拆成 `k` 个子中枢一次性全部 push**，这与 L1 的
   `push(seg)` 批量模式是**同一个代码形状**（不返回控制权的内循环 + 一次调用多次 push）。L2 的
   "active" 语义（`active_l1_window_frontier`，#601 报告 §「新增本体」行）完全建立在
   `WindowScanCursor::resume_from`（"最后一个成立窗口"）之上——批内除最后一个窗口外的所有窗口，
   在 L2 层同样从未经历过"当下正在生长的候选"这一观测态。**结论：L3 的 frontier/队列模型面对同样
   的结构性缺口，且缺口的根不在观测容量（队列深度），在候选身份的定义时点本身**——#603 已用
   BTC 100k 实测证明"加大队列深度对 18 只零挽回"，本票钉出这不是数据集特例，是该批量确认机制的
   代数必然，L2/L3 会重复同一失败模式。
4. **可行观测面改造方向：没有能在不违反 090/E2E 裁定的前提下救回这 18 只的机制性方案**。唯一诚实
   的方向不是"改进观测"，是**在原因码层面新增一类**（本票建议命名 `chain_confirmed_no_pending_window`
   或同义），承认这些完成信号本就不可能有 earlier Live——这把 #597 destination 的验收条件
   （"要么有 earlier Live，要么有可审计原因码"）第二支路径坐实，而不是继续在第一支路径（观测面
   扩容）上加码。本票不替裁，§5 展开代价对比。

## 1. 批量确认机制读码钉界

### 1.1 单次 `append` 内的多段确认循环

`IncrSegments::append`（`segment.rs:565-737`，parser 每 bar 调用一次，接线见
`parser/mod.rs:277` `*incr_segments = prev_segments.append(&strokes, parse_config)`）：

```
668  let min_seg = config.seg_min_strokes as usize;
669  let mut seg_start = resume_seg_start;
...
681  while cursor < n {
...
693      feat.append(cursor, h, l, strokes);
694      let trig = feat.scan_trigger(strokes);
...
700      let Some(hit) = trig else { cursor += 1; continue; };
...
711      let seg = make_segment(strokes, seg_start, end_stroke, seg_dir);
712      new_segments.push(seg);          // ← 段确认点，本次调用内可命中任意次
713      end_indices.push(end_stroke);
714      seg_start = k;                    // ← 下一段的身份（start_index）此刻才被定义
715      seg_dir = opposite;
716      feat.reset(seg_dir);
717      cursor = k;                       // ← 不返回控制权，直接继续扫描已在 strokes 里的笔
718  }
719
720  let pending_start = if seg_start < n { Some(seg_start) } else { None };
```

`resume_seg_start`（重扫起点）取自"倒数第二段的 `seg_start`"（`:608-614`）——因为末段永远要重算
（`:560-563` 注释："末段（最后 confirmed 段）必须重算——新 bar 可能让段内更早的 SecondKindPending
触发复活…使段端回退到更早位置"）。这意味着**每次调用重扫的区间不是"只加了 1 笔"，而是"把上次的
末段整个撤销，从其起点开始，用当下完整已知的 strokes 数组重新走一遍状态机"**。

### 1.2 批量确认为何会发生：#88 级联复活机制

`feat.scan_trigger`（"第二特征序列分型"判据）需要看候选分型**之后**的笔才能判定分型是否成立
（第67/71课"假设转折点"：先试不合并，看是否触发分型——判定天然是回顾式的，需要"未来"笔已经存在
于数组里才能算）。多个 bar 里，`strokes[resume_seg_start..n]` 之间可能已经积累了若干笔——它们
"已经存在"，只是状态机在**上一次** `append` 调用里还没能确认它们（分型判据当时不成立）。当某一笔
新数据的到来打破了这个僵局（`feat.skipped_secondkind()`/`euf_rescan` 机制，`:695-699`、
`:721-727`），本次 `append` 从 `resume_seg_start` 重新走一遍——由于状态机内部循环**不在两次
`push` 之间让出控制权**，一旦第一处触发解除，`cursor = k` 之后立刻继续用**同一批已存在的笔**
去试探下一个触发点；如果下一段自身的确认条件恰好也已经被这批笔满足（不需要等待再来一个新 bar），
就在同一次调用里连续 `push`。

测试 `cascade_revival_bit_exact_incr_vs_full`（`segment.rs:1012-`）显式验证并断言这一现象存在
（"deep_rollback_seen"，即 `confirmed_len` 比"仅丢末段"更靠前——多段一次性重新确认），并证明增量
与全量结果 bit-exact——批量确认不是增量算法的 bug，是**全量算法本身**（`divide_segments_with_tail`
`:396-429` 同一循环形状）的固有行为，增量只是忠实复现它。

### 1.3 pending/tail 暴露面

`active_segment_frontier`（`nest_lifecycle.rs:1648-1692`）是唯一构造点，读的是 `l0.tail`——而
`l0.tail` 由 `parser/mod.rs` 在**每次 `parse_bar` 完成后**（即 `append()` 已经返回、批内所有确认
都已发生之后）从 `pending_start` 派生一次（`tail.rs` 模块头）。**观测粒度 = bar 粒度，且只在
批量循环全部跑完之后采样一次**——这是 #603 钉出"18 只从未入队"的直接技术原因：`ActiveFrontierQueue`
（`nest_lifecycle.rs:1590-1637`）无论深度多少，`observe()` 每 bar 只能拿到 `active_segment_frontier`
这**一个**返回值，批内被吃掉的中间段从未产生过一次独立的 `Some(frontier)` 供 `observe` 记录。

## 2. 18 只分桶与教义判定

### 2.1 与 #603 桶定义的关系

本票不重新量化——沿用 #603 §0/§1.1 表格的精确计数（18 只"C 段从未进过队列" / 17 只"占槽期 B 恒异于
完成 B" / 11 只"占槽期全 MISS"，46 合计，逐 as_of 清单见 #603 探针 `/tmp/wt603_*.py` 产物，本票
未复跑）。本节只回答票面任务2的核心问题："18 只的 C 在'行进中'是否存在任何可观测状态源"。

### 2.2 是否存在可观测状态源：无，且教义上必然无

**逐层论证**：

1. **身份的定义时点**：段 N+1 作为一个候选（拥有自己的 `start_index`）在 `OpenTail`/`PendingTail`
   的语义下，只有当它成为"当前正在延伸的走势尾部"时才存在（`tail.rs` 模块头："`Origin.ChanlunElements.OpenTail`
   是级别递归轴的尾部（一个解析级别**最多一个**正在延伸的走势尾部）"）。段 N+1 的 `start_index`
   在代数上等于段 N 的确认端点 `k`（`segment.rs:714`）——**段 N 不确认，段 N+1 连坐标都没有**，
   遑论"独立可观测的当下状态"。
2. **段 N+1 自身确认条件何时被满足**：`scan_trigger` 判据看候选分型之后的笔（第二特征序列扫描）。
   若这些"之后的笔"在段 N 确认那一刻**已经全部在 `strokes` 数组里**（#88 级联复活场景的字面
   条件），则从"段 N+1 拥有 `start_index`"到"段 N+1 满足确认条件"之间，**不需要任何新的市场数据
   到来**——两者是同一次状态机推进里，代数上紧邻的两步。不存在"段 N+1 先作为未定形态存在了一段
   时间，只是没被采样到"这回事：它的整个生命区间坍缩为零长度。
3. **与"不预判最终结果"裁定的关系**（`tail.rs:11-14`）：该裁定禁止的是"把当下状态强行归类为最终
   结果"——它假设**存在一个"当下状态"可供归类**。18 只的情形里，"当下状态"这个概念本身不适用，
   因为不存在一个"段 N+1 尚未确认、但已经拥有独立身份"的时刻。这不是对裁定的违反或例外，是裁定的
   适用范围之外——裁定管辖"有当下状态、不能预判其归宿"的情形，18 只是"当下状态与最终结果在时间轴
   上重合为一点"的情形，两者是不同的存在论范畴。

**边界条件（本判定何时会翻转）**：若未来实测发现 18 只里存在段 N+1 的确认笔**跨越了本次 append 调用
的 bar 边界**（即段 N+1 的部分确认笔是在段 N 确认**之后的某个后续 bar**才出现，而非全部在段 N 确认
那一刻已存在于 strokes 数组），则该实例不属于"生命区间坍缩为零"的范畴，而是一个真正的、本可以在
中间 bar 被观测到、但因为查询/账本口径原因被跳过的候选——这种情形才是真正的观测面缺口，需要与
"零长度生命区间"的情形分开处理。**本票未对 18 只逐只做这一区分**（需要重跑 #603 探针并追加"段 N+1
确认笔的 bar 跨度"字段，超出本票只读钉界范围），标注为**下游若采纳 §5 建议前必须先做的一次实测核验**。

## 3. L2/L3 同构影响

### 3.1 塔层的镜像循环

`detect_centers_windowed_resume`（`recursive_tower.rs:723-805`，L1→L2/L2→L3 通用，`build` 参数
按级别切换）：

```
738  while i + 2 < units.len() {
739      match build(&units[i], &units[i + 1], &units[i + 2]) {
740          Some(seed) => {
...
756              let emitted = if n < UPGRADE_TOTAL_SEGMENTS {
758                  out.push((c, (i, j - 1)));                    // ← 普通单窗：一次一个
...
761              } else {
                      // #148 升级重切：n≥9 段一次性拆成 k 个子中枢
770                  let k = n / 3;
771                  for t in 0..k {
...
775                      out.push((...));                          // ← 同一次调用内连续 push k 次
789                      metas.push(WinMeta { ... emitted: k });
                    }
790                  k
                  }
792              last_window = Some((i, emitted));
793              i = j;                                            // ← 不返回控制权，继续扫描
794          }
795          None => { i += 1; }
796      }
797  }
```

`WindowScanCursor::resume_from`（`recursive_tower.rs:394-405` 文档："最后一个成立窗口的起点"）与
`last_window_emitted`（"最后一个成立窗口产出的中枢数"）——这两个字段的设计**本身就承认了"一次续扫
可以产出多个中枢"**，但只把**最后一个**窗口标记为"frontier"（可回退重算），批内更早产出的窗口/
中枢立即视为已 sealed。这与 L1 `pending_start` 只保留"最后一段"的逻辑是**同一套协议**（对照
`segment.rs:560-563` 注释"末段必须重算"与 `recursive_tower.rs:380-388` 注释"末位中枢在未被
non-extension 单元终止前开放"——两处用几乎相同的语言描述同一约束）。

### 3.2 L2 "active" 语义继承同一盲区

#601 报告钉出 `active_l1_window_frontier`（`nest_lifecycle.rs:1749`）"从 `resume_from` 重跑与塔
逐字相同的窗口扫描…取末窗"——即 L2 的"当下行进中候选"同样只能是 `detect_centers_windowed_resume`
一次续扫里的**最后一个**产出，批内更早产出的（包括 #148 升级重切一次性吐出的 `k-1` 个非末位子中枢）
从出生到 sealed 之间同样不经过任何外部观测点。

**推论（#602 开工前必须知道）**：若 L3 的 frontier/队列模型沿用同一"读末窗"协议（#601 报告
"塔存储零改动"，`detect_centers_windowed_resume` 本身未变），则 L2 层必然存在与 L1 的 18 只同构的
一批"批量确认、从未单独 pending"的窗口/中枢——**这批窗口在 L3 层的完成信号覆盖率统计里会重演
与 #603 完全相同的证伪模式**：任何加大 L3 侧队列深度的方案，对这批窗口挽回量恒为 0，原因不是数据
集特例，是 `detect_centers_windowed_resume` 循环形状的代数必然（§0-3 已论证）。

### 3.3 认识论等级标注

本节结论（§3.1-3.2）为 **L0**（纯代数/定义——从 `detect_centers_windowed_resume` 与
`active_l1_window_frontier` 的代码结构直接推导，未跑真实数据验证 L2 层批量确认在 BTC 100k 上的
实际发生频次）。是否有 BTC 100k 上真实出现过 `last_window_emitted > 1`（含普通多窗紧邻续扫与
#148 升级重切两种子情形）的窗口、以及它们在 L2 完成信号覆盖率统计里贡献了多少缺口，**未经 L2 实测
验证**——按 `formalization-validity-domain` 规则标注，#602 开工前若要依赖本节推论定量规划验收目标
（而非仅作定性风险预警），需要先对既有 L2 dump 跑一次与 #603 `/tmp/wt603_final.py` 同构的探针
（判据：某完成信号的活跃期内，`WindowScanCursor.last_window_emitted` 是否 >1 且该完成信号对应
非末位子窗）。

## 4. 教义边界小结（对照 `tail.rs:11-14`）

| 情形 | 是否有可观测当下状态 | 教义判定 |
|---|---|---|
| 段 N+1 的确认笔全部在段 N 确认时已存在于 strokes（#88 级联复活字面条件） | 无——生命区间坍缩为零长度 | **裁定管辖范围外**（不存在"当下状态"可供预判或不预判） |
| 段 N+1 的部分确认笔在段 N 确认**之后**的 bar 才出现 | 有——真实存在一个"段 N+1 已有 start_index、尚未确认"的窗口 | **裁定管辖范围内**，且若该窗口未被观测账本记录，是真实的观测面缺口 |
| L2/L3 批内非末位窗口/中枢（`last_window_emitted>1` 情形） | 与段情形同构，取决于该窗口自身确认所需信息是否已在续扫触发时全部就位 | 同上，需逐窗判断，本票未做 L2 实测区分 |

18 只的实际归属（第一行 vs 第二行）**本票未逐只核验**（§2.2 边界条件已标注），是 §5 建议的前置
核验步骤。

## 5. 可行的观测面改造方向与代价（不替裁）

### 方向A：接受不可观测，新增原因码（本票推荐起点，代价最低）

对 §2.2 第一行情形（生命区间坍缩为零）：新增诊断/账本原因码（如
`chain_confirmed_no_pending_window`），在完成信号覆盖率统计里把这批候选从"应该有 earlier Live
但缺失"重分类为"结构上不存在 earlier Live"——这不改变任何机制、任何真值路径，只改变统计口径的
诚实性（同 #603 §0 归因表的桶已经在做的事，本票建议把它从"研究报告里的桶"提升为"账本/诊断层的
正式原因码"）。

**代价**：低——只需在 `nest_lifecycle.rs` 的诊断/统计层新增一个分类判据（判据：`bridge_identity`
匹配到的完成信号，其 `seg_c_full` 在 confirmed segments 里的确认 bar 与其**前一个**链式段
（`seg_a` 对应段的确认 bar，或更精确地——同一 `append()` 调用内 `end_indices` 相邻两项）是否
相同）。**风险**：判据本身需要访问"哪几段是同一次 `append` 调用里一起确认的"这一信息——当前
`IncrSegments`/`confirmed_len` 不显式记录"本轮 push 了几段"，需要新增一个字段（类比
`WindowScanCursor::last_window_emitted` 在塔层已经在做的事——L1 段层目前没有对应字段）。

### 方向B：细粒度轮询（不建议，代价高且价值存疑）

在 `append()` 内循环每次 `push` 后都采样一次 `tail` 状态，暴露"批内中间快照"。

**为何不建议**：§2.2 已论证，对于确认笔全部已在同一 `strokes` 快照里就位的情形（本票估计是 18 只
的主体，但未逐只核验），批内中间快照与最终快照在**同一个 `as_of`/bar 时刻**——细粒度轮询不会产生
一个"更早的 bar"，只会在同一个 `observed_at` 上产生一条冗余记录，对 `earlier Live
(observed_at < completion_as_of)` 判据**没有任何帮助**（覆盖率判据是 bar 粒度的，不是调用粒度的）。
除非把整个观测时钟从 bar 级细化到"parser 内部状态机步进"级——这是对 `090` 登记的 bar 粒度观测协议
的根本性重构，影响面覆盖 L1/L2/L3 全部 provider 与账本，且价值只覆盖§2.2 边界条件里"确认笔跨 bar
才出现"的第二行情形（真实缺口），对第一行情形（本就零长度）无效。**建议：不投入，除非 §2.2 边界
条件核验后发现第二行情形占比显著。**

### 方向C：重新定义候选发现口径（#603 §7 遗留1(a) 原始建议，本票订正其可行性）

#603 遗留把这 18 只描述为"要救只能改 provider 的候选发现口径（而非观测容量）"——本票分析后认为
这一表述**需要精确化**：对 §2.2 第一行情形，"候选发现口径"同样救不了，因为救的前提是"存在一个
更早的、独立于确认结果的候选状态可供发现"，而这个状态根本不存在。方向C 只对§2.2 第二行情形
（真实跨 bar 缺口）有意义——如果核验后发现 18 只里有相当比例属于第二行，需要的不是"候选发现口径"
而是"把 `PendingTail` 从单值改为向量"（允许 parser 同时暴露"当前段"+"下一段的部分已知信息"）——
这是对 `OpenTail` 单值裁定本身的修订，教义分量极重（`tail.rs` 模块头明确"一个解析级别最多一个
正在延伸的走势尾部"是对齐 Origin `OpenTail` 五构造子的忠实移植），**建议上呈编排者裁定而非自行
实装**，本票不替裁。

### 推荐顺序（不替裁）

1. 先做 §2.2 边界条件核验（复跑 #603 探针 + 新增"该完成信号的链式前段是否同批确认"判据），
   分清 18 只里第一行/第二行的真实比例；
2. 若第一行占绝大多数（本票基于代码结构的先验判断）：走方向A（原因码），成本最低，教义最干净；
3. 若第二行占非零且非可忽略比例：该子集需要编排者对方向C（`OpenTail` 单值裁定修订）表态，
   不建议在无裁定的情况下自行改动 `PendingTail` 的向量化；
4. 方向B（细粒度轮询）在两种情形下都不建议。
5. **对 L2/L3（#602）**：在实装前先做 §3.3 的 L2 实测核验，量化 `last_window_emitted>1` 在
   BTC 100k 上的真实发生频次与其对完成信号覆盖率的贡献——避免重演 #603 的"未经机制验证即采纳
   队列深度方案"教训（#599 归因失败的直接原因）。

## 6. 结果包六要素

1. **结论**：18 只批量确认段从未进入 pending 槽的根因是 `IncrSegments::append`/
   `divide_segments_with_tail` 内部单次调用可连续 `push` 多段（`segment.rs:681-718`，#88 级联
   复活机制实证），`active_segment_frontier`/`ActiveFrontierQueue` 只在批量循环全部跑完后采样
   一次，批内非末位段无观测窗口。教义判定：对确认笔全部已在同批 strokes 快照就位的子情形（本票
   先验判断为主体），这不是观测面缺口，是候选身份定义时点与确认条件满足时点代数重合，`tail.rs`
   "不预判最终结果"裁定不适用（无当下状态可供预判）；对确认笔跨 bar 才出现的子情形（若存在），
   才是真实缺口。L2/L3 塔层 `detect_centers_windowed_resume` 存在结构同构的批量 push 循环
   （`recursive_tower.rs:738-799`，含 #148 升级重切一次 push k 个子中枢），#602 开工前须做
   L2 实测核验，不能假设队列深度方案在塔层比 L1 更有效。
2. **定义依据**：`segment.rs:565-737`（`IncrSegments::append`）、`:372-434`
   （`divide_segments_with_tail`）、`:1004-1010`+测试体（#88 级联复活实证）；`nest_lifecycle.rs:1648-1692`
   （`active_segment_frontier` 唯一构造点）、`:1590-1637`（`ActiveFrontierQueue`）；
   `recursive_tower.rs:723-805`（`detect_centers_windowed_resume`）、`:394-405`
   （`WindowScanCursor` 文档）；`tail.rs` 模块头（`OpenTail` 单值裁定）与 `:11-14`
   （"不预判最终结果"）；#601 报告（`active_l1_window_frontier` 定义与"塔存储零改动"）；
   #603 报告 §0/§1.1（18/17/11 三桶精确计数）。
3. **边界条件**：(a) §2.2 教义判定依赖"18 只主体属于确认笔同批就位"这一先验判断，**未逐只核验**——
   若核验后发现显著比例属于跨 bar 情形，§4/§5 的推荐顺序需要调整（方向A 不再是唯一起点）；
   (b) §3 的 L2/L3 同构结论是 L0（代数/定义级），未经 BTC 100k 实测验证塔层批量 push 的真实发生
   频次，#602 若要据此定量规划验收目标须先做 §3.3 建议的核验；(c) 若编排者裁定 `OpenTail` 单值
   约束可修订（方向C），本票 §5 的成本判断需要重算。
4. **下游推论**：#602（L3 实装）开工前不应假设"L1 的 18 只是数据集特例"或"塔层队列深度方案会
   比 L1 更有效"——两者是同一代数机制的两个实例，塔层的 `last_window_emitted>1` 是天然存在的
