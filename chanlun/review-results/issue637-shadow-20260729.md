## 结论：**FAIL**

发现计数：**HIGH 5 / MEDIUM 4 / LOW 4**

三条硬阻断，且互相独立（修任一条不解另两条）：

1. **票面范围第 3 条「生产调用点 ≥1（grep 可证）」未满足**——`consume_death_certificate` 的全部调用点都在 `#[cfg(test)]` 内（HIGH-4）。登记表却已被改成「已接线（#637）」、计数 0/3→1/3，构成不实登记。
2. **迟到证明的处置与票面逐字要求、与在案裁定 ADR-0001 补充十一/#583 完全相反**——票面写「不问迟到——054:60 延迟合法、#583 在案」，实现把迟到证明拒为 `Err`，并用测试把这个行为固化成期望（HIGH-1）。
3. **判同在真实数据上恒不命中**——比较的两个量纲不同（tick 整数 vs 原始价格浮点），不是精度问题（HIGH-3）。端到端测试用手搓字面量恰好让两者数值相等，正好掩盖了这一点（MEDIUM-2）。

这三项分别落在「有没有接上」「接上后语义对不对」「接上后判据命不命中」三个层面，不是收尾修补能覆盖的范围，故不给 CONDITIONAL。

**PASS 的部分（如实登记）**：指纹独立复跑与报告完全一致（2495/0/138）；flaky 测试的定性属实；「不动买卖点账本侧」的禁区遵守到位（`retrace_ledger` 逻辑零改动）；fail-loud 用 `Result` 而非 `bool`/`Option` 的形状选择正确；报告对「零生产调用点」「四条边→三条边缺口」两项的自我登记是诚实的（虽与它自己改的 doc 矛盾）。

## 发现列表

### HIGH-1　迟到证明被拒 = 票面逐字要求与在案裁定的反向实现

**证据（实现）**：`rust/src/trading/center_book.rs:367-374`——判同要求锚必须是**当前** `last`：

```rust
let matched = self.last[ladder].is_some_and(|lc| { lc.seg_start == anchor && ... });
if !matched { return Err(DeathCertificateError::NoMatchingCenter { ladder, anchor }); }
```

锚一旦被新中枢取代（`last` 前移），证明即被拒。`center_book.rs:687-701` 的测试
`late_certificate_after_center_superseded_fails_loud` 把这个行为**固化为期望**。

**证据（票面）**：范围节逐字「输入 `CenterDeathCertificate` → 对锚定中枢（四条边判同）登记 Broken」，
Question 节逐字「不问迟到——054:60 延迟合法、#583 在案」。

**证据（在案裁定）**：
- `docs/adr/0001-graded-exit-and-shortdiff-doctrine.md:221`（补充十一）：「**Superseded（被取代）不是中枢的死**——只是「在场中枢换了一个」…原中枢区间为历史事实（ZG/ZD 冻结），**其三类点判据在死后继续适用**（回抽回不回原区间是客观事实）」
- 同文件补充十四（`:252`）出口全集：「**破坏**（三类买卖点，定理三充要条件，唯一终结）/ **更替**（Superseded…**非破坏**）」
- 同文件 #583「讣告抢跑定性」：「wf8 漏发 58 条 = 如实形态…**迟到但都到 31（全 Broken，054:60 为原文预期）**」

即：被取代后迟到抵达的死亡证明，在案口径是**应当登记 Broken**（wf8 实测 31 条正是这样落的），
本实现把它判成失败。票面写的「判同失败（无此中枢/已死）」中的「无此中枢」指从未存在过的锚，
不是「曾经存在、已被更替」——把更替读成「无此中枢」正是补充十四点名禁止的「把更替登记成破坏/非破坏之外的第三态」的镜像错误。

**失败场景**：BSP 事件流推进到新中枢 `cs=20` 后，`retrace_ledger` 才对旧中枢 `cs=10` 落锤开出证明
（054:60 延迟合法 ⟹ 这是**常态**而非边缘）。当前实现返回 `Err(NoMatchingCenter)`，旧中枢的 Broken 永不登记，
其名下挂起按补充十一/十三应「延续到原中枢三类点清算」却等不到清算事件。

**结构上并非不可支持**：`dead` 是 `HashSet<i64>`（`center_book.rs:41`），插入不需要该锚在 `last` 在场。
实现选择了要求 `last` 判同，是设计选择而非结构限制。

### HIGH-2　`KilledByOtherCause` 是伪概念，且真实接线后会成为主导返回值

**证据**：`CenterBook.dead` 的唯一写入路径（本票之前）是 `center_book.rs:123-141`：

```rust
if ev.confirmed && ev.class.kind() == BspKind::Type3 { ... dead.insert(cs); ... }
```

即 `dead` 中的每一个元素**都是三类点杀的**。而证明的开具条件同样是三类点判胜
（`retrace_ledger/book.rs:649-663`：`death_certificate` 只从 `LedgerState::Confirmed` 取，
`certificate_of` 由 Confirmed 档现开）。

**教义**：18 课定理三原文（`docs/chanlun/text/chan99/0010-第八节 走势中枢.md:13`）：
「某级别"走势中枢"的终结，**当且仅当**一个次级别走势离开该"走势中枢"后，其后的次级别回抽走势不重新回到该"走势中枢"内。」
ADR-0001:252 复述为「三类买卖点，定理三**充要条件**，唯一终结」。

充要 ⟹ 两条路径杀同一中枢是**同一教义事件的两次观测**（一致性确认），不是「两条路径都想杀同一中枢」的分歧。
`center_book.rs:364-366` 把它当作 `Err`：

```rust
if self.is_dead(ladder, anchor) { return Err(DeathCertificateError::KilledByOtherCause { ladder, anchor }); }
```

错误码名「其他死因」在本账中**不存在对应的现实**——`dead` 里没有非三类点来源的元素。

**失败场景**：054:60 延迟合法 ⟹ 证明恒后于 BSP 事件流抵达。真实接线后，凡是 `CenterBook` 已从
BSP 流自行观测到 confirmed Type3 的中枢（即绝大多数），证明抵达时一律返回 `Err(KilledByOtherCause)`。
这条「接线」在生产上的主导返回值将是错误，而非它声称要做的 Broken 登记。

### HIGH-3　判同的价格边比较是量纲错配，真实数据上恒不命中

**证据**：`center_book.rs:369-370`：

```rust
lc.zd == cert.center.zd as f64 && lc.zg == cert.center.zg as f64
```

- 左侧 `LiveCenter.zd/zg: f64` 的来源：`lib.rs:1602-1619` 从 Python 侧透传的**原始价格浮点**
  （同处 `close` 也是原始价，`lib.rs:1583`），中途无任何量化。
- 右侧 `CenterFrame.zd/zg: Tick`，`Tick = i64`（`src/theta_v0/types.rs:15`），由
  `quantize(price, tick_size) = (price / tick_size).round()`（`types.rs:24`）产出——**tick 计数，不是价格**。

两者相差一个 `1/tick_size` 因子。除非 `tick_size == 1.0`，`zd as f64 == lc.zd` 恒为 false。
例：`tick_size = 0.01`、价格 `43250.50` ⟹ `Tick = 4325050`，与 `43250.50` 比较恒不等。

**这不是「量化精度舍入的假阴性」**（报告 §八.1 的定性），而是单位错配，误差量级是 `1/tick_size` 倍，
不是半个 tick。同样的问题也适用于 `start_index as i64 == lc.seg_start`：前者是 theta_v0 的
CompletedMove/段索引（补充十五「段 N 终点索引 = 段 N+1 起点索引」的坐标系），后者是 legacy
Python-parity 引擎自己的段起点标识；两套段序列由不同引擎独立切分，无对齐依据（本票 doc 亦承认
「仓内当前无换算表」，`center_book.rs:344-345`）。

**失败场景**：接线后每一张真实证明都返回 `Err(NoMatchingCenter)`——与 HIGH-2 合起来，
该入口在生产上没有任何输入能走到 `Ok(Broken)` 分支。

### HIGH-5　cert 杀路径不守恒：ingest 杀路径的三项收尾动作全部缺失

`consume_death_certificate`（`center_book.rs:375-378`）只做三件事：插 `dead`、插 `broken_by_certificate`、`version += 1`。
对照 `ingest` 的 confirmed Type3 杀路径（`:123-149`），缺三项：

| 状态 | ingest 杀路径 | cert 杀路径 | 后果 |
|---|---|---|---|
| `pending_departure` | `:147-149` 显式清除该锚的窗口 | **不清** | H1 禁令窗口滞留 |
| `dead_down` | `:126-131` Sell 侧置位 | **不置**（cert 无 side 字段） | 方向判据永远读成「向上终结」 |
| `frozen` | `:142-144` hard_type3 && Buy 置位 | **不置** | 冻结语义缺失 |

**时序演算（票面点名的「candidate 离开段窗口置位在先、cert 杀在后」）**：

1. `ingest(2, [Sell1 confirmed, cs=10])` → `last=Some(10)`
2. `ingest(2, [Buy3 candidate, cs=10])` → `:196-201` 置 `pending_departure=Some((10, Buy))`、`cf_windows+=1`、`pending_excursion=NEG_INFINITY`
3. `consume_death_certificate(2, cert(10,…))` → `dead={10}`，但 `last` 仍是 `Some(10)`、`pending_departure` 仍是 `Some((10, Buy))`
4. `has_pending_departure(2)` 仍返回 **true** —— 中枢已死，禁令窗口仍挂着
5. 后续 `negate_pending_departure(2, c)`（`:220-250`）**不查 `is_dead`**：`debug_assert` 通过（`lc.seg_start == cs == 10`），Buy 侧照算 excursion，价格否定时照调 `push_up_strength(2, 10, …)`

第 5 步正是 `h2_death_dismissed_window_not_recorded`（`:553-563`）明确断言**不应发生**的事——
该测试固化「中枢死亡解除的窗口不推入力度历史（离开段终结了中枢，不是『继续是中枢震荡』的样本）」。
cert 杀路径绕过了这条不变量，污染 H2 力度历史。

补充：第 3 步后，`ingest` 收到的所有 `cs=10` 事件都会被 `:150` 的 `elif !dead.contains(&cs)` 守卫跳过，
`last` 会一直停在死锚 10 直到出现新 `cs`——期间窗口只能由价格否定解除（并顺带污染 H2）。

**`dead_down` 缺失的交易后果最实质**：`is_dead_down` 的消费方全在生产决策路径上——
`level_operating_unit.rs:1193`、`unified_osc.rs:304`、`axiom_voice.rs:301` 与 `:422`。
cert 杀的中枢恒 `is_dead_down == false`，等价于「三买向上终结」⟹ 按 ADR-0001 补充十一「三买 → 回补」处理。
若该证明实际来自三卖（`RetraceSide::Sell`），正确处置是「三卖 → 不回补、核销为未闭合减出」——方向读反会造成错误回补。
信息在结构层就丢了：`ThirdPointPack` 有 `side` 字段（`book.rs:118`），`CenterDeathCertificate`（`book.rs:98-103`）**没有**。
报告 §八.3 只提到「不产 `CenterEvent`」，未登记 `dead_down` 这条更实质的后果。

`has_pending_departure` / `up_strength_verdict` 的消费方同样在生产路径上
（`level_operating_unit.rs:1346 :1360 :1363`、`unified_osc.rs:198`）。

### MEDIUM-1　幂等键是锚而非证明，两张矛盾证明会被静默吞掉

**证据**：`center_book.rs:376` 只把 `anchor`（`start_index as i64`）存入 `broken_by_certificate`，
不存证明内容；`:361-363` 的幂等判据也只查 anchor。

**可构造反例**：
```
consume(2, cert{start_index:10, zd:1,   zg:2,   issued:5})  → Ok(Broken)
consume(2, cert{start_index:10, zd:999, zg:999, issued:0})  → Ok(AlreadyBroken)   // 零动作，静默
```
第二张证明的价格边与第一张矛盾（同锚不同框 = 上游引擎改口，正是 `retrace_ledger` 自己用
`NotConstitutedReason::CenterRebased` 处理的形态），却被当成「同一证明重复消费」静默吞掉。

票面幂等条款逐字：「**同一证明**重复消费零动作」。实现落成的是「**同一锚**的任意证明零动作」，
范围比票面宽，且与本票自称的 fail-loud 精神（「不静默吞掉分歧信号」，`:350-352`）自相矛盾。

### MEDIUM-2　端到端测试不端到端，且手搓值恰好掩盖 HIGH-3

**证据**：`center_book.rs:612-617` 的夹具 `cert()` 直接手搓 `CenterFrame { zd, zg, start_index, end_index }` 字面量；
`death_certificate_registers_broken_end_to_end`（`:619-634`）用 `cert(10, 1, 2, 99)`。

「产证明」指经 `RetraceLedger::death_certificate()` / `ThirdPointPack::death_certificate` 真实开具，
而非构造字面量。当前测试只覆盖 `consume_death_certificate` 单函数，是单元测试。

**更要紧的是掩盖效应**：手搓的 `zd=1, zg=2`（Tick）与 `ingest` 喂的 `1.0, 2.0`（价格）恰好数值相等，

HIGH-3 的量纲错配会当场暴露为红。测试的构造方式正好绕开了本票最核心的风险点。

### MEDIUM-4　证明无级别信息，`ladder` 全凭调用方传，无 level↔ladder 映射依据

**证据**：`CenterDeathCertificate`（`book.rs:98-103`）只有 `center: CenterFrame` + `issued_as_of`，
无级别/层字段；`consume_death_certificate(&mut self, ladder: usize, …)`（`:355-358`）的 `ladder` 完全由调用方决定，

**可构造反例**：同一张证明依次喂给 `ladder=2` 与 `ladder=3`，若两层恰好各有 `seg_start=10`、`zd/zg` 相同的中枢，

theta_v0 塔的 `level` 与 trading 的 `ladder`（`MAX_LADDER = 11`，`types.rs:26`）之间仓内无既有映射
（grep：`src/trading/` 下引用 `theta_v0` 的只有本票新增的 `center_book.rs:15` 一处 `use`）。
这是「接线」在真实场景落不了地的第二个结构原因，报告 §八完全未登记。

### LOW-1　`KilledByOtherCause` 判定先于判同，不校验价格边，错误码可能误导

`:364` 的 `is_dead(ladder, anchor)` 只比 anchor 数值，不校验 `zd/zg`。一张锚定不同中枢、
但 `start_index` 数值恰好撞上本层某个历史已死中枢 `seg_start` 的证明，会得到 `KilledByOtherCause`
而不是更准确的 `NoMatchingCenter`。判定次序（幂等 → 已死 → 判同）本身合理，但「已死」分支缺边校验。

### LOW-2　cert 杀不可观测：无查询接口、不产 `CenterEvent`

`broken_by_certificate`（`:49`）私有且无 getter，外部无法区分某中枢是 cert 杀还是 ingest 杀；
`consume_death_certificate` 不写 `events_out`，`CenterEvent` 的既有消费者
（`ingest` docstring `:98` 点名的 T4b 加码 / FatigueGate 清空路径(2) / 域腿解冻观测）看不到这次死亡。
报告 §八.3 已如实登记此项，故仅记 LOW。

### LOW-3　`ladder >= MAX_LADDER` 直接索引 panic

`:361` `self.broken_by_certificate[ladder]` 等四处均为裸索引。与 `ingest` 同惯例（既有代码同形），
非本票新引入，但新入口的调用方将来自 theta_v0 侧（级别口径不同，见 MEDIUM-4），越界风险高于既有调用面。

### LOW-4　报告 §七 关于 rustfmt 的声明不实

### 4. 判同映射的 soundness

- **`start_index as i64 ↔ seg_start`**：`CenterFrame::anchor()`（`retrace_ledger/mod.rs:145-150`）确实以
  `start_index` 为 per-中枢路由锚，`CenterBook` 也确实以 `seg_start` 为 per-ladder 中枢身份键——**字段角色对应成立**。
  但两者是**两套引擎各自切分的段序列**的索引：theta_v0 侧是 CompletedMove 索引（补充十五共享枢轴坐标系，
  `end_index <= seg_start` 含等值），trading 侧是 legacy Python-parity 引擎透传的 `cs`（`lib.rs:1602`）。
  **无实质对齐依据**——本票 doc 亦承认「仓内当前无换算表」（`:344-345`）。
- **`Tick as f64` 位精确比较**：**量纲错配，真实数据恒不命中**（HIGH-3）。不是精度问题。
- **`end_index` 不参与**：doc 已如实登记（`:342-344`）。在当前判同已恒不命中的前提下，这一项相对次要；
  但注意 ADR-0001 补充十三「中枢 = 四条边的框…三类点判据锚在框的**右边**」——`end_index` 恰是判据锚所在的那条边，
  它不参与判同意味着无法区分「同起点、不同完成时点」的两代框。
- **结论**：会**恒不命中**（价格边量纲错配即足以保证），不会误命中。
