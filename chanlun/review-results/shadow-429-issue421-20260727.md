### 3.2 Spec 轴

#### HIGH — P-H1：生产产物坍缩为零寿命终态快照，不是完整生命周期

完成事件先被收集为 `completed_keys`；同 prefix 的活窗命中后直接 `continue`，随后只把完成事件
放进观察批次（`ce2038b779:rust/src/theta_v0/classifier/nest_lifecycle.rs:1105-1153`）。
`channel_switches` 因“同刻两通道碰撞”即加一，并不要求 book 中已有先前活身份
（同文件 `:1133-1140`）。

生产证据：

- `/tmp/wt421-post-100k-p123.stderr:5`：
  `triggers=1135 live_windows=77825 completion_events=119988 channel_switches=77825
  extension_suppressed=0 ... completion_force_unavailable=0`；
- 逐行复核 `/tmp/wt421-post-100k-lifecycle.dump`：1135/1135 个 FEED 行均
  `live_windows == channel_switches`；
- 按身份配对 `Observed` 与 `StructureCompleted`：213/213 同 `as_of`，
  `positive_lifetime=0`；原始例见该 dump `:385-388`；
- 终局为 `Confirmed=121`、`NeverConstituted=92`、`ForceOvertake=0`，
  `Supersedes=0`。

20k 同构：36/36 身份零寿命，`Confirmed=22`、`NeverConstituted=14`、
`ForceOvertake=0`。

这不满足 #421 Problem/Solution 的“产生、观察、坐实或被否证完整生命史”，也使 #426
“两类否证终局在真实数据上均可触发”未满足。自查档其实已记录
`live_windows=channel_switches`、`extension_suppressed=0`
（`issue421-acceptance-selfcheck-20260727.md:117-127`），但只把它归入双终局“部分”，
漏判了完整生命周期本身。

#### HIGH — P-H2：#428 审计在生产接缝构造性不可达，0% 不是实测发生率

生产出口的两类观察构造固定为：

- completion：`LifecycleObservation::event(..., true)`
  （`rust/src/theta_v0/classifier/nest_lifecycle.rs:1105-1110`）；
- live：`LifecycleObservation::pan_live(..., false)`
  （同文件 `:1122-1131`）。

而力度求值规定 Event 恒为 `Verified(event.divergence_confirmed)`，只有 PanLive 才可能
`Unavailable`（同文件 `:443-465`）。所以生产出口不存在
`structure_completed == true ∧ force == Unavailable` 的构造路径。

F9 直接绕过 `feed_replay_prefix`，手工构造
`PanLive(..., true)`（同文件 `:2948-2954`）。红日志只是缺类型/方法的编译红
（`/tmp/wt421-f9-red.log:2,171`），绿日志证明直接 API 可记账
（`/tmp/wt421-f9-green.log:436`），不证明生产接缝可达。

发生率分母也不是唯一完成信号：每个 trigger 把所有 run 的历史 provider events 再次
`flat_map`（`rust/src/bin/p123_fast_replay.rs:1257-1260`），stats 直接累计 vector 长度
（`nest_lifecycle.rs:1105-1113`）。100k 的 `119988` 对应唯一终态身份仅 `213`
（约 563 倍重复观察），不可作为 #428 发生率分母。

#### HIGH — P-H3：每 trigger 新增全量 provider 重算，违反 US15 与稀疏驱动

每次 lifecycle trigger 都调用 `feed_lifecycle_trigger`
（`rust/src/bin/p123_fast_replay.rs:869-881`）；后者调用
`collect_lifecycle_runs`，无 dirty/cache 条件地遍历全部 level×run，重新执行
projection → decompose → assemble_level_view → provider
（同文件 `:1175-1233,1247-1260`）。

这与 #421 US15“接线不引入额外的全量重算成本”及“只跟随重估节拍、不改稀疏驱动”冲突。
单次计时仅作佐证：100k pre/post `prefix_s=0.881 → 1.412`（+60.3%，
`/tmp/wt421-pre-100k-p123.stderr:1`、
`/tmp/wt421-post-100k-p123.stderr:1`）；静态调用链本身已足以判定新增全量重算。

未发现新增第二套力度谓词或证书真值水线；问题是同一 provider 语义被另起一条全量执行管线，
而非判据 fork。未发现其他 scope creep。
