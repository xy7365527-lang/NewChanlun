## 问题

> `consume_at` 是怎么运行的？谁调用它，调用链每一层在干什么，数据怎么流？

## Overview

`consume_at`（`rust/src/theta_v0/classifier/consume_at.rs:128`）是 E2E-O 簿装配模块
（`e2eo.rs`）里"消费"阶段的核心纯函数：把一条已闭合（`Closed`）的谱系证书
（`TowerChainCertificate`）按策略（`ManagedBspPolicy`）投影成受管 BSP 创建
（`ManagedBspCreation`）与链接（`BspLink`），供下游 WireV1 薄调用方读取。它本身不做 I/O、
不查簿，是"推进"（`advance`，增量维护 `AliveIndex`/`PathDag`/`event_to_bsp`）与"消费"两阶段
里纯函数化的那一半。

## Key Concepts

- **`TowerChainCertificate`**（`chain_cert.rs`）：谱系证书，含 `status`（`ChainStatus::Closed`
  等）、`closed_at`、`key`、`nodes`（`ChainNodeTrace`，各自 `key`/`status`）。
- **`ManagedBspPolicy` / rule**：消费策略，每条 rule 投影到 `(policy_id, rule_id, slot)` 三元组。
- **`event_to_bsp: HashMap<CandidateKey, BspStructuralKey>`**：调用方（`E2eOAssembly::advance`）
  预解析好的"候选事件 → BSP"映射，`consume_at` 只读不查簿（#982 裁定 A）。
- **`prior_bsp_by_key` / `prior_links_by_key`**：跨调用累积的幂等状态，保证同一 `BspKey` 只创建
  一次、`LinkKey` 只写一次。
- **`ConsumeError`** 四分支：`NoConsumption` / `LateAuthorization` / `InvalidPolicy` /
  `InconsistentState`，按此顺序先到先返回（函数内注释逐条写明判据）。

## How It Works（调用链 + 数据流）

```
E2eOAssembly::consume(&mut self, policy)         [e2eo.rs:~148]
  1. self.chain_book.heads() 取全部证书头
     .filter(status==Closed && closed_at.is_some())
     .sort_by_key((closed_at, key))               # 去随机化：同 as_of 按 key 升序
  2. for certificate in closed:
       as_of = certificate.closed_at
       consume_at(as_of, &self.prior_bsp, &self.prior_links,
                   certificate, policy, &self.event_to_bsp)   [consume_at.rs:128]
         ├─ 1. NoConsumption：status != Closed → Err（consume() 已过滤，理论不可达）
         ├─ 2. LateAuthorization：closed_at > as_of → Err（同 as_of 升序保证不可达）
         ├─ 3. InvalidPolicy：rules 为空，或两条 rule 投影同一 (policy_id,rule_id,slot) → Err
         ├─ 4. InconsistentState：prior 存在 created_at/written_at > as_of 的条目 → Err
         └─ 5. 正常路径：for node in closed_lineage.nodes
                 跳过非 Alive 节点（Falsified/Absent 不授权）
                 event_to_bsp.get(&node.key) 查无则跳过（Absent 非证伪）
                 prior_bsp_by_key 无此 key 且本次未创建 → push ManagedBspCreation
                 for rule in policy.rules：
                   projection = ProjectionKey{ lineage, policy_id, rule_id, slot }
                   link_key = LinkKey{ bsp, projection }
                   prior_links_by_key 无此 key 且本次未写 → push BspLink
       ├─ Err(e) → consume() 直接 `?` 上抛（fail-closed，不吞错误）
       └─ Ok((creations, links)) → 累积进 self.prior_bsp / self.prior_links（下次调用的幂等基线）
                                   并汇总进 creations_total / links_total
  3. 返回 (creations_total, links_total) 给调用方（WireV1 薄读数口）
```

数据流：`AliveIndex`/`PathDag` 增量（`advance` 阶段产出）→ `chain_book` 的 `Closed` 证书 +
`event_to_bsp` 映射（`advance` 阶段维护）→ `consume_at` 逐证书投影 → `prior_bsp`/`prior_links`
状态累积（供下次调用幂等判断）→ `(ManagedBspCreation[], BspLink[])` 增量返回值。

## Where Things Live

- `rust/src/theta_v0/classifier/consume_at.rs`：纯函数 `consume_at` 本体、类型族
  （`ProjectionKey`/`LinkKey`/`ManagedBsp`/`ManagedBspCreation`/`ConsumeError`）、单元测试。
- `rust/src/theta_v0/classifier/e2eo.rs`：装配层 `E2eOAssembly`，`advance`（推进）+ `consume`
  （唯一调用 `consume_at` 的生产路径，`:169`）两入口。
- `rust/src/theta_v0/classifier/chain_cert.rs`：`TowerChainCertificate`/`ChainStatus`/
  `ChainNodeStatus`/`AliveIndex`/`PathDag` 定义，`consume_at` 只读其公开字段。
- `rust/src/theta_v0/classifier/bsp_bridge.rs`：`BspStructuralKey` 定义来源，`event_to_bsp`
  的桥接簿由此模块 `advance_indexed` 增量维护。

## Gotchas

- `consume_at` 本身是纯函数（无内部状态），幂等与跨链累积状态**由调用方**
  （`E2eOAssembly::consume` 里的 `self.prior_bsp`/`self.prior_links`）持有并在每次调用后写回——
  读函数签名容易误以为状态在函数内部维护。
- `LateAuthorization`/`InconsistentState` 两个错误分支在生产路径（`consume()` 内按
  `(closed_at, key)` 升序遍历）"理论恒不可达"，代码注释明写这点；它们仍是冻结签名的一部分，
  单元测试（`consume_at.rs:521` 起）单独构造非法输入触发，不依赖生产调用顺序。
- 语义模糊的两个判据（`LateAuthorization`/`InconsistentState`）注释里留了 `TODO`，声明"精确判据
  待冻结语义细化"——这是本仓"实装先行、语义留白照实标注"的惯例，不是遗漏。
