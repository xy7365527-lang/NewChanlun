Schema 不是忠实实装

第 0002 课 · 一个真实的「我解决了」如何被当场拆穿——以及你该问的那一句

就在你读上一课时，蜂群里发生了一件值得当教材的事。一个工位报告：「§1 递归矛盾——四处退化桩全部忠实替换，无矛盾，build 绿。」 另一个异质工位（codex）当场说：不，它还是退化的，只是藏得更深。 谁对？这一课教你怎么自己判断——这是你质询蜂群最核心的一项能力。

1. 案情：同一段代码，两种裁决

缠论递归要求：第 n+1 级走势 = 把第 n 级走势序列分段，每段 ≥3 个不同的下级走势合成一个上级走势， 于是得到一个多元素的上级序列。工位的「忠实」修法是：

def composeStep (n) (xs : List Move) : List Move :=
  if xs.length >= 3 then [ Move.compose xs ... ] else []

它把载体从 Move（单走势）换成了 List Move（序列），并宣称「现在用真实序列了，不再 [m,m,m] 复制，忠实」。 表面看很有道理——确实没复制了。

codex 的反驳（一句话拆穿）： [ Move.compose xs ] 把整个下级序列 xs 压成一个上级走势—— 输出 List Move 的长度永远 ≤ 1。这是「全局聚合摘要」，不是「多个上级走势由多个窗口递归生成」。 缠论要的是 segmentsOf : List Stroke → List Segment 那种多进多出，每个输出元素背后有自己的 ≥3 个下级 witness。

所以两版的退化只是形态不同：

旧桩「忠实」修法真正忠实
构造[m,m,m] 复制三份[compose xs] 整段压一个分段窗口 → 多个上级
上级序列长度1≤ 1可多个
≥3 不同 witness假未证须证

2. 病根：Schema（骨架）≠ 忠实实装（血肉）

为什么聪明人也会掉进去？因为 Lean 能编译、能过 build，给人「做完了」的错觉。但编译只保证类型对，不保证缠论对。

区分两个层级（上一课的认识论分级在这里落地）：
  • Schema / 接口（L0）：「存在一个全函数 Fstep」「函数即全且唯一」——这是同义反复的真理，任何函数都满足，对缠论一无所知。
  • 忠实实装（L1/L2）：「这个 Fstep 真的实现了第67/71课的分段规则、每个上级真有 ≥3 个不同下级」——这才有缠论内容，且要真实数据才能证伪。
codex 的 origin 版本很诚实地承认这一点：它把递归写成 ElementPipeline 接口，明说 "deliberately an interface"——骨架严格，血肉留给实例。错的不是写接口，错的是把接口的 L0 真理当成「忠实实装完成」来声明。这叫声明膨胀。

3. 通用的识破法

不懂 Lean 也能用。当任何人（AI 或人）说「我把 X 忠实实现了」，问三层：

  1. 反退化见证：「给我一个具体例子，证明它没退化。」——本案中：「给我一个输入，它的输出上级序列长度 ≥ 2。」给不出，就是 length≤1 的聚合。
  2. 这是哪一层的真理：「这是『类型/函数自动成立』（L0 骨架），还是『缠论规则真的被编码』（L1）？再问，有真实数据撑吗（L2）？」
  3. 边界条件：「什么情况下你这个结论会翻——如果翻，说明你没覆盖那个情况。」

带走的锋利问题

「你说忠实实现了递归——给我一个上级序列长度 ≥ 2 的具体例子，并指出每个上级元素的那 ≥3 个不同下级 witness。 拿不出来，你做的就是『整段压一个』的聚合，不是缠论递归。」
