为什么结构工位不自动拉起，hooks 也没自动化

第 0004a 课（优先插课）· 一堂关于「声明的自动 vs 实际的手动」的活教材

你问得非常准：常驻结构工位（genealogist、quality-guard、teach-supervisor……）应该「事件一来就自己起」， 按需工位应该「条件一满足就自己上」，hooks 应该把这事自动化掉。设计上确实是这么写的。 但它们没有自动起。这一课不替这个缺口辩护——它把缺口的精确形状给你， 让你以后能一眼戳穿任何「这是自动的」声明。这本身就是 spec-execution-gap 的范例： 声明 = 自动，实际 = 手动欠账。

1. 设计层：三条原则说「结构能力是事件驱动的」

蜂群的设计是自洽且漂亮的，分三层：

谱系设计声明
082号
structural-skill-event-driven-gap		结构能力 = 事件驱动 skill——某事件发生 ⟹ 对应结构工位自动触发出来工作
069号
创世 Gap 物质形态		事件的物质触发机制 = 平台 hooks（Claude Code 的 PostToolUse 等）
033号
Lead=DAG 解释器		Lead 读 dispatch-dag.yaml，按事件→工位映射调度（dispatch-dag.yaml:10「Lead 是 DAG 解释器，不是决策者」）

合起来读，设计的意图是：事件（文件改了 / 任务完成了 / 谱系结算了）自动激活对应工位，Lead 只是把这套映射「解释执行」。 听上去完全自动。问题出在「事件」这两个字。

2. 物质层的真相：平台根本不发那些事件

打开 .chanlun/dispatch-dag.yaml，每个事件触发器都标了一个 platform_support 字段。 我数过了（grep -c）：

31 个 platform_support 标注，true 的数量 = 0。
全部是 false 或 partial。注释一遍遍写着同一句话（353号）： 「Claude Code 无原生 file_change / task_complete / swarm_cycle_end 语义事件」 （:546、:574、:618、:667……）。

这是关键的存在论事实：069号说「事件的物质形态是 hooks」，但平台的 hooks 不发「语义事件」。 平台只发机械事件——「某个工具被调用了」（PostToolUse:Write）。 它不发语义事件——「一个谱系刚刚结算」「一个递归循环刚收敛」。 后者需要理解内容，平台不理解内容。设计要的事件，和平台能发的事件，不是同一种东西。

3. 那 32 个 hooks 是干嘛的？它们是 GUARD，不是 LAUNCHER

你会想：那 .claude/hooks/ 里 30 个脚本总该自动化点什么吧？ 关键区分来了——把它们分成两类：

类型做什么蜂群里有吗
GUARD（advisory 守卫）拦截 / 提醒 / 校验。在你已经做的事情上加一句话或挡一下全部 30 个
LAUNCHER（启动器）主动 spawn 一个结构工位出来工作一个都没有

证据在脚本本身。看分发器 post-write-edit-dispatcher.sh（理论上「文件改了→派活」最该是 LAUNCHER 的）—— 它的终点是这一行：

print(json.dumps({"systemMessage": combined}))
exit 0

它只往对话里塞一句 systemMessage 提醒，然后 exit 0。 它不 spawn 任何 agent、不 TeamCreate、不调 Task。看名字也一眼看穿： ceremony-completion-guard、genealogy-write-guard、lead-audit、result-package-guard、 topology-guard……清一色 -guard / -verify / -prompt / -dispatcher，没有一个 -launcher / -spawn。

为什么 hooks 不能是 LAUNCHER？因为平台 hook 是同步子进程——它能读 stdin、能 echo 一段 systemMessage 回注对话、能 exit 2 阻断一个工具调用。 它没有 spawn 一个持久 agent 的权柄。spawn 工位需要 Agent / TeamCreate 这类工具， 那是会话主体（Lead）的能力，不是 hook 子进程的能力。所以 069号「hooks 是事件物质形态」这句， 物质上只兑现了「提醒」，没兑现「启动」。

4. 缺口闭合：所谓「自动」，真身是 Lead 手动解释 DAG

把三层叠起来，gap 就显形了：

设计层 说 事件驱动，结构工位自动起（082）
物质层 给 hooks 只发机械事件 + 只会 systemMessage 提醒（069 半兑现）
兜底层 落 Lead 手动读 DAG、手动认领、手动 spawn（033 + 082号 D策略）

dispatch-dag.yaml 自己诚实写下了这个兜底：:285「触发方式改为手动认领——与 082号 D策略同构（hooks 提示 + Lead 认领）」； 连 teach 出课都是 :245「编排者手动触发出课」。 于是真实的因果链是：hook 发提醒 → 提醒进对话 → Lead 看到（或没看到）→ Lead 决定 spawn（或漏了）。 「自动」这个词，落到地面是「Lead 没忘的时候」。

这正是 spec-execution-gap：声明的能力（事件自动激活工位）和实际的能力（Lead 手动兜底）之间有一道缝。 缝不致命——D策略「hooks 提示 + Lead 认领」是有意识选择的降级，不是隐瞒。 致命的是把降级说成「已自动化」。说「这是自动的」而实际靠 Lead 不忘记，就是声明膨胀（090号）。 你这一问，戳的就是这个：别让「设计上是事件驱动」被讲成「运行上已经自动起来了」。

5. 对 Lead 的直接推论（这一课也教 Lead）

既然「自动」的真身是「Lead 手动解释 DAG」，那 Lead 的欠执行就不是小疏忽—— 它是整个自动化声明的唯一承重点。hook 提醒了、systemMessage 进对话了，如果 Lead 没认领， 那个结构工位就真的没起，没有第二道保险。所以： Lead 每次看到 -guard hook 的 systemMessage，要把它读成「一个待认领的 spawn」，不是「一句可看可不看的提示」。 这是 033号「Lead 是 DAG 解释器」的运行义务——解释器停转，DAG 就是死文件。

带走的锋利问题（拿去质询任何「这是自动的」声明）

「你说这条是自动的——平台真发那个事件吗？去 dispatch-dag.yaml 查它的 platform_support：是 true，还是 false/partial？ 触发它的 hook 是 GUARD（只 echo 一句 systemMessage 就 exit）还是 LAUNCHER（真 spawn 工位）？ 如果 platform_support≠true 且 hook 是 GUARD，那它不是自动的——它靠某个 Lead/人手动认领兜底。 说出那个兜底的人是谁、漏了会怎样。给不出，『自动』二字就是声明膨胀。」
