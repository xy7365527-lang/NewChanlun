teammate 与 subagent：同一原语，一个布尔位的分岔

第 0007 课（优先插课）· 描述说「不可用」，schema 却含那个字段——哪个为准？一堂用物证裁决的活教材

编排者要 Lead「用 teammate（后台并行），不要用 subagent」。这要求一个前提：Lead 真能 spawn 后台工位。 但 Lead 手里的 Agent 工具自带一处刺眼矛盾——它的文字描述说「run_in_background / name / mode 在此不可用，仅同步 subagent」， 它的 JSON schema 却含 run_in_background 属性。两者不可能都对。这一课按 0004a 的物证法把它坐实， 给出可证伪的裁决——因为这直接决定 Lead 接下来怎么 spawn。

1. 概念区分：两者是同一原语，差在一个布尔位

先把概念摆清。subagent 和 teammate 不是两种工具，是同一个 spawn 原语（Agent）的两种调用模式， 分岔点就是 run_in_background 这一个布尔字段：

subagent（同步）teammate（后台）
调用Agent(..., run_in_background: false)（或省略）Agent(..., run_in_background: true)
Lead 拿到什么阻塞，直到子 agent 跑完，返回完整最终报告作为工具结果立即返回一个 handle（agentId，格式 a…-…），子 agent 在后台继续跑
Lead 期间能否响应不能——被这一个调用占住能——Lead 保持响应，可同时编排多个
生命周期一次性：返回即结束持久：完成后发 task/agent 通知，可经 SendMessage(to: agentId) 续聊
协调方式无需协调（就一个结果）任务板（TaskCreate/TaskList…）+ SendMessage
底层是同一原语吗？是。本课的 SendMessage 物证直接证明这一点——它的描述写道： 「to "main"（background subagents only）」「to resume a completed background agent, use the agentId」。 平台自己把后台工位叫 "background subagent"——可见 teammate 不是异类，就是开了 run_in_background 的 subagent。 差异只在那一个布尔位：开 = 非阻塞持久 teammate，关 = 阻塞一次性 subagent。

2. 平台真相：那个矛盾，哪一端为准（可证伪裁决）

像 0004a 查 platform_support 那样，这次的物证就在工具定义本身——这是最硬的物证，因为它是本 session 实际加载的 schema。

矛盾的两端（逐字）：
① Agent 工具描述结尾：「run_in_background, name, and mode are unavailable here — only synchronous subagents.」
② Agent 工具schema里却列着 run_in_background 属性：「Set to true to run this agent in the background. You will be notified when it completes.」
描述说三个字段「unavailable」，schema 却定义着它们。两端不可能都对。

不要凭好看的那一端选。要找独立的第三方物证来打破对称——本课现场抓到两条：

物证说了什么指向哪端
A · 系统对 deferred 工具的回执本 session 尝试加载 TaskCreate/TaskList/TaskGet/TaskUpdate 时，系统返回：这些工具「no longer available (their MCP server disconnected)」——只有 TaskStop 与 SendMessage 成功加载任务板工具族真实存在过（否则无从「disconnected」），但此刻这台 session 连不上
B · SendMessage 的续聊语义「to resume a completed background agent, use the agentId (format a…-…)」「"main" — The main conversation (background subagents only)」平台的消息协议预设了后台 agent 的存在——若全程只有同步 subagent，这套 agentId 续聊 / to:"main" 回汇就没有指涉对象
裁决（可证伪）：「run_in_background 能不能用」不是一个全局真假，是一个 session-级运行时事实。 schema 含它 + SendMessage 预设后台 agent ⟹ 平台原语层支持后台（描述里那句「unavailable」是过期/语境化的，针对「任务板 MCP 未挂载」的退化态写的）。 但物证 A 证明：本 session 的任务板（Task* MCP）此刻断连——没有任务板，后台工位即便能 spawn，也无法被 TaskList 实时观测。
判据（拿去证伪，不要背结论）：Lead 真要用 teammate 前，实测一次—— ①调 Agent(run_in_background: true)，看返回的是立即的 agentId handle（证后台成功）还是阻塞到完整报告（证退化成同步）； ②调 TaskList 看任务板是否响应（证编排者能否看实时 in_progress）。两者皆真 = teammate 全面并行成立；任一为假 = 当前 session 只能退化用同步 subagent。

3. 何时用哪个

就算两者都可用，也不是「teammate 永远更好」。选择由任务的依赖结构决定，不由「显得并行」决定：

用同步 subagent（阻塞）用后台 teammate（非阻塞）
需要立即拿到结果才能继续（下一步的输入是它的输出）全面并行多个独立工位（lead-parallel-dispatch 218号：无依赖即并行）
串行门：必须等这一步成败才决定走向Lead 要保持响应、同时编排 + 接编排者中断
一次性查询、单点搜索（如 Explore 一个文件）编排者要在任务板看实时 in_progress（异步可观测性）
结果短、无需持久续聊长任务、需 SendMessage 续聊 / 多轮协调

注意：本课规则卡（lead-parallel-dispatch 218号）要求「无依赖即全部并行 spawn」。全面并行的载体是后台 teammate—— 若退化成「同步 subagent 批量」，Lead 每 spawn 一个就被阻塞到它跑完，批量 ≠ 并行，只是快速串行。这正是下一节锋利问题要戳的。

4. 这堂课对 Lead 的直接义务

编排者的指令「用 teammate 不用 subagent」落到 Lead 身上是一个可验证的运行时承诺，不是一句姿态。 Lead 报「已 teammate 全面并行」时，声明里藏着两个必须为真的事实：(1) Agent 返回的是立即 handle（真后台），(2) 任务板能 TaskList 出实时状态（编排者可观测）。 两者任一为假，「teammate 并行」就是声明膨胀（090号）——实际是被阻塞的同步 subagent 批量，伪装成并行。

诚实的退化路径（不是 workaround）：若实测发现本 session 任务板断连（物证 A 的情形）， 正确动作是诚实声明「当前 session 任务板不可用，退化为同步 subagent 批量执行，编排者暂无实时任务板」， 而不是嘴上说 teammate、底下跑同步还假装并行。前者是诚实标注有效域边界（formalization-validity-domain 同源）；后者是 spec-execution-gap（声明=teammate / 实际=阻塞 subagent）。

带走的锋利问题（拿去质询任何「teammate 全面并行」声明）

「你说这是 teammate 全面并行——它真后台了吗？你那次 Agent 调用返回的是立即的 agentId handle（a…-…）， 还是阻塞到完整最终报告才返回？编排者现在能在任务板看到实时 in_progress 吗——TaskList 响应吗？ 还是其实退化成了同步 subagent 批量、Lead 每个都被阻塞、『并行』只是快速串行？ 给不出『立即 handle + 实时任务板』两条证据，『teammate 并行』就是声明膨胀——你做的是被阻塞的 subagent，不是后台 teammate。」

来源（全部本 session 工具定义 + 系统回执物证，非转述）： Agent 工具描述「run_in_background, name, mode are unavailable here — only synchronous subagents」对撞 其 schema 内的 run_in_background/name/mode 属性定义； 系统 deferred-tool 回执「TaskCreate/TaskList/TaskGet/TaskUpdate no longer available (MCP server disconnected)」（仅 TaskStop/SendMessage 加载成功）； SendMessage 描述的 agentId 续聊 + to:"main"（background subagents only）语义。
规则：lead-parallel-dispatch.md（218号 Lead 全并行 / 275号局部依赖）；spec-execution-gap skill（声明=能力一致性）；谱系同 0004a 的 082/073a。
认识论等级（诚实标注）：本课的概念区分（同一原语 + 布尔位分岔、何时用哪个）是 L0 方法论结晶； 对「run_in_background 能否用」的裁决诚实标为 L2-session局部——它是当前这台 session 的运行时事实（schema 支持原语 / 任务板此刻断连）， 不是跨所有 session 的全局常量。这正是为何裁决落成「Lead 必须实测一次」而非「背一个结论」——session 切换 / MCP 重连后真值可能翻转，必须用判据现场证伪。
「立即 handle vs 阻塞报告」「原语支持 vs 任务板连通」「批量 ≠ 并行」这三个区分若发虚，喊停，坐实再走。
