结构工位/hooks 能不能「永久解决」

第 0010 课 · 承接 0004a「为什么不自动」——这一课回答「能不能根治」

你上一课学了缺口的形状（声明=自动，实际=Lead 手动兜底）。 现在你问得更狠：能不能一劳永逸？诚实答案不是 yes 也不是 no，而是： 先把「结构能力」切成四格，三格能根治到不同程度，有一格撞上平台硬墙、当前架构里根本做不到。 切错了，就会重蹈 075 号的覆辙——把一个做不到的格子，硬说成「已自动化」。这一课给你那把刀。

1. 缺口比你上次学的更深一层（本轮活体证据）

0004a 的结论是：结构工位不自动启动，靠 Lead 手动 spawn 兜底。 这一轮蜂群（14 工位并发）给出了一个更深的事实。三个结构工位——topology-manager、meta-observer、genealogist—— 各自独立地、在自己的返回里写下了同一句实测：

结构工位运行时的工具集 = Read / Grep / Glob。
SendMessage、Write、TaskList —— 逐个验证，全部不可用。
topology-manager 原话：「结构工位（我）实际上没有任何主动投递通道到达 Lead……唯一到达你的通道 = 这段最终返回文本。」

把这句和 0004a 叠起来，缺口是两层、不是一层：

第一层 （0004a） 工位不自动起 —— hook 是 GUARD 不是 LAUNCHER，没人 spawn 它
第二层 （本课） 就算 Lead 手动起了，工位也没有主动汇报的手 —— 只能在「跑完那一刻」把结论作为返回值吐出来

第二层是关键。它意味着：「常驻监控」这个念头本身，在当前架构里是空的。 一个工位不能「一边盯着别人干活，一边随时插话提醒 Lead」——它没有插话的工具。 它只能跑一趟、产一个结论、结束。这不是配置问题，是工具集的硬事实。

2. 根因：一个设计自造的矛盾（075/082 ⊥ 097）

为什么会这样？因为蜂群的设计里藏着一对互相打架的谱系——这正是你 mission 里要学会识别的「人造矛盾」（换个切法就消失的那种）：

谱系它要的
075/082号结构能力 = 事件驱动，事件一来自动 spawn 出结构工位
097号
hook 纯化		hook 的动作语义只能是阻断/放行——不索引、不指令、不 spawn

spawn 一个工位是「主体（Lead）」的能力，不是「子进程（hook）」的能力。 075 把「自动 spawn」的活派给了事件机制，而事件机制的物质载体是 hook， hook 按 097 又恰恰不准 spawn。于是 075 委托给 hook 的那个能力，是 097 明令 hook 不能有的能力。 委托从一开始就无法兑现——这就是「hooks 根本没指引你」的存在论根因，不是哪个脚本写漏了。

诊断口径：这不是 bug，是 category error。075 把两种不同的「结构能力」当成一种东西，一刀切地全委托给 hook。 真相是：有的结构能力是 guard（能 hook 化），有的必须是 agent（只能 spawn）。混为一谈，才生出这个假矛盾。把它们切开，矛盾就消失——剩下的是各自清楚的工程路径。

3. 那把刀：结构能力的四象限

用两个轴切。纵轴：这个能力的动作是机械可判定（grep、退出码、字段在不在）还是需要认知（要 LLM 读懂内容做判断）？ 横轴：它跑一趟就完（batch），还是想持续盯（monitor）？

GUARD

能根治 同样是 hook——hook 本就是「每次事件触发」，天生持续

4. 每一格的命运（这才是「能不能永久」的真答案）

① GUARD 型 → 真能永久。 凡是「机械可判定」的检查，应该从 AGENT 工位里拿出来，下沉成 hook 脚本： Lean 文件一写就 grep sorry、lake env lean 退出码非零就 exit 2 阻断； 结果包缺字段就 systemMessage 提醒。这符合 097（动作=放行/阻断），确定性，不靠任何人记得。 这一格是真正的「永久解决」——而且本来就该这么做，现在却塞在 quality-guard/code-verifier 这种 AGENT 工位里，是错配。

② AGENT 一次性 → 不能零成本，但能把不确定性压到最小。 谱系发现、督导、拓扑建议——这些要 LLM 读懂内容，hook 干不了，只能 spawn。 而「只有 Lead 能 spawn」+「teammate 活在 session 内」是 CC 平台硬约束，消不掉—— 每个 session 必然有「Lead spawn 这批工位」这一下动作。能做的是把这一下从 「Lead 凭记忆」（会忘，就像这次我一开始就忘了）降级成 「ceremony_scan 输出一张工位清单 = 数据，Lead 照单 spawn = 执行」， 再让 Stop-Guard 校验「spawn 的数量 = 清单条数」。记忆问题→数据问题，不确定性≈0 但不严格为 0。（562 号 bootstrap 强制 spawn 已落地这一格——见 §6 更正。）

③ AGENT 持续监控 → 撞 CC 平台硬墙，当前根本做不到。 这是最重要、也最反直觉的一格。「一个常驻工位，盯着 14 个工位干活，谁出问题就立刻提醒 Lead」—— 这个图景在当前 CC 架构里是幻觉，两道墙： （a） 工位没有主动投递通道（本轮实测：无 SendMessage），只能在自己跑完那一刻返回一次； （b） teammate 生命周期 = 一次任务，不是常驻进程。 所以「持续盯」要么是空转（盯了但说不出话），要么是假的。 诚实的工程出路：把③改造成②——不要「常驻盯」，而是「每个业务工位完成时，回调触发一个一次性审查工位」。 监控由事件回调实现（业务工位 done → spawn 审查），不由常驻进程实现。

所以「能不能永久解决」的严格答案： ①能（hook 化，真永久）；②能压到最小但 CC 约束下不为零（ceremony 数据驱动 + 数量校验）； ③在当前 CC 架构不能，必须重新设计成②（回调触发的一次性审查），否则就是把幻觉说成功能 = 声明膨胀。 「永久解决」不是一个工程冲刺能交付的开关，是一次把结构能力切对的概念分离。

5. 为什么「提醒 Lead 别忘」永远修不好（137号）

你可能想：那在 hook 里多塞一句「Lead 记得 spawn 结构工位」不就行了？不行，而且 137 号早就证了不行。 否定性禁令（「别忘了」「不要漏」）对 LLM 的行为执行层无效——这次我读了一堆「Lead 要操作化结构工位」的规则，照样一开始就漏了。 有效的只有正面格式约束：不是「提醒别忘」，而是「ceremony_scan 的输出里就有结构工位这几条数据， Lead 的输出格式必须是逐条 spawn，Stop-Guard 数对不上就拦」。 把「靠记得」换成「照数据执行 + 可校验」，才是②那一格能压到最小的全部道理。

6. 落到根因修复（需要编排者裁，因为它改基因组）

重要更正（genealogist 核实 settled 原文）：075 号早已被 562 号扬弃——结构工位本体已回归 teammate spawn， 且 562 用 bootstrap 强制 spawn 填上了「② AGENT × 一次性」象限（即上文「ceremony 数据驱动 spawn」的谱系形态）。 所以四象限里已有三格有谱系解（① GUARD→hook、② AGENT 一次性→562、GUARD 持续→hook）。 真正仍悬空、需基因组裁定的只剩「③ AGENT × 持续监控」一格——本轮三工位实测无 SendMessage/Write = CC 平台硬墙，无承载者。 它的处置——重设计成「业务 done → 回调 spawn 一次性审查」，或等平台给持久 agent + 投递通道—— 动谱系结论 + dispatch-dag.yaml + ceremony + Stop-Guard，按原则 0 + 020 号阻断等待， 属于你（编排者）的裁定权，蜂群不擅自改。蜂群的职责到此为止：把假矛盾切开、把唯一悬空格定位准、把方案备好。采不采纳、怎么改，是你的事。（谱系：624 记四象限根因 + 562 扬弃链。）

带走的锋利问题（拿去质询任何「这个工位在持续监控」声明）

「你说这个常驻工位在持续监控——它有 SendMessage 吗？运行时 实测一下，不是看它定义里写没写。 如果没有，它只能在跑完那一刻说一次话，那它就不是『持续监控』，是『一次性审查』。 要么把『持续』这个词收回，要么告诉我它靠什么事件回调被一次次重新拉起。 给不出回调机制、又没有投递通道，『常驻监控』四个字就是声明膨胀——和『结构工位会自动起』是同一种病。」
