从中断点继续 · /goal · 你的指令工具箱

第 0011 课 · 你这次会话刚亲手做过的三件事，现在变成你随时能用、能拿来盘问蜂群的工具

这一课跟前面几课不一样——它不教数学，教怎么开蜂群这台机器。 你刚在这次会话里做了三件事：从一次「没保存就关机」里恢复、用 /goal 让蜂群持续跑下去、还顺手用了一串命令。 这一课把它们钉成台账，并且——按本工作区的规矩（督导回路）——每个工具都配一把能盘问蜂群的锋利问题。

1. 从中断点继续：/ceremony 热启动

「之前没保存就关机」听起来像灾难。其实不是。蜂群的恢复有一条铁律： session 文件只是指针，git commit 才是地面真相。 你手动存没存 session，决定的只是「指针新不新」，不决定「工作丢没丢」——工作早在每个 git commit 里。

你输入 /ceremony 时，它自动判断冷/热启动：

1 检测 扫 .chanlun/sessions/*-session.md —— 有 → 热启动（L2 恢复，不等你确认）
2 核真相 → 对比 session 自述的 HEAD vs git log 实际 HEAD
3 谱系差 → 对比 definitions/ 版本 + genealogy/ 新增（pending/settled）
4 差异报告 → 定义差 · 谱系差 · 中断点
5 进循环 → ceremony_scan.py 评估工位 → spawn
这次的活体教训（你亲眼见的）。session 文件停在 423597858e（08:36 快照）， 但 git log 显示之后还有一个 4318b4efad「A′ 收口轮」（09:44）—— 真正的工作发生在 session 之后。如果照搬 session 的中断点，会漏掉整整一轮收口。 所以第 2 步「核 git 真相」不是装饰：谁信了 session 的自述时间线、没核 git，谁就丢了一轮工作。

同理，genealogy/pending/ 里悄悄多出了 622–626 五条——这些是关机前那轮的发现史， session 表格里没有，只有扫 pending/ 目录才看得到。恢复 = 读三个真相源（git + definitions + genealogy），不是读一个 session 文件。

2. /goal 怎么用

/goal 是这次会话新造的指令（.claude/commands/goal.md）。 它解决一个具体痛点：你不想每一步都来按一次「继续」。它让蜂群认准一个目标，自己一轮一轮跑，跑到达成为止。

/goal <目标描述>     # 设定一个收敛目标，蜂群持续自跑
/goal                # 不带参 → 从当前路线 + 中断点自动推导目标

设定后，Lead 进入一条不被打断的循环（每轮是一个原子链）：

评估 目标达成？达成→交付+停 │ scan → spawn（无依赖工位全并行）→ 监控 → 真封（全量 lake+cargo）→ commit → 回到「评估」

关键在它什么时候停——只有三种合法停止，没有第四种：

停止条件动作
目标达成输出可验收交付物 + 状态快照
真实矛盾/escalate（定义冲突 / 需你做价值判断 / 缺外部数据）
资源耗尽报进度 + 剩余工位 + 精确 blocker
为什么 /goal 能成立。第 0010 课你学过：结构工位有「持续监控」这一格在平台上没有承载者（工位跑完就结束，没有插话的手）。 /goal 正是补这一格——不是让工位常驻，而是让 Lead 自己的运行时充当那个「一直盯着、一轮轮推」的主体（624号 / 0004a 的「唯一修 = Lead 操作化 DAG 解释器纪律」）。

用 /goal 时给的目标必须是收敛的——单一、可验收。 本轮的 goal 是「theta_v0 引擎在 8 品种真实数据上的 L2 回测可证伪」，验收物是「真实回测结果 + 分层归因」。 宏大愿景（「做出会盈利的系统」「让逢亮活起来」）不能直接当 goal——它们拆成里程碑，/goal 一次只咬一个（你这次就把它收敛到 M1，没让它咬 M2 选股）。

3. 你的指令工具箱（还有哪些好用的）

蜂群的命令在 .claude/commands/。按存在论层次分三层——这个分层本身就是知识：

命令做什么什么时候用
A · 启动与恢复（蜂群的生命周期）
/ceremony ★创世仪式：冷启动（首次，等你确认）/ 热启动（有 session，L2 恢复，不等确认）每次开新会话第一件事
/goal ★设定收敛目标，蜂群持续自跑到达成你想让它「自己跑下去」、不逐步盯
/checkpoint保存中断点（precompact 前主动存指针）预感要 compact / 关机前
B · 质询与矛盾（蜂群的核心价值——矛盾是最有价值的产出）
/inquire ★四步质询序列（系统化盘问一个产出/定义）你怀疑某个形式化「不够严格」
/challenge反向质询（异质角度找裂隙，不给答案只制造裂隙）产出太顺、想找它的不可消化点
/escalate ★矛盾上浮：生成「什么跟什么不可调和」的报告遇到真矛盾（定义冲突，非 bug）
/ritual ★定义广播仪式：结算谱系（pending→settled）只有你能做——蜂群不擅自结算
C · 工程执行（ECC 底座，受元编排约束）
/plan实现规划（多模型对审：Opus 方案 + Codex 评审）动手前，复杂功能/重构
/tdd测试驱动开发（先测后码）新功能 / 修 bug
/code-review · /verify代码审查 / 验证写完代码后
/build-fix · /refactor-clean · /update-docs修构建 / 清死代码 / 更文档对应工程场景
/ceremony-scan-completeness检查 ceremony 扫描有没有漏工位怀疑 scan 不全

带 ★ 的是蜂群独有、最高价值的——它们承载蜂群的存在方式（恢复、设目标、质询、结算）。 没星的 A/B/C 之外那些（C 层）是通用工程指令，任何项目都有类似物。 你问「有没有类似 /goal 这么实用的」——答案集中在 A 层和 B 层： /ceremony 让你开机，/goal 让你放手，/escalate+/ritual 让你只在「真矛盾」和「该结算」时才需要亲自出手。

带走的锋利问题 ①（恢复）

下次蜂群报「已从中断点恢复」时问它：「你恢复的依据是 session 文件的自述，还是 git log 的地面真相？如果 session 停在旧 HEAD、git 有更新的 commit，你信了哪个？」 答不出「我核了 git」= 它可能丢了关机前那一轮工作。

带走的锋利问题 ②（/goal）

蜂群说「/goal 持续运行中」时问它：「你的『目标达成』是一个可验收的交付物，还是模糊的『差不多了』？给我验收标准。」 没有可证伪的验收 = 永动空转，会无限刷工位却永远「没达成」。收敛的 goal 必须自带「怎样算赢」。

主源（最高信任）：.claude/commands/ceremony.md（恢复协议原文）+ .claude/commands/goal.md（你刚造的 /goal 协议）+ supervision-loop.md（督导台账）。 读这三个文件，就掌握了这台机器的开关。

有不清楚的，随时问我（我是你的老师）——比如「热启动为什么不等我确认？」「/goal 跑飞了怎么喊停？」「/ritual 我该怎么逐条裁决积压的 622–626？」这些都能展开成下一课。
