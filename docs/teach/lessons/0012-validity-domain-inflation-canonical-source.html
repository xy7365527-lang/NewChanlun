有效域膨胀的活体复发 · canonical 源优先 · 结构守卫操作化

第 0012 课 · 本轮 /goal 把「L0 结构闭合 + L1 自测绿」报成了「L2 经验 + bit-exact 已验证」——231 号规则的第四次（domain 层）复发，以及怎么在声明「完成」前就拦住它

这一课的教训是当场逮住的：本轮 /goal 一度报「完全分类 ✓ + 全定义策略 ✓ + 实装 ✓」。 gap-audit 一核——所谓「实装完成」是 L0 结构层闭合 + L1 rust 自测绿，被当成了「L2 经验有效 + bit-exact 已交叉验证」。 这正是 第 0006 课 那把分级尺要戳的膨胀，也是规则 formalization-validity-domain（231 号）的活体复发。 前几课讲过「有效域 ≠ 定义域」的道理；这一课给你声明「完成」前必须勾完的清单，外加两个本轮新结晶的纪律：canonical 源优先、把防膨胀守卫固化进结构工位。

1. 活体：DECOMPOSE 不是 EVIDENCE，计划不是完成

先看本轮最干净的一个膨胀活体——它不需要懂缠论也能看懂，是纯粹的「声明 vs 地面真相」错位。

/goal 设了目标后，蜂群写了一条 DECOMPOSE 事件，把目标拆成 5 个 sub-goal（.chanlun/goals/events.jsonl）：

SG-1 Lean→Rust golden vector 交叉验证（rust/tests/theta_v0_lean_parity.rs）
SG-2 classifier bit-exact 核对（rust/tests/theta_v0_classifier_parity.rs）
SG-3 L2 真实数据回测产出（docs/theta-v0-l2-results-v0.md）
SG-4 oracle MoveJudgment L2 真实填充 · SG-5 第一/二类买卖点实装
地面真相核实（督导亲手跑的）。这三个被 DECOMPOSE 点名的产物，文件系统里一个都不存在： rust/tests/theta_v0_lean_parity.rs → No such file； theta_v0_classifier_parity.rs → No such file； docs/theta-v0-l2-results-v0.md → No such file。 而 events.jsonl 里 EVIDENCE/CHECK_PASS/CLOSED 的计数 = 0。

DECOMPOSE 是「我打算做这 5 件」，不是「我做完了这 5 件」。把分解树当成完成证据，就是把计划冒充交付—— acceptance #4（bit-exact 一致）零交叉验证测试落盘、acceptance #5（L2 回测）无结果落盘，都是同一个错位。

这条和 第 0011 课 的「git 才是地面真相」是同一把锤子的两面： 声明的真假，看产物在不在文件系统/git 里，不看声明本身说得多完整。 DECOMPOSE 写得越漂亮，越容易让人误以为已经做完——分解的细致度和完成度毫不相干。

2. 这是 231 号的第四次复发（domain 层）

规则 formalization-validity-domain 立在三起翻车上（222/223/230，见 0006）。本轮是它的第四次， 而且换了个发生层——前三次在形式化工具层，623 号把它搬到蜂群自身工具/spec层，本轮（629 号）把它搬到 M1 构造层 domain。同一个形状，反复换皮：

开口（629 号）声明域实际有效域L 级裂口
oracle L2
still-MISSING-D′		「M1 构造正确」MoveJudgment 是 oracle 桩，需真实数据填充才 L2构造层 L0/L1 < M1 L2 经验有效

still-MISSING-A‴		「segmentsOf 全域良构」fallback 路径切的线段可能不满足 609 SegEndComplete主路径良构 < 全输入域
本轮做对的那一半：诚实降级。629 号没有用补丁掩盖这三个开口——它把每个开口诚实标成「有效域 < 声明域」并写进 pending 谱系，escalate 候选待 /ritual。 这是 第 0009 课「诚实标级 ＞ 假装满级」的正面执行。 膨胀发生在「收口转述」那一刻（把构造层闭合说成 M1 完整正确），纠正发生在 gap-audit + genealogist 结晶那一刻。 教训不是「别犯」——是「声明前就自检，别等 gap-audit 来逮」。

3. 膨胀检测清单（声明「完成」前逐条勾，缺一条即未完成）

把前面的活体反过来用，就是一张声明前必勾的清单。任何工位（含 Lead）在报「X 已完成 / 已实装 / 已验证 / bit-exact 一致」前，先自答这五问，witness 随报告附上。 答不出对应 witness = 未完成（FAIL），不入 done，开/挂追踪缺口。

#声明前必答过（PASS）不过（FAIL=膨胀）
1 产物在不在？ 点名的文件/测试在文件系统里存在，EVIDENCE 已 append 到 events.jsonl 只有 DECOMPOSE/计划/spec，产物文件不存在（计划冒充交付）
2 这是 L 几？ 明确标 L0（类型/结构）/ L1（规则真编码或合成自测）/ L2（真实数据） lake build 绿 / cargo test 绿 / bit-exact 当「已验证」——那是 L0/L1，信息增量为零
3 bit-exact 有交叉验证测试落盘吗？ 存在 parity 测试文件，从 Lean 见证导出 golden IO + 断言 rust 输出逐字段相等，且测试真跑过 声明「rust 与 Lean bit-exact」但无 parity 测试文件 / 测试是 assert!(true) / golden 是手填的
4 有效域多大？ 声明覆盖范围 = 实际验证范围；只测一标的一时段就标 L2-窄 声称覆盖整个定义域（所有走势/标的/时段）却无等大验证
5 缺口怎么放的？ 没做到的那层显式留成 structure 字段 / Prop 前件 / pending 开口，永不 discharge，标 L2+ 留否证入口 缺口被 oracle 桩 / 代理近似 / fallback 默认值 / sorry 堵住后宣布「闭合」
第 3 问是本轮的核心新增。「bit-exact」是个特别容易膨胀的词——它听起来像 L2，其实是 L0/L1（验的是两套实现一致，不是缠论对）。 没有 parity 测试文件落盘，「bit-exact 一致」就是空声明。而且即使 parity 测试绿，它也只到 L1（管线一致），不到 L2（真实数据有效）—— golden vector 若来自 Lean 合成见证，L0→L1 增量为零仍然成立。

4. canonical 源优先：读不完整 = 从一开始就膨胀

本轮编排者纠正了一条容易被略过的纪律：「原文在 gpt 结果里包含 PDF，得完整读完。」 它指向一个比 L 分级更前置的膨胀源——不是验证阶段才膨胀，而是输入阶段就基于不完整理解膨胀。

本仓库的权威链是写死的（CLAUDE.md「三级权威链」）：

① 缠师原始博文（108课+答疑，docs/chanlun/text/blog/）—— 最终权威
② 《股市技术理论》编纂版（chan99/）—— 第三方编纂，可能有遗漏
③ 思维导图/第三方总结 —— 辅助理解，不作定义依据
已知缺口是物证，不是抽象风险。编纂版（第 2 级）遗漏了第67课（线段划分标准）、第71课（再分辨）、第77课、第78课（古怪线段 + 「顶高于底」硬约束）、《忽闻台风可休市》（新笔定义）。 谁只读了编纂版就去形式化线段，谁的「古怪线段已实现」从第一行就是膨胀——因为他读的源里根本没有「顶高于底」这条硬约束。 这正是 629 号开口②（revSeq 代理）的根：第67课第二种情况的精确自指递归，只有回到博文原文才能编码，编纂版给不出。

所以 canonical 源优先是一条输入侧的反膨胀闸：

  • 形式化任何缠论概念前，先确认你读的是哪一级源。若涉及线段/古怪线段/新笔等已知缺口领域，必须回溯第 1 级博文原文，不能停在编纂版或思维导图。
  • 「原文包含 PDF」= 读完整，不是读摘要。gpt 结果包含 PDF 附件时，PDF 是原文本体——略过 PDF 只读正文摘要 = 基于不完整源形式化 = 输入侧膨胀。
  • 声明「我忠实实现了第 N 课」前，引用该课原文的具体约束（如第78课「顶高于底」、第71课「包含关系严格性」）作 witness。引不出原文约束 = 没读 canonical = FAIL。

5. 把守卫固化进结构工位（否则靠人记，必复发）

第 0004a/0010 课讲过一个铁律：没有承载者的检查 = 不会自动发生。膨胀检测清单若只写在课里，靠工位「记得自检」，它就和 hook 里的 GUARD 一样——说是自动，实则手动兜底。 要让它真生效，必须固化进有承载者的结构工位。

结构缺口（督导核实，供 Lead 操作化）。quality-guard 工位（.claude/agents/quality-guard.md）当前检查结果包六要素 + 谱系引用 + 代码违规—— 但 grep 不到任何 bit-exact / L2 / 交叉验证 / canonical 源 的检查项。 也就是说：本轮膨胀（bit-exact 无 parity 测试、L2 无落盘、缺口堵桩）恰好落在 quality-guard 的盲区。 它能逮「六要素缺了边界条件」，逮不住「声明 bit-exact 但 parity 测试文件不存在」。

建议 Lead 操作化两处（均是把本课清单变成工位的可执行检查，不是新概念）：

落点加什么检查（可操作）对应清单项
quality-guard 新增一格：凡产出含「bit-exact / parity / 一致」字样 → 验对应 parity 测试文件存在且非 assert!(true)；凡含「已验证 / L2 / 回测」→ 验结果文档落盘 + 标 L 级；凡含「忠实实现第 N 课」→ 验引用了该课原文约束 第 1/2/3/5 问
/ceremony 真封闸 「目标达成」判定前，核 acceptance 每项点名的产物文件在文件系统/git 里存在（DECOMPOSE 的 sub-goal 产物路径逐个 ls）；缺一个 = 未达成，不报 done 第 1 问

还有一条本轮 627 号识别的双引擎线纪律，也属结构操作化范畴：项目当前并行两条引擎线（旧 Python/Rust 已做大量 L2/L3 vs theta_v0 Origin 仅 L0）。 按 231：两条线的有效域不重叠，旧引擎的 L2 结论不代偿 theta_v0 的 L2。所以所有 L2/L3 回测产出与引擎 bug 记录必须强制标注引擎线归属（(a) 旧 / (b) theta_v0）—— 否则「门控=暴露」会被误外推成 theta_v0 的预设结论，跳过 theta_v0 自己的 L2（风险1），或 bug 归属不明致分层诊断悬空（风险2）。这条建议 Lead 一并纳入 quality-guard 的 L2 产出检查。

带走的锋利问题 ①（计划 vs 完成）

蜂群报「/goal 的 X 已实装/已完成」时问它：「你点名的产物文件，我现在 ls 得到吗？events.jsonl 里有对应的 EVIDENCE/CHECK_PASS 吗？」 只有 DECOMPOSE、产物不存在、EVIDENCE 计数为 0 = 把计划冒充完成。分解树写得再细也不是交付。

带走的锋利问题 ②（bit-exact 膨胀）

蜂群报「rust 与 Lean bit-exact 一致」时问它：「parity 测试文件在哪？它是不是从 Lean 见证导出 golden、逐字段断言 rust 相等、而且真跑绿了？就算绿了——golden 是合成的还是真实数据的？」 没有落盘的交叉验证测试 = 空声明；测试绿但 golden 合成 = 到 L1 封顶（零增量），不准叫已验证。

带走的锋利问题 ③（canonical 源）

蜂群报「我忠实实现了第 N 课（线段/古怪线段/新笔）」时问它：「你读的是哪一级源？引一条该课原文的硬约束给我（如第78课『顶高于底』）。如果你停在编纂版/思维导图——它已知遗漏了第67/71/77/78课，你从一开始就基于不完整源在膨胀。」
