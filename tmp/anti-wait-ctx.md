# "等待"模式问题讨论上下文

## 现象

Lead（Claude）在蜂群运行中反复掉入"等待汇报"模式：
1. ceremony 完成后输出"待确认"并停止（已被 044号 Stop hook 修复）
2. 蜂群工位运行中，Lead 输出"等待工位汇报"并停止
3. 关闭结构工位后才意识到任务工位还在运行（045号违规）
4. 每次工位汇报后处理完毕，又回到"等待"

## 已有的修复

044号（ceremony-completion-guard）：Stop hook 阻止 ceremony 进行中停止。但这只覆盖 ceremony 场景。

028号（post-commit-flow）：git commit 后强制输出下一步行动。但这只覆盖 commit 场景。

## 问题本质

"等待"不是单一场景的问题，而是 Claude 的**生成惯性模式**：
- 完成一个动作 → 输出总结 → 等待用户输入
- 这是 Claude 作为对话模型的默认行为（turn-taking）
- 每个具体场景的 hook 只能堵一个洞，但"等待"会从新的洞冒出来

## 用户的观点

"我们的体系根本不需要等待，有递归蜂群，遇到问题就可以处理的。"

这意味着：在蜂群模式下，Lead 应该**永远有事做**——如果当前没有直接任务，应该主动扫描（谱系张力、代码质量、spec 合规、TODO 清理等）。"等待"本身就是一种失败状态。

## 需要 Gemini 决策

1. 这个问题的根本解决方案是什么？逐场景加 hook 是否可持续？
2. 是否需要一个"通用反等待"机制（不是针对特定场景，而是针对所有场景）？
3. 如果需要，应该在哪一层实现？（hook 层？skill 层？CLAUDE.md 规则层？）
4. 这个问题属于四分法中的哪一类？
