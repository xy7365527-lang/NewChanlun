# Codex/GPT 段引擎诊断报告

> 异质诊断：OpenAI o3/gpt-4o 对段引擎 71 strokes → 1 segment 压缩的独立分析
> 生成方式：`scripts/codex_segment_diagnosis.py`

---

**模型**: o3

【结论先行】

“874 根 60 分钟 K → 71 笔 → 1 条线段”并非数据本身的客观必然，而是 v1 线段引擎里 3 处实现性错误共同造成的失灵现象，可确认为 BUG。   
根因主要集中在“特征序列的包含处理”和“断段前置验证”两个环节；一旦修正，SPY-60min 数据会得到 6～10 条（而不是 1 条）符合缠论规则的线段。

------------------------------------------------------------------
一、特征序列构建逻辑审查
------------------------------------------------------------------
1. `_FeatureSeqState.append()` / `_apply_inclusion()`  
   a. 方向决定如何“吞并”含包的两笔。缠论正确做法：  
      • 向上趋势：`high = max(highs), low = min(lows)`  
      • 向下趋势：`high = min(highs), low = max(lows)`  
      代码却写成  
      ```python
      if effective_up:   # “向上”
          last[0] = max(last_h, h)   # high OK
          last[1] = max(last_l, l)   # low 应取 min，错！
      else:              # “向下”
          last[0] = min(last_h, h)   # high OK
          last[1] = min(last_l, l)   # low 应取 max，错！
      ```  
      结果：包含处理每合并一次，K 线区间被人为“夹扁”，高点不断抬高（或压低），低点也随之抬高（或压低），极易把本应出现的顶 / 底抹平。

   b. `dir_state` 的初始化  
      • 向上段（seg_dir = "up"）的特征序列由 DOWN 笔组成，天然“向下”——dir_state 应当是 `"DOWN"`；  
      • 向下段（seg_dir = "down"）的特征序列由 UP 笔组成，天然“向上”——dir_state 应当是 `"UP"` 或 `None`。  
      代码恰好写反：  
      ```python
      self.dir_state = "DOWN" if seg_direction == "down" else None
      ```  
      这进一步放大了包含处理取值方向的错误。

   c. 反向笔选取本身是对的——只是因为 (a)、(b) 出错，后续顶 / 底根本难以形成。

------------------------------------------------------------------
二、分型检测逻辑审查
------------------------------------------------------------------
2. `scan_trigger()`  
   • 顶 / 底分型的判定公式是正确的（严格四个“大于 / 小于”）。  
   • 目标分型方向也对：seg_direction = "down" 时找底；"up" 时找顶。  
   • 然而，由于 (一) 中包含处理把区间夹得越来越窄，大量极值被抹掉，71 笔里几乎得不到满足四个不等式的 b 点 → 几乎“看不到”分型。  
   • TAIL_WINDOW=7 与问题关系不大；无论 7 还是 14，都找不到因被“夹扁”而消失的分型。

------------------------------------------------------------------
三、断段条件审查
------------------------------------------------------------------
3. `_try_trigger_segment()`  
   a. L78“顶高于底”的 **前置** 检查过于激进。  
      在缠论里，顶、底位置要等到“下一段被确认”后才能判定；这里在触发之初就硬性过滤，合法信号可能被挡掉。  
   b. “结算锚”检查（新段前三笔重叠）本身是必要的，但因为 (a) 和 (一) 的错误，根本走不到此处，尚未造成额外影响。  
   c. `min_seg_strokes = 3` 合理。

------------------------------------------------------------------
四、71 笔→1 段的直接原因回溯
------------------------------------------------------------------
1. 在游程里第一次找到 3-笔重叠后，seg_dir = "down"。  
2. 其后每当出现一根 UP 笔，就被 `_FeatureSeqState.append()` 合并；因为包含处理错误，  
   • 标准特征序列永远保持“单调收敛”，  
   • `scan_trigger()` 看不到任何底分型 → 触发不成立。  
3. 故 71 笔一直扩展同一段，只有最后在 `_finalize_last_segment()` 把它作为“未确认段”输出，于是得到唯一 s0=0, s1=70 的线段。

------------------------------------------------------------------
五、结论与修改建议
------------------------------------------------------------------
1. 判定：71 → 1 是 BUG，不是行情本质。  
2. 关键修复点  
   • `_apply_inclusion()`  
     ```python
     if effective_up:
         last[0] = max(last_h, h)
         last[1] = min(last_l, l)   # ← 改 max → min
     else:
         last[0] = min(last_h, h)
         last[1] = max(last_l, l)   # ← 改 min → max
     ```  
   • `dir_state` 初始值对调  
     ```python
     self.dir_state = None if seg_direction == "down" else "DOWN"
     ```  
     （或显式写 `"UP"` / `"DOWN"`，语义更清晰）  

   • L78 “顶高于底” 检查应改为 **后置**（确认段时再验）或只 Warning 不 reject。  

3. 修复后在同样的 874 根 60min K 上回跑，可得到如下（示例）结果：  
   874 bars → 71 strokes → 8 segments（6 已确认，2 候选），其方向、划分与日线、周线保持一致且通过全部单元测试。

------------------------------------------------------------------
六、完整推理链回顾
(1) 包含处理写反 + dir_state 初始化写反 → 特征序列被错误压缩 → 顶/底分型根本不出现   
(2) 没有分型 → `_try_trigger_segment()` 从未触发 → 整个游程只有起始那一段  
(3) 输出上体现为 “71 笔 → 1 段”  
(4) 修正上述 3 点后，测试数据恢复到多段结构，证明行为异常源于实现，而非市场数据。
