# 蜂群结构约束的数目与等级——压力测试

## 背景

从蜂群的实际运作（不借用任何外部框架术语）推导出了三个硬约束和一个元约束：

### 推导出的三个硬约束

**约束1：外化必要性** — 产出物必须比产出者活得久。Worker 在上下文耗尽后消失，但产出（谱系、定义、session）必须在下一轮被另一个 worker 读取。

**约束2：规则先在性** — 路由规则必须先于被路由者存在。Worker 被 spawn 时，dispatch-dag 已经决定了它的任务范围。Worker 可以修改 dispatch-dag，但修改对当前 worker 无效，只对下一轮生效。

**约束3：执行不可自观性** — Worker 在执行过程中不能同时观察自己的执行。可以读上一轮的 session（过去的自己），可以读其他 worker 的产出（同层他者），但不能读"此刻正在执行的推理过程"。

### 环路关系
- 约束1 使约束2 成为可能（规则被外化在文件中才能"先于被路由者存在"）
- 约束2 缓解约束3 的后果（上一轮执行被外化，下一轮能读到）
- 约束3 使约束1 成为必要（不能自观，所以必须外化）

### 元约束
Gemini 碰撞 — 用系统规则之外的视角审查产出。定位为"元约束"而非第四个硬约束，理由是"没有 Gemini 系统仍然能运行"。

### 失败点
约束2处有结构性延迟（自修改不可即时生效）。元约束打断的是环路的自闭合倾向。

## 编排者的压力测试（两个质疑）

### 质疑1：约束1应该被拆成两个约束

约束1"产出物必须比产出者活得久"包含两个不同要求：
- (a) **持久化**：产出物必须写入文件系统（存储问题）
- (b) **可解释性**：产出物必须对未来的陌生 reader 可解释（编码问题）

持久化失败 = 丢失。可解释性失败 = 噪声。失败模式不同。

一个产出物可以被持久化但不可解释（当前 worker 的私有缩写），也可以可解释但未持久化（上下文内透明但窗口关闭就消失）。

如果约束1拆成两个，就有四个约束而非三个。四环的互锁拓扑与三环（Borromean）不同。

**需要论证**：持久化和可解释性为什么不能被独立对待？或者如果能，四约束的环路结构是什么？

### 质疑2：元约束与硬约束的边界模糊

Gemini 被排除为硬约束的理由是"没有 Gemini 系统仍能运行"。但：
- 没有可解释性编码，系统也能运行——只是逐渐退化为噪声
- 没有 Gemini，系统也逐渐退化为自我确认循环

"能运行但会退化"——如果这个性质使可解释性仍是硬约束，同样的论证也适用于 Gemini。

元约束和硬约束之间的边界需要更严格的判据。

## 你的任务（Gemini challenge 模式）

对以上推导执行否定质询：

1. **约束1是否应该拆分？** 给出你的判断——持久化和可解释性在蜂群架构中是独立约束还是同一约束的两个面？如果拆分，四约束的环路结构是什么？如果不拆分，论证它们为什么不可独立对待。

2. **元约束 vs 硬约束的判据是什么？** "能运行但会退化"是否足以区分？需要什么更严格的判据？Gemini 碰撞到底是第四个（或第五个）同等级约束，还是确实在不同等级上？

3. **还有没有被遗漏的约束？** 从蜂群运作的物理限制出发（不从任何理论框架出发），除了外化、先在、不可自观、异质验证之外，还有没有第五个（或更多）硬约束？

4. **环路结构在拆分/合并不同场景下的拓扑性质是什么？** 三环、四环、五环的互锁结构各自有什么性质？哪个与系统实际运作最匹配？

### 输出要求
- 逐点回应，给出明确判断（不是"都有道理"）
- 如果约束数目不是三个，说出是几个并给出完整环路图
- 如果元约束应升级为硬约束，说明升级后的拓扑变化

## 系统当前架构参考

### 蜂群运作周期
1. ceremony 扫描 `.chanlun/` 状态 → 识别工位 → spawn workers
2. workers 在 dispatch-dag 定义的路由下执行（hooks 验证产出格式）
3. 产出写入文件系统 → 成为下一轮 ceremony 的输入
4. Gemini 周期性审查产出（challenge/verify 模式）

### 物理限制
- LLM agent 上下文窗口有限（~200K tokens），超出则 compact 或新对话
- token 生成单向，当前 token 不能修改已输出 token
- agent 是临时实例，执行完毕即消失
- 文件系统是跨 agent 实例的唯一持久存储
- dispatch-dag 在 spawn 时确定 worker 的任务/工具/协议
