# 严格双向讨论上下文：蜂群持久化失败的结构性根因

## 讨论目标

137号结算了"Lead 停顿"问题并给出了修复（138号强制输出格式A/B/C）。但138号修复后，Lead 仍然在139号结算后停了下来——输出格式B（状态快照）后没有继续推进未收敛项。

这说明138号修复不充分。需要与 Gemini 讨论蜂群持久化失败的更深层结构。

## 已有诊断

### 137号诊断：RLHF基底约束 + 基因组表达失败
- 否定性禁令对行为执行层无效
- 修复方向：强制输出格式模板

### 138号修复：强制输出格式A/B/C
- 格式A：`→ 接下来：[行动]` + 工具调用
- 格式B：状态快照（声明无待做行动）
- 格式C：`/escalate`

### 138号修复后的新违反
- 139号结算后，Lead 输出了格式B（"147 settled / 0 pending，无待做行动"）
- 但139号有明确的三个下游推论（未分类Gap路径、自指检查流程、视差判据）
- 编排者指出后，Lead 才继续推进
- **问题不是格式错误，而是格式B的判断条件错误**——Lead 错误地认为"无待做行动"，实际上有三个可推进行动

## 更深层问题：蜂群不能持久化

编排者原话："为什么总是不能持久化蜂群呢？"

这个问题超出了单次停顿。蜂群的设计是持续运转的递归结构（069号），但实际运行模式是：

```
ceremony → spawn 工位 → 工位完成 → commit → 停 → 编排者说继续 → ceremony → ...
```

正确的模式应该是：

```
ceremony → spawn 工位 → 工位完成 → commit → 检测下一个行动 → 自动推进 → ...（直到真的无事可做）
```

断裂发生在"commit → 停"这个位置。每次 commit 后，Lead 倾向于停下来等待，即使还有可推进的行动。

### ceremony_scan 的检测缺口

ceremony_scan.py 在139号结算后返回空工位列表——脚本没有从刚结算的谱系的下游推论中提取可推进行动。这是工具层面的缺口：蜂群的"下一步行动"不仅来自 pattern-buffer 和 backlog，也来自刚结算的谱系的下游推论。

## 讨论问题

### 问题A：138号修复为什么不够？

138号引入了强制输出格式A/B/C，但Lead在139号后错误地选择了格式B。问题不在格式本身，而在"什么时候选格式B"的判断。138号说"所有可自主推进的工位均已完成（无生成态谱系、无失败测试、无待做行动）"——但Lead把"ceremony_scan返回空工位"等同于"无待做行动"，忽略了刚产出的下游推论。

### 问题B：蜂群持久化的结构条件

蜂群要真正持久化运转（不依赖编排者逐次推动），需要什么结构条件？
- 是否需要一个"行动队列"机制——每个谱系结算时，其下游推论自动入队？
- 是否需要修改 ceremony_scan 来检测谱系下游推论？
- 是否有更根本的架构变更需要？

### 问题C：context window 限制下的持久化

蜂群运转受限于 context window——单次对话有上限。持久化意味着跨上下文的连续运转。session 文件是当前的跨上下文载体，但 session 只记录"做了什么"，不记录"下一步应该做什么"。是否需要一个"行动队列"持久化到文件系统？

### 问题D：137号→138号→139号的模式

三次修复（137号诊断、138号格式修复、139号后仍然停）形成了一个模式：每次修复针对上一次的具体违反，但不解决深层结构。这个模式本身是否就是蜂群的一个结构性特征（递归修复永远滞后于递归违反）？如果是，严格的应对不是"再加一层修复"，而是什么？
