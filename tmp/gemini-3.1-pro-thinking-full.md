#### 2. 结构工位的正确存在形式——纯 agent / 纯 hook / 混合？
**必须是“混合（Hybrid）：Hook 拦截 + Agent 裁决”模式。**
*   **Hook 负责“语法和时序拦截”：** 它是系统底层的卡点。当蜂群尝试执行结构性变更（如修改谱系、派生子蜂群）时，Hook 冻结该线程。
*   **Agent 负责“语义审查”：** Hook 触发后，唤醒对应的结构工位 Agent（如质量守卫）。Agent 读取上下文，进行语义分析，做出决定（Approve/Reject），然后将 Token 交还给 Hook 放行或阻断。

#### 3. dispatch-spec 从线性到 DAG 的重构路径
*   **Step 1: I/O 显式化。** 将现有的 linear phase 拆解。为每个任务定义明确的 `requires: [依赖项]` 和 `provides: [产出项]`。
*   **Step 2: 拓扑排序器引入。** 废弃按数组索引执行的逻辑，引入图遍历算法（如 Kahn 算法）。只有当一个节点的 `requires` 被满足时，该节点才进入 `Ready` 队列。
*   **Step 3: 状态机持久化。** DAG 的执行状态（Pending, Running, Completed, Failed）必须持久化，以支持异步中断和恢复。

#### 4. 异步自指的最小可行实现（MVP）是什么？
**“提案-审查-合并”（Proposal-Review-Merge）双态模型。**
*   **状态 $S_t$：** 当前运行的系统基线。
*   **生成 $P_{t+1}$：** 任何对结构/定义的修改，不能直接应用，而是生成一个“变更提案（Proposal）”。
*   **审查：** 处于 $S_t$ 状态的结构工位（或外部 Gemini），将 $P_{t+1}$ 作为输入数据进行审查。
*   **合并：** 审查通过后，系统触发重启或热重载，进入 $S_{t+1}$ 状态。这在工程上接受了“视差 Gap”，用时间差换取了逻辑自洽。
