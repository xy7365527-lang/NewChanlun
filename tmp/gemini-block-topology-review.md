## 维度1：与现有谱系体系的一致性

**评价：缺口——方案未定义与现有体系的严格关系**

### 现状

现有谱系体系由三个互相耦合的组件构成：

1. **dag.yaml**：nodes（177+条，每条含 id/title/status/type/file）+ edges（depends_on 列表，from→to 形式）。纯声明式，边的语义由 type 字段隐含。
2. **settled/*.md**：每条谱系的完整 frontmatter + 正文。携带 negation_form、topo_effect 等结构化字段。
3. **ceremony_scan.py + topology_operator.py**：读取上述两个数据源，执行工位发现和拓扑操作。

### 方案引入的三层架构

- Event Layer：SHA256 内容寻址的 JSON 区块
- Relation Layer：JSONL 追加式关系图
- Reflexive Layer：rewrite 区块的递归闭合

### 矛盾点

方案第94-100行自己列出了五个"待讨论"问题，但这些不是待讨论的——它们是方案能否落地的**前提条件**。具体分析：

1. **数据模型不兼容**：dag.yaml 的 edges 是无类型的 depends_on 列表（只有 from/to），而 Relation Layer 要求每条边携带 relation 类型（negates/supersedes/residue_of/reopens）。这不是扩展，是**模型替换**——现有 edges 需要全部重新标注关系类型。

2. **节点粒度不匹配**：dag.yaml 的一个 node 对应一条谱系（如 005 号），方案的一个 block 对应一个**事件**（如一次共识、一次让步）。一条谱系的生成过程可能包含多个事件。粒度从"谱系条目"细化到"原子事件"是合理的演化方向，但177条现有谱系的粒度转换规则未定义。

3. **替代 vs 并存的二难**：
   - 如果**替代**：需要迁移177条谱系 + 重写 ceremony_scan.py 和 topology_operator.py + 重写所有读取 dag.yaml 的脚本。迁移期间两套系统的一致性由谁保证？
   - 如果**并存**：两套系统描述同一组谱系关系，数据一致性问题不可回避。谁是 single source of truth？

### 修正建议

方案需要在落地前**先回答**：这是对现有 dag.yaml 体系的替代还是升级。如果是替代，定义迁移协议（包括回滚条件）。如果是升级，定义 dag.yaml → Relation Layer 的严格映射，使现有工具链可以渐进适配。

## 维度2："事件不可变，拓扑可变"的严格性

**评价：自洽，但边界需要显式化**

### 命题分析

"事件不可变，拓扑可变"在方案内部是自洽的：Event Layer 只追加不修改，Relation Layer 通过追加新关系实现"变更"。这符合 append-only 的不可变性语义。

### 与现有 topo_effect 的张力

现有 topology_operator.py 的 freeze/split/sever 操作**直接修改 dag.yaml 节点状态**（如标记 node.frozen = true）。这在方案的框架下是什么？

- 冻结一个节点 = 修改了节点的状态字段 → 这是"事件变化"（修改了已写入的记录）
- 但在方案的框架下，应该是：写入一个 type=event 的新区块（记录冻结操作）+ 在 Relation Layer 追加 relation=freezes 的新边

**现有实现与方案原则矛盾**：topology_operator.py 直接 mutate dag.yaml 节点（in-place 修改），这恰好是方案要否定的模式。方案要求所有状态变更都表达为新区块+新关系。

### 修正建议

如果方案落地，topology_operator.py 需要重写：从"修改 dag.yaml 节点状态"变为"在 Event Layer 写入拓扑操作区块 + 在 Relation Layer 追加关系"。dag.yaml 中的节点状态变为**从 Relation Layer 推导的视图**而非直接存储。这是一个重大架构变更，应该被显式识别。

## 维度3：共识仪式与现有 plan-review 的关系

**评价：缺口——方案中的"共识仪式"与 plan-review skill 功能重叠但语义不同**

### plan-review 现状

plan-review skill（`.claude/skills/plan-review/SKILL.md`）已经实现了：
- Opus 出方案 → Codex 评审 → 多轮对审直到达成共识
- 终止条件：Codex 显式确认满意
- 6轮未收敛走 /escalate
- 结果持久化到 `.chanlun/review-results/`

### 方案的共识仪式

每次 Gemini-Codex 质询收敛时，生成三个原子区块：
1. consensus 区块（结论）
2. residue 区块（让步清单）
3. tension 区块（未决张力）

### 关系判定

两者不是替代关系，而是**抽象层级不同**：

- plan-review 是**过程协议**（谁审谁、几轮、怎么终止）
- 共识仪式是**数据模型**（共识产出的结构化表达）

但方案没有说清楚：
1. plan-review 的输出是否自动转化为共识仪式的三个区块？
2. 如果是，residue 和 tension 的提取规则是什么？plan-review 当前的输出格式（`.chanlun/review-results/plan-review-{timestamp}-round{N}.md`）中没有结构化的"让步清单"和"未决张力"字段。
3. 如果不是，共识仪式是 plan-review 之外的独立流程——那么两套共识机制的触发条件如何区分？

### 修正建议

共识仪式应定义为 plan-review 的**输出格式升级**，而非独立的新流程。具体地：plan-review 的 Phase 4（方案定稿）增加 residue/tension 的结构化提取步骤，输出格式从 Markdown 扩展为三个区块。这样共识仪式是 plan-review 的自然延伸，而非并行的新协议。

## 维度4：Reflexive Layer 的递归终止条件

**评价：缺陷——无显式终止条件，且方案声称"递归自动闭合"未给出论证**

### 问题陈述

方案第47-50行：
> 每当 Relation Layer 被追加时，同时在 Event Layer 写入一个 type="rewrite" 的区块。rewrite 区块的 id 又可以出现在后续关系记录的 created_by 字段中。递归自动闭合。

这里"递归自动闭合"是一个**断言**，没有给出闭合的条件。

### 分析

- 新关系追加 → 触发 rewrite 区块写入 → rewrite 区块可能触发新关系追加 → 触发新 rewrite 区块 → ...
- 如果每次 Relation Layer 变更都**必然**触发新关系追加，这是无限递归
- 如果存在"某些 Relation Layer 变更不触发新关系追加"的条件，这个条件就是终止条件——但方案没有定义它

### 与递归总方针的对照

递归总方针明确提到递归有"铁壁垒"（承重点）作为内在停止条件。但方案的 Reflexive Layer 没有对应的停止机制。递归总方针的停止是**语义层**的（当否定会摧毁谱系一致性时停止），而 Reflexive Layer 需要的是**操作层**的终止条件（什么条件下 rewrite 不再生成新 rewrite）。

### 修正建议

两种可能的终止条件设计：

1. **幂等条件**：如果一个 rewrite 区块的关系变更不改变 Relation Layer 的拓扑结构（如只是重复已有关系），则不生成新 rewrite 区块。这是最小终止条件。

2. **深度限制**：rewrite 区块的 refs 链深度有上界。超过上界时标记为奇点（对应方案中的"持续不收敛"检测）。

建议采用方案1作为默认终止条件，方案2作为安全网。

## 维度5：SHA256 内容寻址与 git 的冗余

**评价：矛盾——方案引入了与 git 功能冗余的内容寻址层**

### git 已有的能力

git 对每个文件计算 SHA-1（或 SHA-256，取决于版本）哈希作为 blob object。git 的 commit 就是内容寻址的：给定相同内容，得到相同 hash。

### 方案的 SHA256 寻址

方案要求每个区块的文件名为内容的 SHA256 哈希。这与 git 的 blob 寻址在功能上完全重叠：
- 两者都实现内容不可变性（相同内容 = 相同 hash）
- 两者都可以通过 hash 检索内容
- 两者都可以检测内容篡改

### 不同之处

方案的 SHA256 hash 是**应用层**的（区块内容的 hash），git 的 hash 是**存储层**的（文件内容的 hash，还包含 git 头信息）。应用层 hash 的优势是：可以在不依赖 git 的环境中验证完整性。

### 判定

如果系统始终运行在 git 仓库中（当前就是这样），应用层 SHA256 与 git 的内容寻址是冗余的。方案第107行自己也提出了这个问题。

### 修正建议

两种方案，取决于设计意图：

1. **如果区块拓扑必须独立于 git**（例如未来可能迁移到非 git 环境）：保留 SHA256，但需要显式声明"区块拓扑是 git 无关的"这一架构决策。
2. **如果区块拓扑依赖 git**（当前事实）：用 git blob hash 替代自定义 SHA256，区块文件名用语义命名（如 `{timestamp}-{type}-{short_hash}.json`），内容完整性由 git 保证。推荐此方案——减少一层不必要的抽象。

## 维度6：Real/对象a 的形式化程度

**评价：缺口——"residue = 对象a"是类比而非操作性定义**

### 方案的表述

方案第59-77行用拉康框架描述：
- 被排除的东西 = 奇点 = 对象a
- residue 区块记录"为达成共识而放弃的部分"
- 持续不收敛的拓扑位置 = 奇点

### 问题

1. **"对象a"的操作性判据缺失**：如何区分一个 residue 是"结构性的对象a"（指向系统不可解决的根本矛盾）还是"技术性的让步"（为了效率/时间而暂时搁置）？方案没有给出判据。

2. **奇点检测的阈值未定义**："同一个拓扑位置被反复改写且持续不收敛"——"反复"是几次？"持续"是多长？"不收敛"的判据是什么？

3. **与现有体系中"承重点"概念的关系**：递归总方针定义了"承重点"（不可否定的拓扑产物）。奇点和承重点是什么关系？一个奇点（持续不收敛的位置）是否可能同时是承重点（不可否定的位置）？如果是，这两个概念的区分标准是什么？

### 修正建议

1. **residue 的二分类**：定义一个结构化字段区分 residue 类型——`structural`（指向定义层矛盾，不可通过工程手段解决）vs `pragmatic`（技术性让步，可在后续迭代中解决）。分类判据：如果解决该 residue 需要修改至少一条已结算谱系的定义，则为 structural；否则为 pragmatic。

2. **奇点检测的操作性定义**：给出具体阈值。建议：同一拓扑位置（定义为同一组 node 之间的关系）在 N 次共识仪式中产生 residue，且 residue 类型为 structural，则标记为奇点。N 的初始值可设为 3（可调整）。

3. **奇点与承重点的关系**：二者互斥。承重点是递归运动中不可否定的稳定产物（铁），奇点是递归运动中不可解决的不稳定位置（裂缝）。承重点使系统稳定，奇点使系统运动。

## 总结

| 维度 | 评价 | 严重度 |
|------|------|--------|
| 1. 与现有谱系体系的一致性 | **缺口** | 高——不解决无法落地 |
| 2. 事件不可变/拓扑可变 | **自洽**（但与现有实现矛盾） | 中——需要 topology_operator.py 重写 |
| 3. 共识仪式与 plan-review | **缺口** | 中——应定义为 plan-review 输出升级 |
| 4. 递归终止条件 | **缺陷** | 高——无终止条件的递归是无限递归 |
| 5. SHA256 与 git 冗余 | **矛盾** | 低——可通过架构决策消解 |
| 6. Real/对象a 形式化 | **缺口** | 中——需要操作性定义 |

### 整体判断

方案的**方向是正确的**——从"静态 DAG + Markdown 谱系文件"演化为"事件驱动 + 关系可追溯 + 递归闭合"的拓扑结构，符合递归总方针的精神。但方案当前处于**概念草案**阶段，距离可执行的工程规格有以下缺口需要填补：

1. 与现有体系的迁移/共存协议
2. Reflexive Layer 的操作性终止条件
3. 共识仪式与 plan-review 的集成方式
4. residue/奇点的操作性判据
