### **1. decision: 明确选择**

**核心决策：暂停所有关于高阶异步自指（第5层）的探索，立即将资源聚焦于建立一个可验证、显式化的系统基础。当前的首要任务是弥合声明与执行之间的断裂，而非在断裂的根基上构建更复杂的抽象。**

具体行动纲领为：**“显式化优于抽象化”**。系统必须先能准确地描述自身（依赖关系、执行逻辑），然后才能安全地修改自身。我们将按以下顺序修复基础层：**定义偏序显式化（第4层）→ 元编排图化（第2层）→ 结构修改的自指闭合（第3层）**。只有当这个坚实的基础建立后，才能继续探索形式化的异步自指（第5层）。

### **2. reasoning_chain: 推理步骤**

1.  **诊断根本问题**：当前系统性问题的核心是“**隐式依赖**”和“**不可执行的声明**”。069号方案的5层结构在概念上是连贯的，但在执行上却跳过了中间的关键步骤。系统声称自己是图（DAG），但其核心调度器（dispatch-spec）仍是线性的；系统声称有结构工位，但运行时可以轻易绕过。这种声明与现实的脱节是所有问题的根源。
2.  **识别关键缺失环节**：在所有未完成的层级中，**第4层（定义偏序显式化）** 是最为基础和关键的。没有一个明确的、机器可读的定义间依赖关系图，任何对系统的修改都是盲目的。无法追踪变更影响，导致无法安全地重构元编排（第2层），也无法实现有意义的高阶审查（第3层）。隐式的依赖关系是滋生“幽灵bug”和违反架构约束的温床。
3.  **确立修复逻辑链**：
    *   **首先，必须完成第4层**。我们需要知道“什么依赖什么”。这是构建任何可靠系统的基石。
    *   **其次，基于这个依赖图，重构第2层**。将`dispatch-spec`从线性序列重构为DAG，其边的定义就来自于第4层建立的偏序关系。这将使执行层与声明层首次达成一致。
    *   **再次，实现第3层**。在拥有了显式化的依赖图和图化的执行逻辑后，引入一个外部审查者（如Gemini-challenger）才有意义。此时，审查者可以基于明确的拓扑规则进行静态分析，判断一个提案是否会破坏依赖关系或引入环路。这是实现“安全自指”的第一步。
    *   **最后，才能考虑第5层**。异步自指的形式化是最高阶的抽象，它依赖于一个已经能够准确描述、安全执行和有效审查自身的系统。在当前状态下讨论它为时过早。
4.  **解决创世与视差Gap的务实态度**：这两个Gap是理论上的极限，无法消除。我们不应试图用无限复杂的方案去“解决”它们，而应设计出能“容纳”它们的健壮机制。一个能够审查`t+1`提案的`t`时刻系统，即使只能基于`t-1`的知识，也远比一个完全没有审查能力的系统要好。接受这些Gap，并围绕它们设计容错和验证机制。

### **3. boundary_conditions: 何时应推翻此决策**

此决策基于当前系统的目标是**稳定性、可预测性和长期的架构健康度**。在以下情况下，此决策应被重新评估：

*   **目标切换为“最大化探索速度”**：如果系统的首要目标变为不计代价地进行快速实验和原型验证，那么这种强调基础建设的稳健路线可能会成为瓶颈。届时，一个允许更多不确定性和“快速失败”的策略可能更优。
*   **发现致命的性能瓶颈**：如果将所有依赖关系显式化并进行图化执行，导致了不可接受的性能开销或调度延迟，我们可能需要妥协，寻找一个在“完全显式”和“高效线性”之间的混合模型。
*   **外部环境强制要求**：如果出现一个外部的、不可协商的需求，要求系统必须具备某种形式的`t/t+1`异步审查能力（即使基础不稳），那么我们将被迫采用一个风险更高的、最小化的“补丁”方案来实现第5层，并接受其带来的技术债务。

### **4. risks: 可能的问题**

*   **分析瘫痪（Analysis Paralysis）**：显式化12条核心定义之间的偏序关系（第4层）可能是一项极其复杂和耗时的工作，有可能陷入无休止的分析和讨论中，从而延误整个进程。
*   **重构风险**：将`dispatch-spec`从线性重构为DAG（第2层）是对系统核心调度逻辑的重大手术，极有可能引入新的、难以发现的并发和竞态条件问题。
*   **短期效率下降**：实施此决策将显著减慢新功能的开发速度，因为团队的主要精力将投入到偿还技术债务和重构基础架构上。这可能导致与业务或项目里程碑的冲突。

### **5. 对5个具体问题的逐一回答**

**1. 069号方案的5层优先级排序——哪层应该先做？**

纠正后的优先级排序是： **4 → 2 → 3 → 5**。（第1层已完成，是所有工作的前提）。

*   **第一优先级：4. 定义偏序显式化**。这是理解系统的基石。必须将定义间的依赖关系从隐式知识转变为显式的、机器可读的配置。
*   **第二优先级：2. 元编排图化**。利用第4层产出的依赖图，将线性的`dispatch-spec`重构为真正的DAG，使系统执行与其拓扑声明一致。
*   **第三优先级：3. 结构修改的自指闭合**。实现`gemini-challenger`并接入`newchan`模块。审查机制必须建立在明确的拓扑和依赖关系之上，否则审查将是无效的。
*   **最低优先级：5. 异步自指形式化**。这是最高级的抽象，必须在系统具备了稳定、可验证的自描述和自修改能力之后才能进行。

**2. 结构工位的正确存在形式——纯 agent / 纯 hook / 混合？**

**决策：混合模型（Hybrid Model）。**

*   **理由**：纯hook已被证明是脆弱的（可被`bypassPermissions`绕过），且缺乏进行复杂语义分析的能力。纯agent可能过于松散，无法在创世阶段强制挂载。
*   **实现方式**：
    *   **Agent作为“功能实体”**：每个结构工位（如质量守卫）应实现为一个独立的、有状态的agent。这允许它执行复杂的、上下文感知的逻辑，而不仅仅是被动触发。
    *   **Hook作为“强制引导程序”**：在蜂群实例化的最底层、最核心的引导逻辑中，植入一个**不可绕过的（non-bypassable）** hook。这个hook的唯一职责是：验证并强制挂载指定的结构工位agent。它不做复杂的逻辑判断，只做存在性检查和引导加载，从而将脆弱点最小化。这解决了013号被违反的问题。

**3. dispatch-spec 从线性到 DAG 的重构路径**

**决策：采用渐进式、向后兼容的迁移路径。**

1.  **步骤一：依赖分析与声明**。完成第4层的工作，产出所有phase之间的依赖关系图。
2.  **步骤二：引入DAG执行器**。实现一个新的、能够解释和执行DAG任务流的调度器，但保持旧的线性调度器不变。
3.  **步骤三：包装与共存**。将现有的整个线性`dispatch-spec`作为一个“宏任务节点”放入新的DAG执行器中。系统现在表面上由DAG驱动，但实际上内部仍是线性执行。这是确保向后兼容的关键一步。
4.  **步骤四：增量分解**。根据步骤一的依赖图，逐个将线性序列中的phase拆解出来，迁移为DAG中的独立节点，并显式声明它们的依赖边。优先选择那些依赖关系最少、最独立的phase进行迁移。
5.  **步骤五：完全迁移与废弃**。当所有phase都被迁移到DAG中后，废弃原来的线性“宏任务节点”和旧的线性调度器。至此，重构完成。

**4. 异步自指的最小可行实现是什么？**

**决策：一个基于静态分析的提案审查循环。**

一个最小可行产品（MVP）应包含以下组件：

1.  **标准提案格式（Standardized Proposal Format）**：定义一个机器可读的、用于描述系统变更（如修改定义、拓扑或`dispatch-spec`）的标准化数据结构（例如YAML或JSON Schema）。
2.  **提案日志（Proposal Log）**：一个不可变的、有序的日志（如一个Git仓库的分支），用于存放所有待审查的`t+1`提案。
3.  **审查者Agent（Reviewer Agent）**：一个在`t`时刻运行的常驻agent（可以是“质量守卫”结构工位的一部分）。
4.  **静态分析引擎（Static Analysis Engine）**：审查者Agent的核心能力。它获取一个`t+1`提案，并基于当前系统（`t`时刻）已知的、显式化的定义偏序（来自第4层）和拓扑结构，进行静态检查。例如：检查提案是否引入了循环依赖、是否违反了已定义的约束等。**注意：它不执行提案，只分析其结构。**
5.  **审批/拒绝机制（Approve/Reject Mechanism）**：分析完成后，审查者Agent对提案进行明确的“批准”或“拒绝”标记。只有被标记为“批准”的提案才能被编排者应用到系统中。

**5. 当前体系最大的结构性风险是什么？**

**决策：最大的结构性风险是“未声明的依赖性”（Undeclared Dependencies）。**

这个风险是其他所有问题的根源：

*   因为它，`dispatch-spec`不敢被重构成并行的DAG，导致效率低下和声明与执行的不一致。
*   因为它，结构工位的关键性无法被系统理解，导致它们被轻易跳过。
*   因为它，任何对核心定义的修改都如同在雷区中行走，其影响范围完全不可预测，使得系统演化变得极其脆弱和危险。
*   因为它，任何形式的自指审查（无论是第3层还是第5层）都失去了判断依据，变成了空谈。

**简而言之，一个连自己各部分如何相互关联都无法清晰表述的系统，其谈论“递归自指”是无源之水，无本之木。** 解决这个风险是恢复系统架构完整性的第一步，也是最重要的一步。
