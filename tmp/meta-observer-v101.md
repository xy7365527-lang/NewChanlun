## 观察 1（编排者方向一致性）：换线后的第一轮——验证而非构建

### 现象

v100 开启了新主线（多 TF 集成），v101 是这条新主线的第二轮。两者的关系：

| 维度 | v100 | v101 |
|------|------|------|
| 编排者方向 | 构建 MultiTFPipelineAdapter | 用真实数据验证 v100 产出 |
| 工位数 | 1（multi-tf-integration） | 1（real-data-validation） |
| 产出类型 | 工程模块 + 测试 | 验证脚本 + 经验证据 + 谱系 |
| 新代码量 | ~466行模块 + ~527行测试 | ~579行验证脚本 |
| 核心管道变更 | 否（adapter 模式） | 否（只读验证） |
| 谱系产出 | 246号（工程集成） | 247号（经验验证） |

v100→v101 形成了 "构建→验证" 的经典工程对：先搭桥，再测试桥能不能走通。编排者明确约束了 v101 的范围：不引入纤维丛双管道对比，先让多 TF 管道独立验证。

### 判定

**正面——编排者方向控制精准。** 不急于在新主线上铺更多代码，先用真实数据检验 v100 的声明（T6 有条件可达、方向性力度背驰产生信号）。结果两项声明都未在真实数据上兑现——这正是验证的价值。

## 观察 3（验证结果与谱系声明一致性）：JSON 数据交叉验证

### 现象

对比 `tmp/real-data-multi-tf-validation.json` 与 247号谱系的叙事。

| 谱系声明 | JSON 数据 | 一致性 |
|---------|----------|--------|
| daily 502 bars, 36 strokes, 3 segments | daily: bar_count=502, stroke_count=36, segment_count=3 | **一致** |
| weekly 105 bars, 6 strokes, 1 segment | weekly: bar_count=105, stroke_count=6, segment_count=1 | **一致** |
| 60min 874 bars, 71 strokes, 1 segment | 60min: bar_count=874, stroke_count=71, segment_count=1 | **一致** |
| daily(6m) 126 bars, 9 strokes, 1 segment | daily: bar_count=126, stroke_count=9, segment_count=1 | **一致** |
| T6 所有数据集均不可达 | t6_reachable_any=false | **一致** |
| 方向性/振幅背驰均为 0 | directional_divergences_total=0, amplitude_divergences_total=0 | **一致** |
| 所有 TF zhongshu=0, moves=0 | 四个 TF 的 zhongshu_count=0, move_count=0 | **一致** |

### 60min 方向异常

247号指出 60min 数据 "direction=down, high=697.84, low=634.92"，但"实际市场在此期间上涨了约 10%"。JSON 确认：60min 的单一线段 direction=down。这不是 247号的观察错误——它反映了段引擎在强单边市中的方向判断问题。71 strokes 被压缩为 1 segment (direction=down)，意味着段引擎选择了 stroke[0] 到 stroke[70] 的方向为下行，但整段期间市场整体是上行的。这是 D2 压缩的另一个维度：不仅数量压缩（71→1），方向也可能与市场整体方向不一致。

分类：**边界观察**——这是 D2 段引擎问题的已知表现（237号覆盖），不是新问题。但 247号在此处的观察增加了一个具体的维度：D2 压缩不仅是数量级问题，还有方向正确性问题。

### 判定

**谱系叙事与 JSON 数据完全一致，无数值矛盾。** 60min 方向异常是 D2 问题的已知表现。

## 观察 5（验证脚本代码审计）：real_data_multi_tf_validation.py

### 正面

1. **验证设计合理**：两组数据（日线+周线 2年、60min+日线 6月），每组分别用方向性力度和振幅力度运行，形成 2×2 的验证矩阵
2. **诊断层次丰富**：不仅报告 T6 可达/不可达，还逐层报告管线各阶段（bars→strokes→segments→zhongshu→moves），精确定位 D2 压缩
3. **力度对比设计正确**：同一数据集用两个 adapter（`use_directional_force=True/False`）运行，保证除力度方法外其他变量一致
4. **异常处理诚实**：`try/except` 仅在数据拉取失败时使用（yfinance 网络依赖），不吞掉管线内部异常
5. **输出可复现**：JSON 结构化输出，包含完整的管线阶段数据，可作为后续验证的基线

### 需注意

1. **yfinance 依赖的时效性**：脚本依赖实时 yfinance 数据拉取。不同时间运行会得到不同数据（市场持续变化）。247号 JSON 是 2026-02-28 的快照，后续重新运行的结果可能不同。这不是脚本缺陷——是真实数据验证的固有特征。但如果需要可复现的回归测试，应该考虑固定数据集。

   分类：**边界观察**——当前不影响 247号结论的有效性（结论是关于"当前管线在当前数据上"的表现），但未来的 regression test 场景需要注意。

2. **`_df_to_bars` 中 timezone 处理**（第99-100行）：当 yfinance 返回 naive datetime 时，脚本硬编码为 UTC。yfinance 的 intraday 数据实际是交易所时区（ET），但由于管线内部不依赖绝对时间（只依赖 bar 序列），这个 timezone 偏差不影响验证结果。

   分类：**边界观察**——不影响正确性，但如果未来需要精确的时间戳匹配（如与外部数据源对齐），需要修正。

## 观察 7（元规则一致性）：蜂群面对否定性结果的处理模式

### 现象

v101 的核心结果是**否定性**的：T6 不可达，背驰为 0。蜂群对否定性结果的处理值得观察。

247号的处理模式：
1. **诚实报告**：没有淡化否定结果（"T6 在真实数据上不可达"，不是"T6 接近可达"或"部分可达"）
2. **归因精确**：不是笼统地说"数据不够"或"需要更多测试"，而是精确定位到 D2 压缩（71→1 极端案例）
3. **区分架构正确性与上游瓶颈**：明确 246号架构本身无误（合成数据 26 测试通过），瓶颈在段引擎
4. **不急于修复**：没有在验证脚本中加 workaround 让 T6 看起来可达，也没有提出"降低中枢门槛"之类的补丁方案
5. **下游推论指向根因**：所有推论都收敛到 D2 段引擎，而不是发散到多个可能的修复方向

这与 no-patch-mentality（090号）和 no-workaround 的精神一致：面对否定性结果，严格记录而非回避。

### 判定

**正面——否定性结果的处理模式符合蜂群语法。**

## 核心发现

1. **247号六要素完整，JSON 数据与谱系叙事完全一致**——无数值矛盾，无声明膨胀。

2. **v100 下游推论3 已验证为否定**：多 TF 架构在当前段引擎下不能替代递归深度。每个 TF 内部的 D2 压缩独立累积，多 TF 不能绕过。

3. **否定性结果的处理模式符合蜂群语法**——诚实报告、精确归因、区分架构与上游、不加补丁、下游推论收敛到根因。

4. **60min 方向异常是 D2 压缩的新维度**——不仅数量压缩（71→1），段方向也可能与市场整体方向不一致。这是 237号诊断的延伸，不是新问题。

5. **无规则违反**。代码审计确认行数上限、immutability、adapter 模式一致性、六要素完整性均符合。
