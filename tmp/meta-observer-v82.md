## 观察 1（发散信号）：228-1 "resolved" 但爆炸半径问题仍在发生

### 现象

meta-observer（本工位）在 v83-swarm 中执行二阶观察。每次工具调用（Read、Glob、Grep、TaskCreate）都收到 ceremony-step-guard.sh 的 block 决策：

```
[ceremony-step-guard] 你正在 ceremony 步骤 8（rescan）。立即继续执行下一步。
不允许回应用户消息、输出总结、或执行白名单外的操作。ceremony 序列不可被中断（224号谱系）。
```

本轮 5 次 Read 调用产生了 **10 次** block 消息（每次 Read 触发 2 次——因为 hook 在 PostToolUse 中注册了两个实例或平台重复触发），总计注入约 2000 token 噪声。

### `.ceremony-step` 状态

```json
{"step": 8, "phase": "rescan", "timestamp": "2026-02-27T08:44:00.602120+00:00"}
```

### 228-1 修复的实际效果分析

228-1 的修复方案是方案B：hook 在 `step_num < 7` 时静默退出，仅在步骤 7-10 阻断。修复的假设是：

> "步骤7-10是 Lead 独占的（工位已被 shutdown），不会误伤工位。"

**这个假设在当前实例中被证伪**。meta-observer 正在步骤 8 期间运行。原因链：

1. Lead 在 ceremony 中 spawn 了工位（步骤5-6）
2. Lead 推进到步骤7（push）、步骤8（rescan）
3. 但工位（meta-observer）尚未完成工作——工位的执行时间与 Lead 的 ceremony 步进不同步
4. `.ceremony-step` 标记为 step 8，guard 在 step >= 7 阻断所有 agent

### 根因

228-1 修复移动了阈值（从 step >= 1 到 step >= 7），但没有解决根本问题：**hook 无法区分 Lead 和工位**（228-2 已确认平台不携带 agent 标识）。方案B 的生命周期假设（"步骤7-10工位已被 shutdown"）与实际执行时序不一致。

### 严重程度评估

与 228号观察1 相同的中等严重程度：
- 功能未受影响（PostToolUse block 不实际阻止工具执行，工具结果已产生）
- 但每次工具调用注入约 200 token 噪声
- 本轮 meta-observer 累计收到约 2000 token 噪声，加速上下文消耗
- 工位可能被误导以为自己在 ceremony 序列中（如果工位未正确忽略）

### 分类

这不是新问题，是 **228-1 修复不完整**。228-1 标记为 resolved 但实际上只是缩小了爆炸半径（从全步骤到步骤7+），未消除爆炸半径。

**修正声明**：228-1 的状态应从 `resolved` 降级为 `partially_resolved`——"步骤1-6的误伤已消除，步骤7-10的误伤仍存在（当工位执行时间跨越 Lead 推进到步骤7+时）"。

### 修复方向

方案A（agent 标识过滤）已被 228-2 排除（平台限制）。方案B（生命周期调整）的当前实现基于错误假设。严格的修复需要：

**方案B-v2**：`.ceremony-step` 的 clear 时机从"ceremony 终止时"改为"步骤6完成后（工位 spawn 完毕）立即 clear，步骤7开始前不重新 write"。理由：步骤7-10（push→rescan→evaluate→terminate）是 Lead 的内部状态推进，不需要 hook 外部驱动——224号/225号已通过 `ceremony.md` 和 `post-commit-flow.md` 的正面指令驱动。hook 的阻断在步骤7-10是**冗余的**——正面指令已覆盖，hook 只增加噪声。

**方案B-v3**（更彻底）：完全删除 ceremony-step-guard.sh 的 block 逻辑。理由：
- 步骤1-6：已静默退出（228-1）
- 步骤7-10：正面指令已覆盖（ceremony.md + post-commit-flow.md）
- hook 的 block 在所有步骤都是冗余的或有害的
- 这与 137号结论一致："否定性禁令对行为执行层无效"——hook 注入的是否定性指令（"不允许做X"），但 137号已证明否定性约束无效，必须用正面格式驱动

## 观察 2（收敛信号）：v80-v82 连续三轮修复轮无新谱系——结构正常

### 现象

| session | 类型 | 新谱系 |
|---------|------|--------|
| v79-swarm | 域推进（三层系统 v2） | 228号（v77 元观察→v79 结算） |
| v80-swarm | 修复轮（227号下游状态） | 0 |
| v81-swarm | 修复轮（审计修复5处） | 0 |
| v82-swarm | 修复轮（228号下游推论） | 0 |

三轮连续无新谱系。

### 判定

**正常模式，非结构性问题。**

理由：
1. v79 产出了 228号谱系，这是最近一个发现轮
2. v80-v82 是对 227号/228号下游推论的收敛性修复——修复轮不产生新谱系是语义正确的（修复不是发现）
3. 蜂群的谱系产出应呈现"发现轮-修复轮-发现轮"的交替模式，连续修复轮意味着上一个发现轮的影响范围较大
4. 228号有3个下游推论 + 2个 stagnation 信号，需要多轮消化是合理的

### 是否构成"修复债务积累"模式？

不构成。修复债务积累的特征是：修复轮产出新的待修复项（修复引入缺口→需要更多修复→循环）。v80-v82 的修复是收敛性的：
- v80：标记状态 → v82 完成标记
- v81：文档修改 → 审计确认消解
- v82：下游推论全部 resolved

没有修复引入新缺口的证据。这是正常的收敛。

## 观察 3（发散信号）：ceremony_scan.py 的 downstream_audit 重复检出问题

### 现象

根据 v82 session 记录，ceremony_scan 在 v82 触发时检测到 228号下游推论"3项 unresolved"。但 v82 的工位实际修复了这些推论并标记为 resolved。问题是：如果 v80 已经开始处理这些推论，为什么 v82 的 scan 仍然检测到它们？

### 分析

两种可能：
1. **正常情况**：v80 只是部分处理（downstream-status-fix 工位超时），v81 处理的是文档审计不是下游推论，所以 v82 的 scan 确实看到未完成的推论。这与 session 记录一致。
2. **缓存/时序问题**：scan 读取的是磁盘上的谱系文件，如果上一轮 commit 但 push 后文件有更新，scan 可能读到旧版本。

根据现有证据，**情况1更可能**——v80 确实因超时未完成，v82 接续完成是正常的接力模式。不构成缓存/时序缺陷。

### 判定

无异常。ceremony_scan 正确检出了真实的未完成项。

## 观察 4（语法记录候选）：stagnation 检测在修改轮中的误报

### 现象

v82 session 记录了 2 个 stagnation 信号被判定为误报：
- "v80/v81 是修改轮，不产生新谱系是正常的"
- "228号未被引用是正常的：它是最新谱系，时序原因"

### 分析

ceremony_scan 的 stagnation 检测逻辑似乎以"谱系增量"为主要指标（217号观察3 已指出）。修改轮不产生新谱系，因此必然触发 stagnation 信号。这意味着：

**每个修改轮都会产生至少一个 stagnation 误报。**

这是一个可预测的、系统性的误报模式。当前的处理方式是 spawn stagnation-auditor 工位人工判定——但这消耗蜂群资源（一个工位 slot + 上下文 token）。

### 语法记录候选

**候选规则**：ceremony_scan 的 stagnation 检测应区分"发现轮"和"修改轮"。修改轮的预期产出是"下游推论 resolved"而非"新谱系"。检测指标应为：

- 发现轮：谱系增量 = 0 → stagnation 信号
- 修改轮：下游推论 resolved 增量 = 0 → stagnation 信号（如果修改轮也没有 resolve 任何推论，才是真正的停滞）

**判定**：这已在 217号观察3 中识别（"stagnation 检测语义问题"）。v82 提供了新的实例数据但不构成新的语法记录——它是 217号的追加证据。
