# 蜂群递归粒度讨论上下文

## 当前实践

v5-full-push 蜂群中，Lead 将多个任务打包分配给单个工位：
- hook-validator：#1 + #2，然后 #9 的 M1+M2+M6
- code-refactor：#5 + #8
- infra-builder：#4 + #3，然后 #7，然后 #9 的 M3+M4
- gemini-refactor：#6，然后 #9 的 M5+M7

每个工位承担 2-3 个任务，顺序执行。

## 用户的观点

蜂群递归的目的是让每一个任务/子任务/职责都可以递归出单一的 teammate 来做。即 1:1 映射：一个任务 = 一个 teammate。

## 当前做法的问题

1. 工位内部的多任务是顺序执行的，失去了并行性
2. 工位承担多个不相关任务时，上下文被污染（hook验证的上下文对 meta-observer 修复没有帮助）
3. 违反了单一职责原则——一个工位应该只做一件事
4. 如果工位在第一个任务上失败或卡住，第二个任务被阻塞

## 反对意见（Lead 的隐性理由）

1. spawn 成本：每个 teammate 消耗 API 资源和上下文窗口
2. 协调成本：更多 teammate = 更多消息传递 = Lead 的路由负担增加
3. 上下文共享：有些任务有亲和性（如 #5 大函数重构和 #8 CI 都涉及 pyproject.toml）
